# redirects.js

## Responsibility

Server-side redirects from page `aliases`: turn every old URL a page claims into a `301`, in the encoding the site's host reads, and say what a rename left behind. Pure functions throughout plus one writer (`fs.outputFile`) — the module holds no state, knows nothing about `Kiss`, and decides nothing about when it runs.

All three findings are **advisory**. None of them moves `ok`, an exit code, or a page. They are things the build knows and a person cannot see: a page that vanished with no redirect, a page that changed address with no redirect, and a redirect the host is about to ignore.

**An alias is a portable fact; `_redirects` is one vendor's encoding of it.** Until 2.4 the module emitted only that file, which meant a site on Firebase Hosting — which ignores `_redirects` entirely and reads a `redirects` array in `firebase.json` — got a file no host reads while `report().redirects` said the redirects were written. A feature whose whole purpose is "an old URL must not 404" was reporting success while the old URLs 404ed.

So the rules come first and the encoding second. `redirects.json` — `{ version, rules: [{ from, to, status }] }` — is written on **every** build that has aliases, whatever `config.redirects.format` says, and the same array is on `report().redirects.rules`. A site whose host kiss does not encode has the fact, in a file and in the report, and needs nothing from this module to act on it.

`format` then picks the host encodings beside it, and it is **unset by default and takes a list**. Unset means the IR alone: kiss does not guess where a site is deployed. That is a change from v2.3, whose only behaviour was `_redirects`, so `writeRedirects` returns `unset: true` for a build that has aliases and chose nothing and `Kiss` turns that into one `warn` line (a `notice` until 2.5.1: measured on a real site with fourteen aliases, one cyan line was the only thing between it and fourteen live 404s) — an explicit `'none'` or `[]` is a decision and is silent. A list because a site can deploy to more than one host (`['netlify', 'firebase']` emits both files from one build); a bare string or function is a list of one, duplicates collapse, and order is kept. The names are: `'netlify'` (the default, `_redirects`, byte-identical to 2.3), `'firebase'`, `'vercel'` and `'htaccess'` (a **fragment to merge** — `redirects.firebase.json`, `redirects.vercel.json`, `redirects.htaccess`, never the site's own config file), `'none'`, or a writer function. kiss never reads or rewrites `firebase.json`, `vercel.json` or `.htaccess`: those files hold hosting targets, headers, rewrites and authentication, and one real site keeps 227 redirects in `firebase.json` by hand — a build step that rewrote one is a build step that can lose a site's deploy config. The `.htaccess` case is the sharpest of the three, because it is the live server config rather than a deploy manifest.

## Public interface

- `canonicalPathFor(buildTo, buildDir, { trailingSlash })` → the page's origin-less canonical path: `/`, `/courses/`, `/about`. It is `toAbsoluteUrl('', toCanonicalPath(rel))` over the same naive `buildTo.slice(buildDir.length)` the sitemap makes.
- `normaliseAlias(alias)` → the alias as it will be written: leading `/` added, `?query` and `#fragment` removed, repeated slashes collapsed, trailing slash **preserved as written**. `null` for an alias with no path in it (`''`, `'?utm=1'`) and for one with whitespace _inside_ it (`'/old post'`, `'/a\n/b'`): the file is space-separated columns and newline-separated rules, so such an alias would write more than the one rule it stands for — and on a fan-out the alias came from the record, which may have been fetched rather than typed. Dropped silently, like an empty one.
- `collectAliases(stack, { buildDir, trailingSlash })` → `RedirectRule[]` (`{ from, to }`), sorted by `from` then `to`. Reads `entry.page.options.aliases` — an array, or a bare string — from every stack entry that is not `generate: false`; `to` is that entry's `canonicalPathFor`. One page listing an alias twice yields one rule; two pages claiming one `from` yield two.
- `renderRedirects(rules)` → the Netlify/Cloudflare Pages text: one `<from> <to> 301` per line, sorted again, newline-terminated, `''` for no rules.
- `renderRedirectsJson(rules)` → the host-neutral IR: `{ version: 1, rules: [{ from, to, status: 301 }] }`, pretty-printed and sorted, so two identical builds write identical bytes.
- `renderHtaccessRedirects(rules)` → the Apache fragment: one `Redirect 301 <from> <to>` per line, sorted. mod_alias `Redirect`, **not** `RewriteRule` — a rewrite's left-hand side is a regex, so an alias containing a `.` or a `+` would match paths it does not name.
- `renderFirebaseRedirects(rules)` / `renderVercelRedirects(rules)` → a fragment to merge: `{ redirects: [{ source, destination, type: 301 }] }` and `{ redirects: [{ source, destination, permanent: true }] }`. Vercel's `permanent: true` is a 308 — the permanent redirect that platform offers, and the closest honest equivalent of the `301` every other format writes.
- `normaliseWriterOutput(returned, buildDir)` → a custom writer's return value as `[{ file, contents }]`, with `file` resolved under the build folder. A writer returning nothing writes nothing. An absolute path, or one climbing out with `..`, **throws**: a redirect writer is site code running in a build, and "write any file on this machine" is not the capability it asked for.
- `coveredByAlias(rel, fromSet, { trailingSlash })` → whether an alias already answers for a build-relative old **file** path. The match is made **in canonical form** (`/old-post.html` → `/old-post`, `/old/index.html` → `/old/`), which is the form a rule's source and target are both written in; an alias spelled as the file (`/old-post.html`) covers nothing. One predicate, used by `removed` and by `moved`, so the two can never disagree about one page.
- `redirectFindings({ rules, currentPages, previousPages, buildDir, trailingSlash })` → `{ removed, collisions, moved }`, all three sorted. `currentPages` is `[{ buildTo, id }]` for the pages this build writes; `previousPages` is the last record (`{ buildDir, pages: [{ buildTo, hash, id }] }`) or `null`. `removed` and `moved`'s `from`/`to` are **served** paths (`servedPathFor`), not file paths.
- `resolveRedirectFormats(format)` → the host encodings to emit, as a list: `[]` for `undefined`, `null` and `'none'`; a bare string or function as a list of one; an array kept in order with duplicates collapsed and every `'none'` dropped.
- `writeRedirects(stack, { config, logger, overwrite })` → `{ status: 'none' | 'skipped' | 'written', rules, files, formats, unset }`. `none` means no page has an alias: **nothing is written**, not even an empty IR. `files` is every path written, `redirects.json` first; `formats` is the list of names that ran, `'custom'` for each writer function — a machine-readable report should not carry a source-code detail — and `[]` when only the IR was written. `unset` is the upgrade flag: aliases exist, no host file was emitted, and the site never chose. `overwrite: false` protects each target independently, so an existing `_redirects` a project keeps in `src/assets/` survives while the IR beside it is still written.
- The `RedirectRule`, `RedirectFindings` and `RedirectWriteResult` typedefs. `RedirectFindings.moved` is `{ id, from, to }[]`, the same shape `BuildRedirects.moved` carries.

## Depends on

`fs-extra` (`outputFile`/`existsSync`, in `writeRedirects` alone) and `./utils.js` (`toAbsoluteUrl`, `toCanonicalPath`, `servedPathFor`). Nothing else — no logger beyond the one it is handed, no config beyond `folders.build`, `links.trailingSlash` and `redirects.format`, no knowledge of staging, check mode or the report.

Every renderer here is **re-exported from `lib/kiss.js`**, so a custom writer composes a shipped encoding instead of reimplementing one. That is not a convenience: the package's `exports` map has a single entry, so `kiss-ssg/lib/redirects.js` is an `ERR_PACKAGE_PATH_NOT_EXPORTED` and a site literally could not reach them — an extension point nobody can build on, against this package's own stated rule that everything public is reachable from `'kiss-ssg'` itself (llms.txt). They are exported flat rather than under a `redirects` namespace because a site reads `config.redirects` in the same file and `redirects.renderRedirects(...)` inside `redirects: { format: ... }` is a sentence nobody should have to parse.

## Depended on by

`lib/kiss.js` only: `writeRedirects` from `Kiss._writeRedirects()` at the top of `complete()`'s settle path (a write that rejects is pushed onto `_failures` as `<redirects>` and fails the build — unlike the sitemap, llms.txt and the feed, whose write failures are logged and swallowed), and `collectAliases` + `redirectFindings` from `Kiss._redirectFindings()` in `_finishBuild()`, latched on `_redirectsPath`/`_redirectsResult` and handed to `buildReport` as the report's `redirects` key (`AIKB/build-report.md`). The identities `moved` pairs on come from `Kiss._stackForRecord()` — the projected stack, the same one the report and the site map are built from — so the id a person reads on the map is the id the pairing used. The ordering half of this is in `AIKB/kiss.md`.

## Non-obvious behavior

- **Every redirect is a `301`, and the IR's `status` field does not change that.** The value is written into `redirects.json` so a consumer has the code in the data rather than hardcoding it, and it sits on the rule rather than on the file because that is where a `302`, `308` or `410` would belong if the surface grew one. It has not: `aliases` is a bare array of path strings, `normaliseAlias` takes a string, and all four encoders hardcode their permanent form (`301`, `type: 301`, `permanent: true`, `Redirect 301`). The field is a place, not a capability — read it as documentation of what kiss emits, never as a knob. Netlify's forced (`!`) rules, wildcards and splats are absent for the same reason: nothing in the page surface can express them.

- **A custom writer that throws fails the build, deliberately.** `writeRedirects` awaits it inside the promise `Kiss._writeRedirects()` catches, so a rejection lands on `_failures` as `<redirects>` and the staging folder is discarded. Swallowing it would rebuild the exact trap this block was written to close — a redirect feature reporting success while doing nothing — one level up, in the site's own code.

- **An unknown `format` name throws at `resolveConfig`, not at write time.** `'firbase'` would otherwise match no built-in, write no host file, and leave every old URL 404ing while the report looked healthy. `lib/config.js` refuses it with the offending value in the message, the way `cleanBuild` is refused.

- **The alias target is `toAbsoluteUrl('', toCanonicalPath(rel))`, never `toCanonicalPath` alone.** `toCanonicalPath` only drops the last segment's extension; the `index` collapse and the trailing slash live in `toAbsoluteUrl`. Without it a directory index targets `/courses/index` and the home page `/index`, and both 404 (or 301-chain) on Netlify and Cloudflare Pages. With an empty `siteUrl` the same join the sitemap, `llms.txt`, the feed and `{{canonical}}` all make returns the origin-less path — so a redirect can never point at a URL the sitemap does not list. There are four copies of this arithmetic in the engine and they are all one function call; do not write a fifth.
- **A fan-out's aliases come from the record, not from the registration.** `Kiss._prepareMultiplePages` deletes the `.pages()` registration's own `aliases` from each item and promotes `model.aliases` in its place, where `slug` and `model` are promoted. Inherited, one `.pages({ aliases: ['/old'] })` would emit N rules with the same source and N different targets — a redirect whose destination depends on stack order, and a file that is not byte-stable. The reader here only ever looks at `entry.page.options.aliases`, so `.page()` and `.scan()` pass theirs through untouched. Being an ordinary page option, `aliases` also reaches the render context and the dev-mode `.json` sibling: accepted, and occasionally useful — a template may legitimately want to say "formerly at …".
- **A non-forced rule is silently ignored when a real file exists at its source**, on both Netlify and Cloudflare Pages. That is what `collisions` is: an alias equal to a live page's canonical path (`/about`) **or** to its build-relative file path (`/about.html`) is a line that will never fire, and saying "collides" understates it — nothing happens at all, with no error anywhere. A `from` two pages both claim is the same class of nothing: only the first matching line can win, and which one that is depends on sort order. Both are reported in the one list.
- **Findings name served URLs; coverage accepts either spelling.** `removed` and `moved` report `/about.html` or `/old/` — the URL a browser asked for and the one the notice tells the operator to paste into `aliases` — while the comparison behind them stays on build-relative file paths. `coveredByAlias` accepts an alias in the canonical form (`/about`) or the served form (`/about.html`), so the alias a finding recommends always silences it.
- **`moved` pairs the two builds by `id`, and only on a non-empty string present on both sides.** Same id, different build-relative path, old path not covered by an alias → one `{ id, from, to }`. `null` means two different things — a page that claims no identity (an inline template, a `generate: false` page, a default id `Kiss` withdrew from two pages) and, in a record written before ids existed, a key that is not there at all — and pairing nulls would pair every idless page with every other and report a whole site as moved. Anything unpaired degrades to the path comparison `removed` has always made, so an old record still answers exactly as it did.
- **`moved` is computed first and suppresses `removed` for the same page.** A page whose id paired is accounted for — it moved, it stayed put, or an alias already covers the move — and the removal loop skips its old path. Without that one rename produces two findings and two notices, and a person fixing the second is fixing something that does not exist. It is also why `Kiss._redirectFindings()`'s "nothing to say" short-circuit is `rules.length === 0 && removed.length === 0 && moved.length === 0`: a move is the one finding a site with no alias anywhere can still have.
- **`moved` only sees a rename that kept the page's identity, and that is a real limit.** A `.pages()` item's default id embeds its slug (`blog/post/<slug>`), so the commonest rename of all — a post's slug — changes the id as well as the path, the two sides do not pair, and the event is reported as a `removed` instead. `moved` is for pages whose id is stable: a `.page()` page whose `path`, `slug` or `ext` changed, and any page (a fan-out record included) carrying an explicit `id`. Say this out loud wherever `moved` is documented rather than letting somebody discover it on the one rename they cared about.
- **`removed` compares build-relative paths on both sides, and that is the whole point.** `buildTo` is `${config.folders.build}/${pageURL}` verbatim, so the same site recorded from `examples/` (`../public/site/index.html`) and rebuilt from the repo root (`public/site/index.html`) shares not one path string. Comparing raw paths — which `diffReports` does, guarding itself instead by pairing on `buildDir` and ignoring an unpaired baseline — would report every page of an untouched site as removed the first time anybody ran the check from another folder. `diffReports` is deliberately **not** reused here for that reason: this finding has to survive the cwd changing, and it answers a narrower question anyway (removed, _and_ not covered by an alias).
- **A page the record wrote no bytes for was never published.** A record is only ever written by a build that passed, so a `null` hash in one is a `generate: false` page; it is skipped rather than reported as a loss.
- **A `generate: false` page contributes no rules either** — there is no file at its canonical path, so a rule pointing at it would redirect one 404 to another. Same filter, same reason, as `sitemap.xml`, `llms.txt` and the feed.
- **No aliases means no file, not an empty file.** A project that keeps a hand-written `_redirects` in `src/assets/` has it copied into the build like any other asset; `writeRedirects` returning `none` leaves it exactly as it was. kiss never merges with that file and never deletes it — when the site does declare aliases, kiss's own file wins, because it is written after the asset copy has drained.
- **The module never decides the report's `null`.** `redirectFindings` always answers with all three lists; `Kiss._redirectFindings()` is what turns "no alias and no finding" into `null` on the report, so that a recorded site nothing has happened to reads the same as a site that uses neither feature — and so two identical records write byte-identical `last-build.json` files, the first of them made before there was any baseline to read.
- **Everything is sorted twice and the file is newline-terminated**, so two identical builds write identical bytes. The record (`AIKB/last-build.json`) carries `redirects` with it, and a file that churned would make every diff of that record meaningless.
