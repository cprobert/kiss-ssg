# watcher.js

## Responsibility

Watches the entry script, configured content folders, assets and helpers. Source events are dispatched by Kiss; asset events reconcile copied outputs through the same rebuild queue.

## Public interface

- `createWatcher({ config, entry = process.argv[1], rebuildSite, onChange, assetsChanged, helpersChanged, logger })` → `{ ready, close }`.
  - `ready` — `Promise` that resolves once every underlying chokidar watcher has fired its own `'ready'` event.
  - `close()` — `async`; closes every watcher. Required for the Node process to be able to exit (chokidar watchers otherwise keep the event loop alive).
  - Watches the entry script for changes; a deduplicated set of `src`, `pages`, `layouts`, `partials`, `models` and `controllers` for source events; helpers for add/change/unlink; assets for add/change/unlink/unlinkDir. Assets call `assetsChanged(posixPath, event)`. Initial scan additions are suppressed. Null folders are not watched. Every watcher logs errors.

## Depends on

`chokidar` (required on first `createWatcher()`), `node:fs` (`statSync`, for the empty-file check); `node:path` (containment); `./utils.js` (`posixPath`, `isInside`).

## Depended on by

`lib/kiss.js`.

## Non-obvious behavior

- Asset log lines name the dispatched event (`Asset add`, `Asset change`, `Asset unlink`, `Asset unlinkDir`) and are emitted inside the settled callback, after coalescing transient empty saves.

- `entry` defaults to `process.argv[1]` (the script that configured `Kiss`) because ESM has no equivalent of CommonJS's `module.parent` — there's no reliable way to ask "who required me" under ESM, so the watcher instead watches the top-level script itself and rebuilds the whole site on any change to it. **That rebuild cannot read a changed page list, and the wording here used to claim it could.** The script is already in the ESM cache and `Kiss._replay()` replays the registrations logged at start-up, so a `.page()` added, removed or renamed in the entry script does not reach the running build — measured: the log said `Rebuilding site:` and the new page was never written. The replay is still worth doing (a template or model edit saved alongside does take effect), so `Kiss` keeps it and prints a notice naming the restart instead. Making the failure honest rather than making it work is the deliberate choice: re-importing the entry script would re-run every registration against a live stack.
- `watch({ entry: null })` disables the entry-script watcher entirely — tests use this to avoid an extra open file handle / watcher they don't need, since they configure `Kiss` from a helper module rather than a real "entry script".
- **The `add`/`addDir` burst from chokidar's initial scan is the one thing the `src` watcher filters out.** The gate is a `scanned` boolean set by that watcher's own `'ready'` handler: chokidar emits an `add` for every existing file during its initial scan, and forwarding that burst would rebuild the site once per file at startup. It is the reason the old `if (event.includes('add')) return` guard existed; that guard also made newly created files invisible until restart, and a page edited to reference a new partial then failed to render with its error swallowed, so the page looked frozen (review finding B2). Real `add`s are forwarded like any other event, and `Kiss` sends them to a full replay.
- A new page view on a `.scan()`-registered site is built by the replay the `add` triggers: `_replay()` re-runs `scan()` when `_scanRequested` is set, so a view that did not exist at the first scan joins `_registrations` there. On an explicitly registered site the replay is a harmless no-op for the new file, which was never going to be auto-discovered. See `AIKB/kiss.md`.
- Source roots exclude assets, helpers and build output with containment predicates. Ancestor roots subsume descendant roots, avoiding duplicate dispatch; configured content outside `src` is watched too. Build output under `src/public` is ignored so generation cannot trigger a rebuild loop. Null assets do not fall back to `src/assets`.
- **Which stack entry (if any) a change belongs to is no longer decided here.** Matching a path against the stack by `view`, sending a partial or layout edit down the scoped fast path, and routing everything else to a replay all live in `Kiss._handleChange` — the watcher has no access to the stack, the partials registration or the rebuild queue, and splitting the decision across two modules is what let the old `getStack()`/`rebuildPage` pair drift from what the queue actually did. The dispatch table is in `AIKB/kiss.md`.
- `rebuildSite` survives as the entry-script watcher's callback only: a change to the script that configured `Kiss` can change anything about the build, so it is always a whole-site replay and never needs the path. `Kiss` logs the restart notice from inside that callback (`watch()`), not here — the watcher decides nothing.
- A site rebuild is not purely additive: `_replay()` also deletes output files the previous stack wrote that the new stack no longer produces (and re-runs `sitemap()` if one was ever requested), so deleting a model from a `.pages()` fan-out folder, or changing a slug in a controller, actually removes the old page from the dev server — see `AIKB/kiss.md`. That includes a page whose model or controller fails to resolve mid-rebuild (e.g. a half-saved JSON file caught by `chokidar` while still being written): the page is simply never re-prepared, so it drops out of the new stack and its previous output is removed like any other orphan — the dev server 404s on it rather than continuing to serve the stale HTML until the next valid save.
- Nothing the watcher calls is awaited by it, but every rebuild it triggers is still tracked: `Kiss` puts each render on `_generating` and serialises the work through its rebuild queue, so a whole-site rebuild triggered moments later waits for it (and for any still-resolving initial build) before it resets the stack — see `AIKB/kiss.md`.
- Every watcher registers `'error'` → `logger.error('Watcher error', err.message)`. Chokidar emits `'error'` on things like an `EPERM`/`ENOSPC` from the underlying OS watcher; without a listener that is an unhandled `'error'` event, which crashes the process.
- `ready` resolves when every active watcher has completed its initial scan (including a configuration with no active watchers). Await it before testing authoring events.
- All four watcher roles are created with `awaitWriteFinish: { stabilityThreshold: 30, pollInterval: 10 }` (`WRITE_SETTLE`), so a rebuild fires ~30ms after a file's size last changed rather than on the first notification. Editors and `fs.writeFile` can emit several `change` events per save; without this, a rebuild can read the file mid-write (old or truncated content), and under load the follow-up notification can be deduped/throttled by chokidar so no corrective rebuild ever happens.
- **A delete also takes ~100ms to arrive, for a different reason.** Chokidar's `atomic` option is on by default: it parks every `unlink` for 100ms and cancels it if an `add` for the same path lands inside that window, which is how a write-tmp-then-rename-over-target save reaches us as one `change` instead of `unlink` + `add`. So an `unlink` is delivered late, not lost: measured over 1500 delete-and-wait cycles run 6-up on 4 cores, chokidar dropped none and the worst latency was 104ms. Watch tests that time a deletion should budget against that floor, not against the poll interval.
- **`chokidar` is required on the first `createWatcher` call, not at module import.** `lib/kiss.js` imports this module for the dev-only branch, so a one-shot build was loading chokidar to never call it. A synchronous `require` keeps `createWatcher` synchronous, which `Kiss.watch()` needs — it is chainable public API returning `this`, not a promise.
- **`awaitWriteFinish` is set to a 30ms threshold with a 10ms poll, and that number is the dev loop's felt latency.** It is pure idle — chokidar sits on the event until the file's size has held still that long — so it surfaced in the benchmark as a re-render cost of ~108ms that was identical at 50 and 500 pages, and identical again on a machine 25% slower. A figure that ignores both page count and CPU speed is a timer, not work. Dropping it from 100ms took re-render to ~37ms (-66%), at both page counts.
- **Empty saves receive a bounded 200ms grace period after the normal write-settle check.** A following event cancels the timer; a pending add stays an add when content arrives, so new-page discovery is retained. A file still empty at expiry is forwarded: intentionally clearing a partial must clear its rendered content. `close()` cancels timers and prevents further dispatch. A save delayed beyond the grace period can still expose a transient empty state; this is a debounce, not an atomic-write guarantee.
- **Why 30ms is still a wide margin:** the threshold only has to outlast the gap _between_ successive writes, not the write itself — while a file is still growing its size keeps changing, so the wait keeps extending. What it must cover is a truncate-then-write (vim, and anything that does not write atomically), where the file is briefly empty or partial between two syscalls; that gap is sub-millisecond on a local filesystem, and the watched sources are templates, models and controllers — small text files. `test/unit/watcher.test.js` pins the property rather than the number: it writes a file in two syscalls and asserts the handler never observes the half-written state, capturing the content _inside_ the handler because a later read would find the file complete either way.

- **`config.folders.helpers` gets a watcher of its own, whether or not the folder exists yet.** It was installed only when the folder was already there at `watch()` time, which meant that writing a first `helpers/index.js` mid-session got no watcher, no rebuild and no notice — and the restart notice that might have covered it is suppressed for this folder by design, so nothing said anything at all. It now takes the same three events as the `src` watcher (`add`, `change`, `unlink`), suppresses chokidar's initial-scan `add`s the same way, and applies the same `isEmptyFileEvent` guard, so a truncate-then-write save gets a grace period; a file still empty after 200 ms is delivered and may unregister every helper. It exists because the helpers folder sits beside the build script, outside `src`, where no other watcher sees it — and because `Kiss` can now do something useful with the event: `helpersChanged` re-imports the module on a cache-busted URL, re-registers (Handlebars replaces a helper of the same name; a name the new source dropped is unregistered) and re-renders every page — for an edit to the **entry**. For a module the entry imports, and for a delete, `Kiss` decides differently: see `AIKB/site-helpers.md`. That is the difference between this and the `src` fallthrough, which could only ever trigger a replay that ran the cached module and changed nothing. A site that points `folders.helpers` _inside_ `src` is excluded from the `src` watcher, the same way `folders.assets` is and for the same reason: both have a watcher of their own, and a second dispatch for one file is not a harmless duplicate. It used to get both — a whole-site replay that cannot pick a module edit up, racing the reload that can, over one registry — and `Kiss._handleChange` only ever suppressed the restart _notice_ for that folder, never the replay.

- A pending empty add followed by unlink cancels discovery without forwarding a deletion for a file never delivered. `isInside` is imported from `utils.js`; its tests live with that module and there is no watcher re-export; config and Kiss use that same containment predicate.
