# feed.js

## Responsibility

Builds an RSS 2.0 feed from the page stack and writes it to the build folder. The third file derived from the registry, beside `sitemap.js` and `llms.js`: same pages, same titles, same URL derivation, a different reader — a feed client rather than a crawler or an answer engine.

## Public interface

- `feedFileName(options = {})` → `options.filename` (whitespace-collapsed), else `'feed.xml'`. The one place the default lives, so `Kiss.feed()` and `writeFeed` cannot disagree about where the file went.
- `toDate(value)` → a `Date`, or `null`. Accepts a `Date` (copied, never aliased), a finite number read as epoch milliseconds, or a non-blank string `new Date()` parses. Anything else — a boolean, an object, `'last Thursday-ish'`, `Infinity`, an `Invalid Date` — is `null`.
- `buildFeedItems(stack, { siteUrl, buildDir, section, dateField = 'date', limit = 20, logger })` → `{ items, undated }`. One `{ title, url, description, date }` per page that survives every filter and carries a readable date; `undated` counts the pages that survived the filters but had no usable one. Skips a page whose `page.options` has `ignoreFeed`, `ignoreSitemap` or `generate === false`, and — when `section` is given — one whose first `path` segment is not that section (both sides through `topSegment`, so `'/Blog/'` matches `blog/`). `url` is `toAbsoluteUrl(siteUrl, toCanonicalPath(buildTo.slice(buildDir.length)))` — the identical join `buildSitemapEntries` and `buildLlmsEntries` make. `title` and `description` come from `llms.js`'s own `entryTitle`/`oneLine`. Sorted newest first with the `url` as the tie-break, then truncated to `limit` (a non-finite or negative `limit` means no cap; `0` means no items).
- `renderRss(channel, items)` → the document's text, one trailing newline. `channel` is `{ title, link, description, feedUrl }`. Emits `<rss version="2.0" xmlns:atom="…">`, a `<channel>` with `title`/`link`/`description`/`atom:link rel="self"`, `<lastBuildDate>` when there is at least one item, then one `<item>` per entry with `title`, `link`, `guid isPermaLink="true"`, `pubDate` (`toUTCString()`) and `description` (omitted when empty). Every text node and attribute value is XML-escaped.
- `async writeFeed(stack, { config, logger, options, overwrite = true })` → `Promise<{ status, text }>`. `status` is `'no-site-url'` or `'no-title'` (nothing written), `'skipped'` (`overwrite: false` and a file exists), or `'written'`.

## Depends on

`fs-extra`; `./llms.js` (`entryTitle`, `oneLine`, `topSegment`); `./utils.js` (`toAbsoluteUrl`, `toCanonicalPath`).

## Depended on by

`lib/kiss.js` (`Kiss.feed()`, and `feedFileName` for the `_feedPath` it records for the build report). `lib/sitemap.js` and `lib/llms.js` are siblings rather than consumers: all three read the same stack and make the same `buildTo` → `toCanonicalPath` → `toAbsoluteUrl` join, and `ignoreSitemap` excludes from all three.

## Non-obvious behavior

- **`<lastBuildDate>` is the newest item's date, never the wall clock.** The success criterion for this file is that two identical builds produce identical bytes — a build script that commits its output, and a `kiss-ssg check` diffed against a recorded build, both depend on it; so would `test/integration/replay-equivalence.test.js`'s byte-comparison of two build folders, the day a site under it calls `.feed()`. A `new Date()` in the channel would make every build differ from the last for no reason anyone could act on. The newest item's date is the honest answer anyway: nothing in the feed changed since then. With no items there is no date to claim, so the element is left out rather than invented. `lib/sitemap.js` makes the same move one step less far, injecting `now` as a parameter; here there is no parameter to inject because there is nothing a caller could usefully pass.
- **A date is read from the page option first and the resolved model second, under one field name.** `options[dateField] ?? options.model?.[dateField]` — `dateField` governs both lookups, so a site that dates a post in its `models/posts/*.json` and a site that dates it in the `.page()` call read the same key and neither has to know which the other used. By settle time `options.model` **is** the resolved data (the `.pages()` fan-out has already given each item its own), which is what makes the model lookup possible at all. It is guarded for `null` (a page with no model) and for an array (a non-`dynamic` page handed an array model, which has no date of its own); both are undated, neither is an error.
- **A page with no date is silent; a date that cannot be read warns once.** Most of a site is undated — an About page is not a post — so warning per undated page would bury the feed's own output in noise on every build. A value that was _given_ and cannot be parsed is a typo the author wants to hear about, so it gets one `logger.warn` naming the page and the value, and the page joins the undated count. Neither ever throws: a feed is not the render error channel, and a build minus one item is still the build the author asked for. `writeFeed` logs the total as one `info` line, which is the only place the count surfaces — `report().feed` is the path, not the tally.
- **The `url` is the sitemap's `<loc>`, character for character** — a home page (`https://e.com/`), a file page (`/about`) and a directory index (`/courses/`) alike, because the derivation is the same two `utils` functions. An RSS `<guid isPermaLink="true">` that disagreed with the sitemap would be a second identity for one page, and a feed reader would show the post twice after a rename.
- **Escaping is one function for text and attributes.** `&` is replaced first (or it would re-escape the entities that follow it) and both quote forms go, so the same function is correct inside `<title>` and inside `atom:link`'s `href`. `lib/sitemap.js` escapes nothing at all, which is a standing bug there rather than a precedent here.
- `writeFeed` deliberately does **not** catch its own write error (`fs.outputFile` can reject) — it propagates to `Kiss.feed()`'s `.catch()`, which logs it and does not invoke the callback. Same contract as `writeSitemap` and `writeLlms`.
- **`writeFeed` refuses a `filename` that resolves outside the build folder** — `Refusing to write outside the build folder: <path>`, thrown before the `overwrite` check so it reaches `Kiss.feed()`'s `.catch()` like any other failed write. It is the same `path.resolve` containment check `KissPage.generate()` makes (`AIKB/kiss-page.md`), and the feed is the only one of the auxiliary files whose name the author chooses (`sitemap.xml`, `llms.txt` and `_redirects` are fixed), so it is the only one that needs it: under `'atomic'` and under check `folders.build` is a staging sibling that was promised to be the only thing written, and `filename: '../x'` would have written beside it. `oneLine` collapses whitespace in the name; it does not touch `..`.
- `overwrite: false` only has an observable effect with `cleanBuild: false` too — the default `cleanBuild: true` empties the build folder in the `Kiss` constructor, so there is never an existing feed left to skip.
