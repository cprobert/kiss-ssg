# kiss.js

## Responsibility

The orchestrator and public API. `Kiss` owns config, a per-instance Handlebars environment and Remarkable renderer, the `_stack` of prepared pages, the `_registrations` log of pages as the caller asked for them, and the `_promises`/`_generating`/`_callbacks` queues that track every piece of async work (model resolution, asset copying, generate/sitemap runs, and the promises callbacks return). Every other `lib/*.js` module is wired together and driven from here.

## Public interface

- `class Kiss` (default export), also re-exported as `export { Kiss as 'module.exports' }` so `require('kiss-ssg')` on Node ≥22.12 returns the class, not `{ default: Kiss }`.
- `new Kiss(config)` — resolves config, sets up Handlebars/Remarkable and the instance's asset manifest, ensures folders, queues an asset copy, registers helpers and partials, and (in dev mode) starts the dev server and watcher. A dev server that cannot bind is a **build failure** — see the `<dev server>` bullet below. `_setupFolders()` is also where `cleanBuild` is applied: `true` empties `folders.build` here, `'atomic'` redirects it to a staging sibling — see the staged-build bullets below.
- `.copyAssets(sourceDir, targetDir)` — puts `targetDir` through `_stagedPath()` (a staged build's copies have to follow it into staging) and chains `copyAssets()` onto `_assetQueue` (passing `_assetManifest`, so every copy records into the one manifest the `asset` helper reads) (a `Promise` that serializes calls in registration order) and pushes the chained promise onto `_promises`; returns `this`. Sequential rather than concurrent because one copy's target can be a subdirectory of another's source (e.g. a consumer copying into its own assets folder), and concurrent `fs.copy` walks racing there produce `ENOENT` failures. `_assetQueue` is reset to `Promise.resolve()` alongside `_promises`/`_generating`/`_failures` (and the `_failuresReported` latch) in `_replay()`.
- `.registerPartials()` — re-runs `registerPartials()` against the current Handlebars env, passing the names the previous pass registered so any that have since left disk are unregistered; stores and returns the new set.
- `.page(options)` — attaches a per-page copy of the config, resolves the page's model, runs its controller, prepares a `KissPage`, pushes it onto `_stack`; returns `this`.
- `.pages(options)` — same as `.page()` with `options.dynamic = true` (one page per model in an array); returns `this`. A bad item fails only its own page and is reported on its own — see the `_prepareMultiplePages` bullet below.
- `.scan()` — globs every `.hbs` under `config.folders.pages` (via `utils.globFiles`, so the list is sorted and posix-normalised) and calls `.page()` for any view not already in `_registrations`; sets `_scanRequested` so watch rebuilds scan again; returns `this`.
- `.viewStats()` — logs `{ promise, stack }` counts (and, if `verbose`, writes `debug.json` to the build folder); returns `this`.
- `.generate(callback)` — sets the `_generateRequested` latch, awaits `_promises`, renders every stack entry with `runCount === 0` once (each render caught, failures collected on `_failures`), awaits the writes, invokes `callback` through `_runCallback` (so a callback that throws, or returns a rejecting promise, is collected on `_failures` too); returns `this`.
- `.complete(callback)` — awaits `_settle()` (drain, then render whatever the drain left unrendered, repeated until the stack is stable), then **rejects with an `AggregateError`** if `_failures` is non-empty and `_failuresReported` is not yet set; otherwise invokes `callback` with the resolved data (never on a failed build) and returns that data (a `Promise`, unlike the other chainable methods). Under `cleanBuild: 'atomic'` this is also the promotion point: a settle with no failures promotes the staging folder, a settle with failures discards it — and in check mode a settle with no failures discards it too. It is also where the build report is assembled (`_finishBuild()`), so `report()` and `err.report` are set by the time either outcome reaches the caller.
- `.sitemap(options, callback)` — records the request on `_sitemapRequest` (so watch rebuilds re-run it), awaits `_promises`, writes `sitemap.xml` via `writeSitemap()`, invokes `callback` through `_runCallback`; returns `this`.
- `.getModelByID(id, data)` — looks up `{ id }` in a resolved-models array; returns `.data` or an error object.
- `.watch({ entry = process.argv[1] } = {})` — starts (once) a `createWatcher()` wired to `_handleChange` (every `src` event), `_requestReplay()` (the entry script) and `copyAssets()` + a live reload (the assets tree); returns `this`. What each event means is decided in `_handleChange` — the dispatch table is below — and every rebuild it asks for goes through the serial queue.
- `.report()` — the last settled build as data (`AIKB/build-report.md`), or `null` before the first `complete()` settles. The same object is on the rejection as `err.report`, and a watch rebuild replaces it with its own.
- `.close()` — sets `_closing`, closes the watcher, drains the rebuild queue, closes the dev server, and removes an un-promoted staging folder; a closed instance stays closed.
- `export { utils }` — re-exports `lib/utils.js`'s default export.

`fs-extra`, `node:path`, `handlebars`, `handlebars-layouts`, `remarkable`; and `./utils.js`, `./logger.js`, `./config.js`, `./build-report.js`, `./handlebars-helpers.js`, `./partials.js`, `./assets.js`, `./asset-manifest.js`, `./model-resolver.js`, `./controller-resolver.js`, `./sitemap.js`, `./kiss-page.js`, `./dev-server.js`, `./watcher.js`.

## Depended on by

Nothing in `lib/` — it is the entry point (`package.json`'s `main`). `bin/kiss-ssg.js` drives it from the outside, through the two environment variables below rather than through the API.

## Non-obvious behavior

- Pipeline: `.page()`/`.pages()`/`.scan()` queue work (model → controller → `_preparePage`) as one caught promise per page on `_promises`; nothing renders until `.generate()`. `.generate()` awaits `_promises`, renders every stack entry whose `runCount` is 0, awaits the writes, then fires the callback. `_generating` tracks `generate()`/`sitemap()` runs, `_callbacks` the promises callbacks themselves returned. `complete()` drains all three lists repeatedly because callbacks may queue more work, and then renders anything the drain left unrendered.
- **The build folder is written by four things, and `config.folders.build` is the single handle on all four.** Pages (`_preparePage` copies it onto each `KissPage.buildDir`, which `buildTo` is composed from — plus the dev-mode `.json` debug sibling beside each page), the asset copy (`copyAssets(folders.assets, folders.build)` at construction, and again on a watched asset change), `sitemap.xml` (`writeSitemap` reads `config.folders.build`), and `viewStats()`'s `debug.json`. Nothing writes into the build by any other route, which is what makes the staged build below a one-line redirection rather than four separate detours.
- **`cleanBuild: 'atomic'` builds into a staging sibling and swaps it in on success.** `_setupFolders()` keeps the folder the consumer asked for in `_buildTarget` and points `config.folders.build` at `<build>.kiss-staging-<pid>-<random>`, so all four write paths above land there with no further plumbing; the real folder is not touched at all until the swap. `complete()` is the decision point: a settle with no failures calls `_promote()`, and a settle with failures calls `_discardStaging()`, which deletes the staging folder and leaves the previous output exactly as it was. Promotion happens **once**: `_buildSettled` latches, so the nested `complete()` pattern's second call is a no-op and, crucially, a second `complete()` after a failed build (which resolves rather than re-rejecting, see the report-once bullet) can never promote a build that failed. The failure message names the target path, not the staging path (`_reportedPath`), because the staging folder is an implementation detail the operator should not have to decode.
- **Promotion is rename-aside, not remove-then-rename**, so the previous output is never absent for the length of a recursive delete. `_promote()` renames the existing target to `<build>.kiss-old-<same suffix>` (both siblings of one build share the `<pid>-<random>` suffix, so a leftover pair is recognisably one crashed run), renames staging into the target, and only then removes the old folder. The previous output is therefore absent only _between two renames_ — metadata operations on one filesystem — and if the second one fails, the cross-device `fs.move` fallback is tried, and if that fails too the fragment it wrote is removed and the old folder is renamed back before the error is rethrown, so a failed promotion ends with the previous output byte-identical. The one case that cannot be repaired automatically is a restore that itself throws: the old folder then holds the only copy, so it is named in an `error` line and `close()` deliberately leaves it alone while the target is missing (it removes `_oldDir` only when the build folder is back in place). `_stagingDir` is likewise cleared only after the swap, so a promotion that threw still leaves the staging folder for `close()`.
- **A crashed run's siblings are swept at construction.** `_sweepStaleSiblings()` (atomic, non-dev only) removes any `<build>.kiss-staging-*` / `<build>.kiss-old-*` beside the target and logs one `notice` naming them, so a killed build does not leave a copy of the site accumulating beside published output. Siblings carrying **this** process's pid are skipped: those belong to a live instance, which is the case a second `Kiss` building the same target in one process would hit.
- **After a promotion the instance is an ordinary one.** `_promote()` points `config.folders.build` back at the real folder and re-points every stack entry's `buildDir`/`buildTo`, so a second build on the same instance — or a watch rebuild — writes into the promoted folder instead of a staging sibling nothing will ever swap in again. `_stagedPath()` covers the one write that does not read `folders.build`: a `copyAssets()` the consumer aimed explicitly at the build folder (or a subfolder of it, the metacarpus idiom) is rewritten into staging, or the promotion's `fs.remove(target)` would delete the files that copy had just made. A copy aimed anywhere else is left where it was asked for.
- **`'atomic'` is a one-shot-build feature, and dev mode says so.** With `dev: true` the promotion point is the wrong shape — the dev server serves `folders.build` from construction and every rebuild would have to promote — so `_setupFolders()` degrades `'atomic'` to `true` (wipe at construction, build in place) and logs one `notice` saying that atomic promotion applies to one-shot builds. A **non-dev** `.watch()` is the one seam left: it stages, promotes at the first successful `complete()`, and behaves as an ordinary watch after that. A build that never calls `complete()` never promotes, and `close()` removes the staging folder — which is also what clears a discarded one that a later write recreated (`_discardStaging` deliberately keeps `_stagingDir` set for exactly that).
- **Every settled build assembles exactly one report** (`_finishBuild()`, `AIKB/build-report.md`), after the staging folder has been promoted or discarded so every path in it names the folder the site asked for. It is latched on `_report` rather than on `_failuresReported`, because the nested-`complete()` pattern settles one build twice and `KISS_REPORT` takes one line per build, not per call; `_report` (and `_sitemapPath`, and `_startedAt`) reset in `_replay()` with `_failures`, so a watch rebuild reports itself rather than the first build, and `duration` measures that rebuild rather than the hours the dev server has been up. The report is deliberately additive: `complete()` still resolves with the `generate` data array and still rejects with the `AggregateError` — consumers documented in `llms.txt` rely on both — and the report rides along on `err.report`.
- **Check mode is the one place the engine reads process state.** `KISS_CHECK` is read once in the constructor (`checkModeRequested()`), never in `resolveConfig`, which stays pure. It forces `cleanBuild: 'atomic'` and `dev: false` over the resolved config before `_setupFolders()` runs — so every write goes to the staging sibling and the real build folder is neither emptied nor written — and at the settle it **discards** the staging folder on success as well as on failure. `dev` cannot survive it: `'atomic'` degrades to a wipe in place under a dev server, and a check has to exit. Any value counts as on except `''`, `'0'` and `'false'`: `KISS_CHECK=true` falling silently through to a real build over published output is the one outcome the feature exists to prevent. `KISS_REPORT=<file>` is the second half of the channel — each settled build appends its report as one JSON Lines row, because a script may build several sites (`examples/7-versioned-outputs.js` builds two) and `bin/kiss-ssg.js` wants them all. A report that cannot be written is logged, never fatal. Neither variable changes the script's own exit code; the bin decides that (`AIKB/check.md`). What check mode cannot make honest is a script that reads its own build folder back after `complete()`: example 7's archive index lists the season folders on disk, and under a check no season was published, so it reports none.
- **A staged build's `folders.build` is genuinely the staging path while it runs**, so a template rendering `{{config.folders.build}}` (or a controller reading it) sees the staging name, not the target. Nothing in the engine surfaces it — `{{asset}}` renders build-relative paths and `{{canonical}}`/`sitemap.xml` are built from `siteUrl` — but a site that prints the raw folder into its output should not use `'atomic'` for that page.
- Build failures are collected, not thrown at the page: `KissPage.generate()` rethrows a render/minify/write error, `generate()` catches it per page into `_failures` (`{ view, buildTo, error }`) so the remaining pages still build, and `complete()` rejects with an `AggregateError` (`err.failures` = that array, message `"N page(s) failed to build: <buildTo paths>"` — `buildTo`, not `view`, because `.pages()` fan-out gives every failed entry the same `view` and a message built from `view` would repeat it; `err.failures[]` still carries `view` per entry). Entries with no output path — a controller failure, or a callback failure — fall back to `view` in that message. `generate()`'s own callback still fires either way — callbacks are not the render error channel; `complete()` is. `complete()` does not invoke its callback on failure (same rule as `sitemap()`'s callback).
- **`complete()` reports a build's failures once** (`_failuresReported`, reset with `_failures` in `_replay()`): the first call with a non-empty `_failures` rejects, every later call in the same build resolves with the data instead. It used to re-reject, and the documented "`complete()` from inside a `generate` callback" pattern (below) has two calls draining the same build concurrently — the loser's rejection had no handler attached to it and killed the process after the consumer had already caught and reported the winner's (review finding A-01). The outer call wins in practice: its `_drain()` registered its reactions first, so it stays one microtask ahead of a call started from inside the callback.
- **A `generate()`/`sitemap()` callback that throws is a build failure**, recorded by `_runCallback` as `{ view: '<generate callback>' | '<sitemap callback>', buildTo: null, error }` — not swallowed by the enclosing `.catch()`, which would log it as `Error generating site` or, worse, `Error creating sitemap.xml` for a sitemap that had in fact been written correctly (review finding A-04). The two catches are now distinct: the enclosing one covers the engine's own work, `_runCallback` covers the consumer's. The callback's return value is still not awaited by the `generate()` run itself (see the `complete()`-inside-a-callback bullet below), so a promise it returns gets its own `.catch` — but that caught promise is now recorded on `_callbacks`, which `_drain()` waits for (review finding A-03). So an async callback that rejects is reported by the `complete()` that was already draining, not deferred to a later one; the only rejection still reported late is one from a callback registered after every `complete()` has finished.
- **A dev server that cannot bind is a build failure**, recorded as `{ view: '<dev server>', buildTo: null, error }` — the same shape as a callback failure, since there is no output path to name it by (review findings F-E2/F-E3). It used to be non-fatal and mislabelled: the constructor's `ready.catch` logged `Error running live reload server` for the _static_ server, a second copy of the same fault had already been logged inside `lib/dev-server.js`, and the build then ran to completion with the process left up serving nothing behind an already-printed `Serving …` line. Now `dev-server.js` logs nothing for a bind failure and `ready` carries the whole message; the constructor logs it once, records the failure so `complete()` rejects, and then `await this.close()`s — unlike live reload, which is optional, there is nothing useful to do without the HTTP server, and the watcher plus the (successfully bound) livereload server would otherwise hold the process open long after the consumer's rejection handler had run. The `ready.catch` promise is pushed onto `_generating` so the drain waits for the bind result: a small site would otherwise race the `'error'` event and `complete()` could resolve before the failure was recorded. A synchronous throw out of `startDevServer` takes the same path, and `watch()` is never reached in that case.

- Model failures are _not_ build failures: they keep the documented log-and-skip behaviour and appear in `complete()`'s resolved data as `{ id, data: null, error }`. The page is simply never prepared, so there is nothing to render.
- **Controller failures are.** A controller that throws, a controller file that does not exist, a controller module that does not export a function, and an unrecognised `controller` type now throw out of `applyController` (review finding F-01), and `page()` catches everything downstream of the resolved model in a `try` that pushes `{ view, buildTo: null, error }` onto `_failures` and rethrows (a `.pages()` fan-out never reaches it — it records its own per-item entry and keeps going, see below) — so the chain's `.catch()` still resolves to `{ id, data: null, error }` (`_promises` never rejects) _and_ `complete()` reports it. The `try` sits inside the `.then()`, not in the shared `.catch()`, which is what keeps the two apart: a model rejects before the `.then()` ever runs. Anything else the `.then()` does — `_preparePage`, slug/path derivation — is inside the `try` too, and is a build failure for the same reason: the page cannot be built correctly, so the build must say so rather than ship it.
- `_promises` must only ever contain _handled_ (caught) promises — a bad model rejecting unhandled crashed the process in v1. The `.page()` chain's `.catch()` always resolves to `{ id, data: null, error }` instead of rejecting.
- `_partialNames` holds what the last `registerPartials()` pass registered, and is handed back to the next one. Handlebars never forgets a registration on its own, so without that set a partial deleted from disk would keep rendering its last-known content for the life of the process (review finding B1). The state lives here, not in `partials.js`, because the Handlebars env is per-instance — see `AIKB/partials.md` for why the diff is by name across all four passes rather than per file. A page that still references a deleted partial now fails on the replay: `complete()` collects it in `_failures` and the rebuild queue logs `Error rebuilding site`, and the page's stale output is left alone because it was never rewritten.
- Handlebars and Remarkable are created fresh per `Kiss` instance so partials/helpers from one instance never leak into another (matters for tests that build multiple sites in one process).
- `export { Kiss as 'module.exports' }` exists purely so CJS `require('kiss-ssg')` returns the class itself on Node ≥22.12, not `{ default: Kiss }`.
- `config.logger` is the one dependency-injection seam — pass `silentLogger` (from `lib/logger.js`) in tests to keep output quiet.
- Calling `complete()` from inside a `generate()` callback is safe, not a deadlock: `generate()` invokes the callback (through `_runCallback`, which calls it as `callback.call(this, data)`) and never awaits whatever the callback returns, so the `_generating` entry for that `generate()` run settles as soon as the callback returns (its return value or any promise it returns is not part of what `_drain()` waits on — which is also why `_runCallback` gives a returned promise its own `.catch` rather than pushing it onto `_generating`). `complete()`'s `_drain()` therefore still sees that run resolve and proceeds normally. It is safe on a _failing_ build too, which it was not before A-01: the report-once latch means only one of the two concurrent `complete()` calls rejects, so the one the consumer did not attach a handler to resolves instead of taking the process down. A real downstream site (diploma-msc's `generate.js`) relies on this pattern, calling `complete()` from within a `generate()` callback. Since A-03 the callback's own promise _is_ waited on — by `_drain()`, not by the `generate()` run — so the re-entrancy guard moved there: `complete()` reads `_drainDepth` **synchronously** on entry, and a call that finds it above zero (i.e. one made from inside a callback while another `complete()` is draining) drains `_promises`/`_generating` only, skipping `_callbacks`. Without that skip an `async` callback that awaits `this.complete()` would wait on a drain that is waiting on the callback. A **depth counter, not a flag**: each call increments on entry and decrements in a `finally`, so the answer does not depend on which of the two calls settles first. A flag saved and restored per call got this wrong whenever the nested call settled _last_ — it restored the value it had captured (`true`), leaving the instance permanently "draining", so every later `complete()`, including the one `_replay()` runs on each watch rebuild, silently skipped `_callbacks`. The guard covers the case that exists in practice — the outer `complete()` is what makes the callback run — and not the exotic one where a callback registered while nothing is draining awaits `complete()`: that call would wait on its own callback entry, so the pattern is "await `complete()` inside a callback of a build somebody is already awaiting".
- **`options.config` is a per-page shallow copy**, `{ ...this.config, ...callerConfig }` — not the live instance config, which every page used to alias (review finding A-05). A controller that mutated `options.config.siteUrl` therefore rewrote `kiss.config` itself, retroactively changed pages already prepared, changed every later page, and changed the `<loc>`s in `sitemap.xml`; the same line also silently overwrote a `config` the caller had passed in that page's options, which is now honoured as an override for that page. Shallow is enough: nested values (`folders`, `sass`) are shared by reference and nothing in the engine mutates them — a controller that reaches into `options.config.folders` still reaches the shared object. `_prepareMultiplePages` copies `config` a level deeper per fanned-out page for the same reason the whole options object is rebuilt there: one `page()` call's config object would otherwise alias across the entire fan-out. Everything else (`sitemap()`, `_preparePage`, the watcher) reads `this.config` and is untouched.
- `_registrations` is a log of every `.page()` call's options _as the caller passed them_ — a shallow copy taken at the top of `page()`, before `options.config` is attached and before model/controller auto-mapping mutates the object. `pages()` sets `options.dynamic = true` before delegating to `page()`, so fan-out registrations are captured with that flag and replay as fan-outs. Pages registered from inside a `generate()`/`complete()` callback are logged too, and replay from their snapshot — but they replay _once, up front_ with the rest, not at callback time, so a callback that registers pages derived from resolved model data replays with the options it produced on the first build, not recomputed ones. The snapshot is _shallow_: an object/array model or a function controller is shared by reference with the original options, so a controller that mutates `options.model` in place accumulates those mutations across rebuilds (each replay starts from the already-mutated object). Keep controllers idempotent — return new values rather than mutating what they were handed.
- `_replay()` starts by `await Promise.allSettled([...this._promises, ...this._generating])` — it must not reset those arrays while work is still running. A page chain still resolving (a slow URL model, an initial build that was never awaited) would otherwise land in the _new_ `_stack` and make the replay's own page lose the `buildTo` dedupe, leaving the previous build's output in place. `allSettled`, not `all`: a rejected in-flight promise must not abort the rebuild. Replays never overlap each other (the rebuild queue serialises them), so this only ever waits on non-replay work.
- **`scan()` dedupes against `_registrations`, not `_stack`.** `page()` records a registration synchronously but only _queues_ the page — `_preparePage` runs later, off the promise chain — so `_stack` is empty during a synchronous `.page(…).scan()` chain and again at the top of a replay. Scanning against it registered the same view twice, and the second copy was rejected by `_preparePage`'s `buildTo` dedupe with `Page already processed`. The registrations list is the one written synchronously, so it is the one that can answer "did someone already ask for this view".
- **`_replay()` re-runs `scan()` when `_scanRequested` is set**, so a page file created while watching joins the site instead of waiting for a restart. The order inside `_replay()` is load-bearing: drop vanished scanned registrations → re-scan → replay the rest. Dropping first is what stops a just-deleted view being re-added by its own stale registration. The re-scan runs while `_replaying` is still `false`, so `page()` records what it finds as a new scanned registration that every later replay replays like any other — but it also _queues_ those pages there and then, which is why the replay loop iterates a snapshot of `_registrations` taken before the re-scan. Replaying the post-scan list would queue each new page a second time and lose it to the `buildTo` dedupe.
- `_replay()` drops any `scan()`-created registration whose `.hbs` view no longer exists on disk (logged once as `Removed page: <view>`) before re-registering, so a deleted page file is not re-queued, its `buildTo` is absent from the new stack, and the orphan sweep below removes its output and the `.json` sibling. Only scanned registrations are dropped: `scan()` derives the page list _from_ the file tree, so the file going away is the caller's own instruction, whereas a page registered by name is not — a missing view there stays a build failure rather than a silent disappearance, which is what would hide a typo. Scan-created registrations are tracked in a `WeakSet` (`_scanned`) keyed by the registration object rather than by a key on it, because `_registrations` entries are spread straight back into `page()` on replay and any own key would reach the render context and the dev-mode `.json` sibling; `scan()` sets `_scanning` around its `page()` calls the same way `_replay()` sets `_replaying`.
- **The asset manifest is instance state that survives a replay.** `_assetManifest` (`AIKB/asset-manifest.md`) is created in the constructor, before the first `copyAssets()`, and handed to both that copy and `registerHandlebarsHelpers` — so the `asset` helper reads what the copy emitted. Ordering is already guaranteed by the queues rather than by anything new: the constructor's copy is the **first** promise on `_promises`, and `generate()`/`_settle()` await `_promises` before rendering a page, so no page can render against an empty manifest. `_replay()` resets `_assetQueue` and `_promises` but never re-copies assets and never clears the manifest, which is exactly right — the files are still in the build under the names the manifest holds.
- **A renamed asset is invisible to the orphan sweep, on purpose.** The sweep works from `_stack` `buildTo` paths (page outputs); assets have no stack entry. Stale hashed files are removed by `lib/assets.js` from the manifest's own record of the name it replaced, not here.
- **Under a hashing policy an asset edit re-renders the pages.** `watch()`'s `assetsChanged` normally just re-copies and names the built file for a live-reload stylesheet swap. With `config.assets.hash`, and only for a file the policy actually renames (`isHashable`, i.e. the built `.css`/`.js`), the copy has changed the filename, so every page is linking one that no longer exists: the handler instead asks the rebuild queue for a scoped re-render of `_stack` (the same scoped path an edited partial takes) and lets the queue's `.finally()` do the one reload, after every page has been rewritten. An edited image or `robots.txt` keeps its name, so it keeps the cheaper targeted reload. `_builtAssetPath` also resolves through the manifest, so the path it hands live reload is the file that is actually on disk.
- `_replay()` (watch rebuilds only) discards `_stack`, `_promises` and `_generating` (and `_failures`, and resets `_assetQueue`), re-registers partials, then re-runs `page()` for every entry in `_registrations` with `_replaying = true`, and finally `generate()` + `complete()`. Because the whole pipeline re-runs, models are re-read from disk (and URL models are _re-fetched_ — a watch rebuild costs a network round trip per remote model, unless `config.fetch.cache` is set to a directory, in which case the cached body is read instead and no request is made: see `AIKB/fetch-policy.md`) and controllers re-run; `_replaying` also propagates as `fresh` into `applyController`, which busts Node's module caches so an edited controller file reloads (see `AIKB/controller-resolver.md`). The build dir is _not_ cleaned by a replay (that would blow away assets and leave the site briefly empty for the dev server); instead the replay snapshots the previous stack's `buildTo` paths up front and, in a `finally` around `complete()`, removes any that the new stack no longer contains — plus the same-named `.json` dev debug sibling. So a page whose slug changed, or one that vanished from a shrinking `.pages()` fan-out, no longer leaves stale output behind. The removal runs in a `finally` so a failed rebuild still cleans up — but only one that failed **after** it re-queued the site. The `try` now opens right after `previous` is captured and wraps the whole re-registration half (`registerPartials()`, the drop-vanished-registrations filter, the re-scan, the `page()` loop) as well as `complete()`, and a `requeued` flag flips once the `page()` loop has run. Two reasons. (1) A throw in that half used to skip the `finally` altogether, so `previous` was lost and every stale output stayed on disk for the life of the process — no later replay could see it, because each one snapshots `previous` from a `_stack` that no longer mentions those files, and in dev mode the server went on serving a page that had been deleted. (2) Simply widening the `try` is not enough on its own: with `requeued` still false the new stack is empty because the replay _failed_, not because the site shrank, so an unguarded sweep would delete the entire build. So a replay that throws before re-queuing sweeps nothing and parks `previous` on `_unswept`, which the next replay folds back into its own `previous` (deduped) and sweeps then; the last good build stays on disk in the meantime and the failure is reported as `Error rebuilding site` as before. Once the pages are re-queued the old contract holds unchanged: every page that should exist has a `buildTo` in the stack (`_preparePage` runs before the render), so `previous` minus the stack is genuinely stale even when the rebuild then fails while rendering. **The sweep is only atomic at the rebuild's edge, not per page**: it removes the output and then its `.json` sibling one `await` later, and works through `previous` one entry at a time, so between those awaits the build dir is legitimately half-swept. The completion signal is the rebuild queue settling (`_rebuildInFlight`), never an individual file disappearing — anything that reacts to one removal and then reads another (a test, a deploy step) is reading a state the engine never promised. That is what made `test/integration/watch.test.js`'s deleted-scanned-view test load-sensitive: it waited on `gone.html` and then asserted on `gone.json`.
- A replay re-runs `sitemap()` when one was ever requested: `sitemap()` records `_sitemapRequest = { options, callback }` (idempotent — the replay's own call re-records the same request), and `_replay()` re-issues it right after `generate()` so `complete()` drains it and `sitemap.xml` matches the new stack. v1 (and v2 before this) left `sitemap.xml` stale after a slug change in watch mode. Like the `generate` callback, the `sitemap` callback re-fires on every watch rebuild — once per replay, with that rebuild's `urls`, not just on the original call.
- `_replaying` is read _synchronously_ at the top of `page()` — both to skip re-logging the registration and to capture `fresh` for the async chain that runs later. That is why `_replay()` can reset the flag in a `finally` immediately after the registration loop, even though the chains it started are still pending.
- `_promises` and `_generating` are push-only _within a build_ — never spliced, only reassigned wholesale by `_replay()`. So repeated `complete()` calls inside one build re-await every promise ever queued (all already settled, so cheap), and a long-running `watch()` session no longer grows them without bound: each rebuild starts from empty arrays.
- `_drain()` waits on `_promises`, `_generating` **and `_callbacks`** — the promises `_runCallback` collected from `async` callbacks — re-checking the combined length between rounds. Tracking the callback itself is what makes work queued after an `await` inside it part of the build (review finding A-03): before that, the `while` loop only saw array-length growth that had already happened, so `complete()` resolved while an awaiting callback had not yet queued its pages. What still escapes it is work deferred by a callback that returns nothing to track — a `setTimeout`-ed `.page()` from a _synchronous_ callback queues on a later macrotask with no promise the engine can see.
- **`complete()` renders what the drain leaves unrendered.** `_settle()` alternates `_drain()` and `_generatePending()` — which renders every stack entry still at `runCount === 0`, incrementing the count as it picks each one so a concurrent pass cannot render it twice — and loops until a drain leaves nothing pending. A page prepared after the last `generate()` pass iterated the stack (a `scan()` from a `generate` callback, as `examples/3-pages.js` does; or a page queued after `generate()` whose model resolved after that run's `Promise.all` snapshot) used to be silently dropped from a build that then reported success — an outcome decided by model latency (review finding A-02). The implicit pass is gated on `_generateRequested`: `complete()` finishes a render pass the caller asked for, it never starts one that was not, so `.page(…).complete()` with no `generate()` still writes nothing. `_generatePending()`'s run is pushed onto `_generating` so a concurrent `complete()` and a later replay wait for it, and its per-page failures are collected on `_failures` exactly as `generate()`'s are. It fires no callback — `generate()`'s callback belongs to `generate()`.
- The `modelId` used in `.page()`'s `.catch()` failure entry is captured _before_ the `.then()` chain runs, because `options.model` is reassigned to the resolved data inside `.then()` — reading `options.model` inside `.catch()` for a post-resolution failure would report the data, not the original id.
- **Two pages claiming one `buildTo` is a build failure** (`_preparePage`): the second is still not stacked, but alongside the `Page already processed` log it now pushes `{ view, buildTo, error }` onto `_failures`, so `complete()` rejects. It used to log and return `null`, which meant a page the caller asked for was simply missing from a build that reported success — the same silent-success class as a dropped render (review finding C6). The dedupe applies to `.pages()` fan-out too, since each fanned-out page goes through `_preparePage` individually (v1 never deduped fan-out output); a fan-out whose controller derives the slug from model data is exactly where a collision now surfaces instead of hiding. The rebuild paths do not hit it: `scan()` dedupes against `_registrations` and `_replay()` replays a snapshot taken before its re-scan, both so the same view is never queued twice.
- **The `slug` and `path` fallbacks in `page()` both guard on `.endsWith('.hbs')`.** Only a `.hbs` view is a filename: its folder is the page's path and its basename the slug. An inline template string gets a random `snippet-N` slug (with a logged error) and an _empty_ path — deriving one from the view would cut at the last `/` in the template's own markup, so `'<p>x</p>'` built into `public/-p-x-/…` and any closing tag became an output folder, with the sitemap inheriting the wrong `loc` (review finding C5). The `path` guard was missing while the `slug` one ten lines above was not.
- `_prepareMultiplePages` builds a **fresh options object per fanned-out page** (`{ ...options, slug, model }`), and must keep doing so. It previously mutated and reused one object across the loop, which `_preparePage` then stored on each `KissPage` by reference (`kissPage.options = options`) — so every page in the fan-out aliased the same options. The visible symptom was `applyController`'s "title from `model.title`, unless already set" mapping: item one filled the title and the guard skipped the rest, so all pages rendered the first item's title. `{{model.x}}` stayed correct throughout, which is why the characterization tests missed it — they only ever asserted on `model`, never on an option derived from it.
- **A bad item in a `.pages()` fan-out fails that item only** (`_prepareMultiplePages`): the per-item `applyController` + `_preparePage` step runs inside its own `try`, so a controller that throws for one item is recorded as `{ view: '<view> [item N: <slug>]', buildTo: null, error }` and the loop moves on to the next item. It used to let the throw unwind the whole loop into `page()`'s `try`, which recorded one `{ view, buildTo: null }` entry and abandoned every later item — unregistered, unrendered and unreported, so one failure entry stood for the entire tail of the fan-out (review finding F-E1; diploma-msc fans 64 catalogue pages from one call). N bad items now report N failures and the good items still build. The label is the only handle the operator has on _which_ record was malformed: there is no `buildTo` yet, and every item in a fan-out shares one `view`, so the position is always included and the item's own `slug` too when the model carries one. Because nothing escapes the loop, `page()`'s catch never records a second entry for the same item — that double-record is what a `throw` after the per-item catch would reintroduce.
- `viewStats()`'s `debug.json` serialises a _projection_ of `_stack` (`{ view, buildTo, runCount, options }`), never the entries themselves: a stack entry's `page` holds the Handlebars environment (internally cyclic) and the logger, so `JSON.stringify` on the raw stack throws "Converting circular structure to JSON" and the file silently never gets written. The write is not awaited — `test/integration/view-stats.test.js` polls for the file with `waitFor`.
- Watcher rebuilds are fire-and-forget from the watcher's point of view — nothing awaits what `_handleChange` returns — but they are still _tracked_: `_rebuild(entries)` pushes each `page.generate().catch(() => {})` onto `_generating` (caught there because `KissPage.generate()` now rethrows, and it has already logged; a scoped rebuild must not turn into an unhandled rejection or a `complete()` failure), so a replay's `allSettled` waits for it and `complete()` drains it. `_generating` accumulates one entry per re-rendered page until the next replay resets the array.
- **All rebuild work goes through one serial queue** (`_runRebuildQueue()`): one in-flight slot and one pending slot, where the pending slot is a set of scoped targets (stack entries to re-render) plus a "replay" bit. `_requestReplay()` sets the bit and clears the set — a replay rebuilds everything, so it supersedes every scoped rebuild — and returns the in-flight promise, so N rapid watcher events (save-all, a formatter, a branch switch) produce at most one in-flight run plus one follow-up and the last replay reads the newest files. `_requestRebuild(entries)` adds to the set, or is a no-op while the bit is set. Two rebuilds must never overlap, for two distinct reasons: `_replay()` resets `_stack` synchronously, so two replays interleaved would let the older one's still-pending chains fill the new stack and the newer pages — the ones carrying the newest edit — would be rejected by `_preparePage`'s `buildTo` dedupe with a `Page already processed` error, leaving stale output; and scoped work in flight when a replay starts re-renders from a stack the replay is about to discard. Two scoped rebuilds racing each other are the same hazard in miniature, which is why the queue covers both kinds rather than only replays. The follow-up run is _not_ chained into the returned promise (the `.finally()` callback returns `undefined`), so awaiting `_requestReplay()` waits only for the run that was in flight. Errors from either kind of run are caught and logged as `Error rebuilding site`.
- **Live reload is issued from here, once per settled build**, because nothing watches the build folder any more (review finding F-E4 — see `AIKB/dev-server.md` for what was removed and why). `_reload(changed = '/')` is the single call site of the dev server's `refresh`; it is a no-op when there is no dev server, and it swallows anything the call throws, because a live-reload socket that has gone away must never fail the rebuild that triggered it. There are exactly three places it fires:

  | When                                                               | Where                                                   | Path sent                  |
  | ------------------------------------------------------------------ | ------------------------------------------------------- | -------------------------- |
  | the first build settles                                            | the constructor's dev block, after `_settle()`          | `'/'` (reload the page)    |
  | a rebuild settles — replay or scoped, one reload for the whole run | `_runRebuildQueue()`'s `.finally()`                     | `'/'`                      |
  | an assets copy the watcher asked for finishes                      | `watch()`'s `assetsChanged`, chained onto `_assetQueue` | `_builtAssetPath(changed)` |

  The rebuild reload sits in the queue's `.finally()`, which is **after** a replay's orphan sweep, so the browser can never fetch a page that is still being written or one the sweep is about to remove. The initial one exists because a browser left open across a restart would otherwise sit on the previous build's output until the next edit. `_builtAssetPath(changed)` maps an edited asset to where it lands in the build folder (with `.scss`/`.sass` → `.css`, since that is what sass wrote): naming the built file is what lets livereload swap a stylesheet in place instead of reloading the page, which is why the assets watcher forwards the changed path at all. It returns `'/'` when there is no assets or build folder — nothing was copied, so there is nothing to name.

- **The watch dispatch lives here, not in the watcher** (`_handleChange(event, path)`), because deciding needs the stack, the partials registration and the rebuild queue — all of which are `Kiss` state. The watcher forwards every event under `src` and this is the whole table:

  | Event                                                     | Action                                           |
  | --------------------------------------------------------- | ------------------------------------------------ |
  | `add` / `addDir` (after the watcher's own `ready`)        | `_requestReplay()`                               |
  | `unlink` under `folders.pages`                            | `_requestReplay()`                               |
  | `change` under `folders.partials` / `folders.layouts`     | `registerPartials()` + `_requestRebuild(_stack)` |
  | `change` of a page view matching stack entries            | `_requestRebuild(matches)`                       |
  | anything else (model, controller, unknown file, no match) | `_requestReplay()`                               |

  A replay is the default and the fallback: only the two scoped rows are narrower than one, and each is provably so.

- **The partial/layout fast path is safe without a dependency graph.** An edited partial or layout cannot change `_registrations`, `_stack`, any page's resolved options, its `buildTo`, or the sitemap — the only thing a replay would do differently is _which_ pages it re-renders, and this re-renders all of them. So the stack is unchanged by construction, orphan cleanup, the `buildTo` dedupe and `_failures` are untouched, and what is skipped is exactly the expensive half of a replay: every model re-read from disk, every controller re-imported with a cache bust, every URL model re-fetched over the network (or read from `config.fetch.cache`). That is why the path re-renders the whole stack rather than trying to work out who used the partial — knowing that would need a traced graph, and would only ever save render time on top of this (`planning/specs/2026-09-05-watch-dependency-graph-design.md`, steps 2 and 3). `test/integration/replay-equivalence.test.js` is the standing proof: the same edit sequence applied through the real dispatch and through forced replays must leave byte-identical build directories.
- **A partial edit arriving while a rebuild is in flight is upgraded to a replay** (the `_rebuildInFlight` check inside the fast-path branch of `_handleChange`). Whether the run already in flight read the file before or after the edit landed is a race nobody can reason about — the render is synchronous but the registration that fed it may not be — so the pessimistic answer is the only one that can be justified. It costs one full rebuild in the rare overlapping-save case and removes a class of "the dev server is showing the old partial" bug.
- **`_rebuild(entries)` skips any target `_stack` no longer holds.** A scoped target queued before a replay names a page from the stack that replay discarded; re-rendering it would write from options nothing holds any more, and its `buildTo` may since have been swept as an orphan. The skip is silent — it is the expected outcome of "a replay supersedes scoped work", not a fault.
- `close()` quiesces before tearing down (review finding B6): it sets `_closing` — honoured at the top of the queue, so no new run starts — closes the watchers first so no new requests arrive, then awaits the in-flight slot _in a loop_ (the pending slot can start one more run before the flag is seen), and only then closes the dev server. Without it a rebuild requested just before `close()` kept running and writing, so a caller's clean-or-deploy step raced a build it believed had stopped — in the repro the orphaned replay recreated the build directory after it was removed. `_closing` is never cleared: a closed instance stays closed, so calling `watch()` again on one would watch without ever rebuilding.

## Types

`kiss-ssg` ships TypeScript declarations without being TypeScript. The public API's JSDoc lives beside the runtime it describes — the page/build typedefs at the top of this module, the config ones in `lib/config.js` — and `npm run types` generates `types/*.d.ts` from it. `package.json` points `types` and its `exports` map at `types/kiss.d.ts`, and `files` ships the folder, so a consumer gets full completion from plain JavaScript with `// @ts-check` and no TypeScript of their own.

- **The typedefs declared here**: `PageOptionsKnown` (the documented page options) and `PageOptions` (those plus arbitrary extra keys, which render as top-level context); `PagesOptions`; `PageOptionsPatch` and the `KissController` callback that returns one; `BuildDatum`/`BuildData` (what `generate()`/`complete()` resolve with), `BuildFailure`, and `BuildError` — the `AggregateError & { failures }` `complete()` rejects with; `SitemapUrl`, `SitemapOptions`, `WatchOptions`. `KissConfig`, `KissConfigInput` and `KissFolders` are re-exported from `lib/config.js` with `@typedef {import('./config.js').X} X`, so a consumer reaches every one of them as `import('kiss-ssg').X` from a single entry.
- **Every `_`-prefixed field and method is marked `@private`**, so the emitted class declaration carries them as `private _stack;` rather than as documented API. The public surface of `types/kiss.d.ts` is exactly the API llms.txt describes.
- **`npm run types` is `node scripts/emit-types.mjs`, not a bare `tsc`, because of one TypeScript bug.** The declaration emitter drops the quotes from an arbitrary module namespace name when it reads it out of a `.js` file (from a `.ts` source they survive), so `export { Kiss as 'module.exports' }` — the line that makes `require('kiss-ssg')` return the class on Node ≥22.12 — comes out as `export { Kiss as module.exports }`, which is a **syntax error**: the whole declaration fails to parse, and every consumer silently falls back to `any`. The script runs `tsc -p tsconfig.types.json` and then puts the quotes back (`quoteStringExportNames`). Re-check this whenever TypeScript is upgraded; the fixup is a regex over the emitted text and `test/unit/types.test.js` asserts the line survives.
- **`types/` is checked in and must not be hand-edited.** `test/unit/types.test.js` re-emits into a temp folder and byte-compares every file, so a JSDoc edit without a regeneration fails the suite naming the file and the command. `types/` is in `.prettierignore` — tsc owns its formatting, and the comparison is against exactly what tsc wrote.
- **What the types are checked against is a consumer, not an assertion.** `test/fixtures/consumer/site.js` is a plain-JS site with `// @ts-check` that builds a config, queues pages with a typed controller and reads `err.failures`; it must type-check clean. `bad.js` beside it must produce exactly three errors — a wrong `cleanBuild` type, a misspelled key inside `folders`, and a method that does not exist — which is what pins the deliberate asymmetry between the config's index signature and `folders`' closed one.
- **Two honest `any`s remain.** `kiss.remarkable` is `any` because `remarkable` ships no types and a structural stand-in would refuse the plugin API; `options.model` is `any` because a model is the site's own data, of a shape the engine never knows.
