# kiss.js

## Responsibility

The orchestrator and public API. `Kiss` owns config, a per-instance Handlebars environment and Remarkable renderer, the `_stack` of prepared pages, the `_registrations` log of pages as the caller asked for them, and the `_promises`/`_generating` queues that track every piece of async work (model resolution, asset copying, generate/sitemap runs). Every other `lib/*.js` module is wired together and driven from here.

## Public interface

- `class Kiss` (default export), also re-exported as `export { Kiss as 'module.exports' }` so `require('kiss-ssg')` on Node ≥22.12 returns the class, not `{ default: Kiss }`.
- `new Kiss(config)` — resolves config, sets up Handlebars/Remarkable, ensures folders, queues an asset copy, registers helpers and partials, and (in dev mode) starts the dev server and watcher.
- `.copyAssets(sourceDir, targetDir)` — queues `copyAssets()` onto `_promises`; returns `this`.
- `.registerPartials()` — re-runs `registerPartials()` against the current Handlebars env; returns its result.
- `.page(options, callback)` — resolves the page's model, runs its controller, prepares a `KissPage`, pushes it onto `_stack`; returns `this`.
- `.pages(options, callback)` — same as `.page()` with `options.dynamic = true` (one page per model in an array); returns `this`.
- `.scan()` — globs every `.hbs` under `config.folders.pages` and calls `.page()` for any not already in `_stack`; returns `this`.
- `.viewStats()` — logs `{ promise, stack }` counts (and, if `verbose`, writes `debug.json` to the build folder); returns `this`.
- `.generate(callback)` — awaits `_promises`, renders every stack entry with `runCount === 0` once (each render caught, failures collected on `_failures`), awaits the writes, invokes `callback`; returns `this`.
- `.complete(callback)` — awaits `_drain()` (repeated `Promise.all` over `_promises` + `_generating`), then **rejects with an `AggregateError`** if `_failures` is non-empty; otherwise invokes `callback` with the resolved data and returns that data (a `Promise`, unlike the other chainable methods).
- `.sitemap(options, callback)` — records the request on `_sitemapRequest` (so watch rebuilds re-run it), awaits `_promises`, writes `sitemap.xml` via `writeSitemap()`; returns `this`.
- `.getModelByID(id, data)` — looks up `{ id }` in a resolved-models array; returns `.data` or an error object.
- `.watch({ entry = process.argv[1] } = {})` — starts (once) a `createWatcher()` wired to rebuild pages/site/assets; a site rebuild goes through `_requestReplay()`/`_replay()` (below), a page rebuild is a plain re-render; returns `this`.
- `.close()` — closes the watcher and dev server if running.
- `export { utils }` — re-exports `lib/utils.js`'s default export.

## Depends on

`fs-extra`, `glob`, `node:path`, `handlebars`, `handlebars-layouts`, `remarkable`; and `./utils.js`, `./logger.js`, `./config.js`, `./handlebars-helpers.js`, `./partials.js`, `./assets.js`, `./model-resolver.js`, `./controller-resolver.js`, `./sitemap.js`, `./kiss-page.js`, `./dev-server.js`, `./watcher.js`.

## Depended on by

Nothing in `lib/` — it is the entry point (`package.json`'s `main`).

## Non-obvious behavior

- Pipeline: `.page()`/`.pages()`/`.scan()` queue work (model → controller → `_preparePage`) as one caught promise per page on `_promises`; nothing renders until `.generate()`. `.generate()` awaits `_promises`, renders every stack entry whose `runCount` is 0, awaits the writes, then fires the callback. `_generating` tracks `generate()`/`sitemap()` runs. `complete()` drains both lists repeatedly because callbacks may queue more work.
- Build failures are collected, not thrown at the page: `KissPage.generate()` rethrows a render/minify/write error, `generate()` catches it per page into `_failures` (`{ view, buildTo, error }`) so the remaining pages still build, and `complete()` rejects once with an `AggregateError` (`err.failures` = that array, message `"N page(s) failed to build: <views>"`). `generate()`'s own callback still fires either way — callbacks are not the error channel; `complete()` is. `complete()` does not invoke its callback on failure (same rule as `sitemap()`'s callback), and re-rejects on every subsequent call in the same build because `_failures` is only reset by `_replay()`.
- Model and controller failures are *not* build failures: they keep the documented log-and-skip behaviour and appear in `complete()`'s resolved data as `{ id, data: null, error }`. The page is simply never prepared, so there is nothing to render and nothing lands in `_failures`.
- `_promises` must only ever contain *handled* (caught) promises — a bad model rejecting unhandled crashed the process in v1. The `.page()` chain's `.catch()` always resolves to `{ id, data: null, error }` instead of rejecting.
- Handlebars and Remarkable are created fresh per `Kiss` instance so partials/helpers from one instance never leak into another (matters for tests that build multiple sites in one process).
- `export { Kiss as 'module.exports' }` exists purely so CJS `require('kiss-ssg')` returns the class itself on Node ≥22.12, not `{ default: Kiss }`.
- `config.logger` is the one dependency-injection seam — pass `silentLogger` (from `lib/logger.js`) in tests to keep output quiet.
- Calling `complete()` from inside a `generate()` callback would deadlock: the callback runs inside a promise pushed onto `_generating`, and `complete()`'s `_drain()` awaits `_generating` before resolving — so `complete()` would be waiting on a promise that can't settle until the callback (which called `complete()`) returns. Never call `complete()` from inside a `generate()`/`sitemap()` callback.
- `_registrations` is a log of every `.page()` call's options *as the caller passed them* — a shallow copy taken at the top of `page()`, before `options.config` is attached and before model/controller auto-mapping mutates the object. `pages()` sets `options.dynamic = true` before delegating to `page()`, so fan-out registrations are captured with that flag and replay as fan-outs. Pages registered from inside a `generate()`/`complete()` callback are logged too, and replay from their snapshot — but they replay *once, up front* with the rest, not at callback time, so a callback that registers pages derived from resolved model data replays with the options it produced on the first build, not recomputed ones. The snapshot is *shallow*: an object/array model or a function controller is shared by reference with the original options, so a controller that mutates `options.model` in place accumulates those mutations across rebuilds (each replay starts from the already-mutated object). Keep controllers idempotent — return new values rather than mutating what they were handed.
- `_replay()` starts by `await Promise.allSettled([...this._promises, ...this._generating])` — it must not reset those arrays while work is still running. A page chain still resolving (a slow URL model, an initial build that was never awaited) would otherwise land in the *new* `_stack` and make the replay's own page lose the `buildTo` dedupe, leaving the previous build's output in place. `allSettled`, not `all`: a rejected in-flight promise must not abort the rebuild. Replays never overlap each other (`_requestReplay()` serialises them), so this only ever waits on non-replay work.
- `_replay()` (watch rebuilds only) discards `_stack`, `_promises` and `_generating` (and `_failures`), re-registers partials, then re-runs `page()` for every entry in `_registrations` with `_replaying = true`, and finally `generate()` + `complete()`. Because the whole pipeline re-runs, models are re-read from disk (and URL models are *re-fetched* — a watch rebuild costs a network round trip per remote model) and controllers re-run; `_replaying` also propagates as `fresh` into `applyController`, which busts Node's module caches so an edited controller file reloads (see `AIKB/controller-resolver.md`). The build dir is *not* cleaned by a replay (that would blow away assets and leave the site briefly empty for the dev server); instead the replay snapshots the previous stack's `buildTo` paths up front and, in a `finally` around `complete()`, removes any that the new stack no longer contains — plus the same-named `.json` dev debug sibling. So a page whose slug changed, or one that vanished from a shrinking `.pages()` fan-out, no longer leaves stale output behind. The removal runs in a `finally` so a failed rebuild still cleans up.
- A replay re-runs `sitemap()` when one was ever requested: `sitemap()` records `_sitemapRequest = { options, callback }` (idempotent — the replay's own call re-records the same request), and `_replay()` re-issues it right after `generate()` so `complete()` drains it and `sitemap.xml` matches the new stack. v1 (and v2 before this) left `sitemap.xml` stale after a slug change in watch mode.
- `_replaying` is read *synchronously* at the top of `page()` — both to skip re-logging the registration and to capture `fresh` for the async chain that runs later. That is why `_replay()` can reset the flag in a `finally` immediately after the registration loop, even though the chains it started are still pending.
- `_promises` and `_generating` are push-only *within a build* — never spliced, only reassigned wholesale by `_replay()`. So repeated `complete()` calls inside one build re-await every promise ever queued (all already settled, so cheap), and a long-running `watch()` session no longer grows them without bound: each rebuild starts from empty arrays.
- `_drain()` only catches work queued *synchronously* by a settled callback's continuation — a `setTimeout`-deferred `.page()` call (or anything else that queues work on a later tick) escapes it, because the `while` loop's re-check only sees array-length growth that happened before its next `Promise.all` starts.
- The `modelId` used in `.page()`'s `.catch()` failure entry is captured *before* the `.then()` chain runs, because `options.model` is reassigned to the resolved data inside `.then()` — reading `options.model` inside `.catch()` for a post-resolution failure would report the data, not the original id.
- Dedupe by `buildTo` (in `_preparePage`) also applies to `.pages()` fan-out, since each fanned-out page still goes through `_preparePage` individually — v1 never deduped fan-out output.
- `viewStats()`'s `debug.json` serialises a *projection* of `_stack` (`{ view, buildTo, runCount, options }`), never the entries themselves: a stack entry's `page` holds the Handlebars environment (internally cyclic) and the logger, so `JSON.stringify` on the raw stack throws "Converting circular structure to JSON" and the file silently never gets written. The write is not awaited — `test/integration/view-stats.test.js` polls for the file with `waitFor`.
- Watcher rebuilds are fire-and-forget from the watcher's point of view — neither callback is awaited — but they are still *tracked*: `rebuildPage` pushes `page.generate().catch(() => {})` onto `_generating` (caught there because `KissPage.generate()` now rethrows, and it has already logged; a single-page rebuild must not turn into an unhandled rejection or a `complete()` failure), so a replay's `allSettled` waits for it and `complete()` drains it. `_generating` accumulates one entry per single-page rebuild until the next replay resets the array. `rebuildSite` calls `_requestReplay()` without awaiting it.
- Replays never overlap: `_requestReplay()` serialises them with a trailing-edge collapse — a request made while `_replayInFlight` is set only sets `_replayQueued` (and returns the in-flight promise), and exactly one follow-up replay runs from the `.finally()` when the current one settles. So N rapid watcher events (save-all, a formatter, a branch switch) produce at most one in-flight replay plus one follow-up, and the last replay reads the newest files. This matters because `_replay()` resets `_stack` synchronously: two overlapping replays would let the older one's still-pending chains fill the new stack first, and the newer pages — the ones carrying the newest edit — would then be rejected by `_preparePage`'s `buildTo` dedupe with a `Page already processed` error, leaving stale output. The queued follow-up is *not* chained into the returned promise (the `.finally()` callback doesn't return it), so awaiting `_requestReplay()` waits only for the replay that was in flight.
