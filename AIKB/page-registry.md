# page-registry.js

## Responsibility

Pages from registration to the stack, and their identity. A `.page()` / `.pages()` / `.scan()`
registration is logged for replay, given a per-page config, resolved to its model, run through its
controller and prepared as a `KissPage` on `_stack` — one caught promise per page on `_promises`.
And identity: the id a page claims or is given, the index `{{link}}` resolves ids against, and
the stack as the build record describes it. Nothing here renders; `generate()` does that.

Every function takes the `Kiss` instance and reads its state at call time. The state stays on
`Kiss` — `_stack`, `_registrations`, `_registrationDirectories`, `_scanned`, `_idIndex`,
`_idNoticed`, `_promises`, `_failures` — and each private method on `Kiss` (`_preparePage`,
`_idIndexFor`, `_lookupPage`, `_stackForRecord`, `_prepareMultiplePages`, `_page`) is a one-line
delegator to the function here. The public `.page()`, `.pages()`, `.scan()` and `.viewStats()`
stay on `Kiss` with their documentation and their `return this`; `scan()` and `viewStats()`
delegate their bodies (`scanPages`, `logViewStats`). Calls between these functions go back
through the instance (`kiss._preparePage(…)`, `kiss._idIndexFor()`, `kiss.page(…)`), so a test
that patches one on the instance is seen.

## Public interface

- `registerPage(kiss, options, directory)` — `_page()`: logs the registration (unless replaying),
  auto-maps the model and controller, and queues the model → controller → prepare chain.
- `prepareMultiplePages(kiss, options, data, fresh, origin, directory)` — the `.pages()` fan-out.
- `preparePage(kiss, options, origin, idPrefix, directory)` → the stack entry, or `null` when the
  page failed (a duplicate output path, a duplicate explicit id, an invalid `canonical`).
- `idIndexFor(kiss)` → `{ byId, withdrawn }`, memoised on `_idIndex`. `lookupPage(kiss, id)` —
  what `{{link}}` asks, through the constructor's `lookupPage: (id) => this._lookupPage(id)`
  closure. `stackForRecord(kiss)` — the stack with withdrawn default ids nulled.
- `scanPages(kiss)`, `logViewStats(kiss)` — the bodies of `scan()` and `viewStats()`.
- `defaultIdForView(view)`, `explicitIdOf(options)` — pure.

## Depends on

`fs-extra` (`existsSync`, `outputJson`), `node:path`, `./utils.js`, `./kiss-page.js`
(`KissPage`), `./model-resolver.js`, `./controller-resolver.js`, `./aikb.js` (`pageOrigin`); the

## Non-obvious behavior

- `_preparePage` sets `KissPage.markdownCopy` from **the page's** `config.markdownCopies` too, through `resolveMarkdownCopies` (`lib/config.js`), falling back to the instance's: the page's value arrives as the page wrote it (`config: { markdownCopies: false }`), so it is resolved rather than trusted, and a malformed one throws at registration. `{ selector }` when copies are on, `null` when off.
- `_preparePage` takes `extLess` from **the page's** resolved config (`options.config?.extensionLess`), not the instance's, falling back to the instance when a page has none. `page()` merges the global config with the page's overrides before the page is prepared, so this is the resolved value for that page. It matters because a site that is `extensionLess` everywhere still owes its host one literal `404.html` — Netlify and Cloudflare Pages look for that exact filename and do not fall back to `404/index.html`. Before this, an `options.config` override naming `extensionLess` was accepted and silently ignored, which is the worst shape of bug: the config is documented as per-page, the page took it, and the output path came out the other way. Covered by `test/integration/canonical.test.js` § per-page extensionLess.
- **A `generate: false` page claims no output path.** `_preparePage`'s `buildTo` dedupe only counts entries that will be written, on both sides — a skipped page neither fails a real page registered after it nor fails itself when one came first — and the replay sweep's `current` set excludes them, so a page that turns `generate: false` between builds has its stale output removed. It still sits on `_stack` (so `.scan()`'s by-view dedupe and the `complete()` data array are unchanged) and is skipped by the sitemap.
- **A page's identity is computed in `_preparePage`, after `prepare()`, and nowhere else.** `id` is what `{{link "<id>"}}` resolves, and the default has two halves that are known at two different times: the view route is known synchronously at `page()` entry, but the page's **normalised** slug only exists once `KissPage`'s setter has run it through `toSlug` — `options.slug` is still raw (`'Hello World'`, or the `${base}-${i}` a fan-out seeds). `_preparePage` after `prepare()` and before the push is the one point where both are in hand, which is also why the `{{link "blog/post" slug=…}}` sugar slugs its argument: both sides of that comparison go through `toSlug` exactly once. The rules: a `.page()`/`.scan()` page defaults to the view's route without its extension (`blog/listing.hbs` → `blog/listing`, leading `./` or `/` stripped); a `.pages()` item defaults to `<prefix>/<normalised slug>`, where the prefix is the registration's own `id` if it has one and the view route otherwise — which is how two fan-outs of one view into different folders get distinct ids; an inline template (a view that is not a `.hbs` filename) gets none, because it has no route; and a `generate: false` page claims none either, on the same reasoning as the output-path exemption above — it cannot be linked, so it must not take an id off a page that can.
- **A registration's `id` is a prefix, a record's `id` is a claim — the `aliases` rule, one level over.** `_prepareMultiplePages` does `delete item.id` beside `delete item.aliases` and then promotes the record's own (`model.id`) onto the item, where `slug`, `model` and `aliases` are promoted. Broadcast instead, the registration's id would be claimed by item 1 and fail the build on item 2. Only a **non-empty string** is promoted: a record whose `id` field is a database integer is data about the record, not a claim on a page's identity, and `explicitIdOf()` applies the same test everywhere so "explicit" means one thing. A controller-returned `id` is explicit too — it is just `options.id` by the time `_preparePage` sees it.
- **Two explicit ids collide like two output paths; two default ids withdraw instead.** An explicit id already claimed by another entry is logged as `Page id already claimed: <id>`, recorded on `_failures` and the page is not pushed — the exact treatment `Page already processed` gives a duplicate `buildTo`, because two pages claiming one identity means a `{{link}}` to it could only ever have meant one of them. A **default** id two pages arrived at must not fail: one view rendered by two `.page()` calls is how pagination is written today, and every site that builds must keep building. So neither page keeps it, one `notice` names both views and asks for an explicit id, and a `{{link}}` to it fails the page that asked. Explicit beats default: the explicit page keeps the id, the default withdraws with a notice naming both — deterministic, and fixable by naming one page.
- **The id index is lazy, memoised against the live stack, and never a snapshot.** `_idIndexFor()` builds `{ byId, withdrawn }` from `_stack` on demand; `_preparePage` sets `_idIndex = null` after every push, and `_replay()` resets it (and `_idNoticed`) beside `_report`. Two things make that necessary rather than tidy. Pages are pushed one at a time and can be registered after a render pass has begun, so an id stamped onto an entry at push time would let the first page keep an id the second is about to collide with — and any page rendered in between would have linked it successfully. And `_replay()` replaces `_stack` with a **new array**, so anything holding the old one (or an index built at helper-registration time, which happens once per instance in the constructor and is never re-run) would serve the first build's registry for the life of the watch session. The helper therefore gets `lookupPage: (id) => this._lookupPage(id)` — a bound function, resolved per call. `_idNoticed` keeps a collision notice to one line per id per build, because the index is rebuilt on every registration.
- **A withdrawn default id is `null` on the record, not the string.** `_stackForRecord()` projects the stack before `buildReport` and `buildSiteMap` see it, nulling the id of any non-explicit entry whose id was withdrawn. `site-map.json`'s rows are read as the `{{link}}` autocomplete, so an id on the map must be one the helper will resolve; the alternative — reporting an id two pages share — would also hand `lib/redirects.js`'s id pairing an ambiguous key. The projection is a shallow copy per affected entry, so the live stack keeps its ids and a later registration can still change the answer.
- **`_preparePage` validates a page's `canonical` option, once, for its four readers.** `canonical: '<absolute http(s) URL>'` on a page is rendered verbatim by the `canonical` helper and withdraws the page from `sitemap.xml`, `llms.txt` and the feed (`AIKB/handlebars-helpers.md`, `AIKB/sitemap.md`, `AIKB/llms.md`, `AIKB/feed.md`), and the report carries it per page. A value that is not an absolute URL fails the page here — a build failure naming the page and the value — rather than at render, because a page whose template never renders `{{canonical}}` would otherwise be silently withdrawn from three files on the strength of a typo. Measured need: learna-kiss's 104 course pages whose canonical is the same course on diploma-msc.com, which kept it on a hand-rolled helper through 2.5.0.
- **`options.config` is a per-page shallow copy**, `{ ...this.config, ...callerConfig }` — not the live instance config, which every page used to alias (review finding A-05). A controller that mutated `options.config.siteUrl` therefore rewrote `kiss.config` itself, retroactively changed pages already prepared, changed every later page, and changed the `<loc>`s in `sitemap.xml`; the same line also silently overwrote a `config` the caller had passed in that page's options, which is now honoured as an override for that page. Shallow is enough: nested values (`folders`, `sass`) are shared by reference and nothing in the engine mutates them — a controller that reaches into `options.config.folders` still reaches the shared object. `_prepareMultiplePages` copies `config` a level deeper per fanned-out page for the same reason the whole options object is rebuilt there: one `page()` call's config object would otherwise alias across the entire fan-out. Everything else (`sitemap()`, `_preparePage`, the watcher) reads `this.config` and is untouched.
- `_registrations` is a log of every `.page()` call's options _as the caller passed them_ — a shallow copy taken at the top of `page()`, before `options.config` is attached and before model/controller auto-mapping mutates the object. `pages()` sets `options.dynamic = true` before delegating to `page()`, so fan-out registrations are captured with that flag and replay as fan-outs. Pages registered from inside a `generate()`/`complete()` callback are logged too, and replay from their snapshot — but they replay _once, up front_ with the rest, not at callback time, so a callback that registers pages derived from resolved model data replays with the options it produced on the first build, not recomputed ones. The snapshot is _shallow_: an object/array model or a function controller is shared by reference with the original options, so a controller that mutates `options.model` in place accumulates those mutations across rebuilds (each replay starts from the already-mutated object). Keep controllers idempotent — return new values rather than mutating what they were handed.
- **`scan()` dedupes against `_registrations`, not `_stack`.** `page()` records a registration synchronously but only _queues_ the page — `_preparePage` runs later, off the promise chain — so `_stack` is empty during a synchronous `.page(…).scan()` chain and again at the top of a replay. Scanning against it registered the same view twice, and the second copy was rejected by `_preparePage`'s `buildTo` dedupe with `Page already processed`. The registrations list is the one written synchronously, so it is the one that can answer "did someone already ask for this view".
- **Two pages claiming one `buildTo` is a build failure** (`_preparePage`): the second is still not stacked, but alongside the `Page already processed` log it now pushes `{ view, buildTo, error }` onto `_failures`, so `complete()` rejects. It used to log and return `null`, which meant a page the caller asked for was simply missing from a build that reported success — the same silent-success class as a dropped render (review finding C6). The dedupe applies to `.pages()` fan-out too, since each fanned-out page goes through `_preparePage` individually (v1 never deduped fan-out output); a fan-out whose controller derives the slug from model data is exactly where a collision now surfaces instead of hiding. The rebuild paths do not hit it: `scan()` dedupes against `_registrations` and `_replay()` replays a snapshot taken before its re-scan, both so the same view is never queued twice.
- `_prepareMultiplePages` builds a **fresh options object per fanned-out page** (`{ ...options, slug, model }`), and must keep doing so. It previously mutated and reused one object across the loop, which `_preparePage` then stored on each `KissPage` by reference (`kissPage.options = options`) — so every page in the fan-out aliased the same options. The visible symptom was `applyController`'s "title from `model.title`, unless already set" mapping: item one filled the title and the guard skipped the rest, so all pages rendered the first item's title. `{{model.x}}` stayed correct throughout, which is why the characterization tests missed it — they only ever asserted on `model`, never on an option derived from it.
- **A bad item in a `.pages()` fan-out fails that item only** (`_prepareMultiplePages`): the per-item `applyController` + `_preparePage` step runs inside its own `try`, so a controller that throws for one item is recorded as `{ view: '<view> [item N: <slug>]', buildTo: null, error }` and the loop moves on to the next item. It used to let the throw unwind the whole loop into `page()`'s `try`, which recorded one `{ view, buildTo: null }` entry and abandoned every later item — unregistered, unrendered and unreported, so one failure entry stood for the entire tail of the fan-out (review finding F-E1; diploma-msc fans 64 catalogue pages from one call). N bad items now report N failures and the good items still build. The label is the only handle the operator has on _which_ record was malformed: there is no `buildTo` yet, and every item in a fan-out shares one `view`, so the position is always included and the item's own `slug` too when the model carries one. Because nothing escapes the loop, `page()`'s catch never records a second entry for the same item — that double-record is what a `throw` after the per-item catch would reintroduce.
- `viewStats()`'s `debug.json` serialises a _projection_ of `_stack` (`{ view, buildTo, runCount, options }`), never the entries themselves: a stack entry's `page` holds the Handlebars environment (internally cyclic) and the logger, so `JSON.stringify` on the raw stack throws "Converting circular structure to JSON" and the file silently never gets written. The write is not awaited — `test/integration/view-stats.test.js` polls for the file with `waitFor`, on it _parsing_ rather than on it existing: `fs.outputJson` creates the file truncated and fills it a tick later, so a `pathExists` poll wins the race often enough to fail the suite under load and reads back an empty string.
- **The map's model and controller classification is captured in `page()`, not read off the stack.** By the time a page reaches `_preparePage` its `options.model` _is_ the resolved data and `options.controller` may be a function, so a map read off the stack alone would say `inline` for every page in the site. `page()` calls `pageOrigin(options)` (from `lib/aikb.js`) immediately after its two auto-mappings — so a page that never named a model still records the `<view>.json` the engine found for it — and hands the result down to `_preparePage`, which parks it on the stack entry as `entry.origin`. `_prepareMultiplePages` passes the same origin to every fanned-out page, which is why a `.pages()` call contributes one row per item all naming one registration. It is deliberately **not** a key on `options`: every own key of a registration is spread back into `page()` on replay and reaches the render context and the dev-mode `.json` sibling.
