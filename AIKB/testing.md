# Testing

Cross-cutting notes on how tests in `test/` are organized and written — not a per-module doc, so it's free-form and not required to follow the five-heading template.

## Layout

- `test/unit/` — one file per `lib/` module _except the orchestrator_ (`lib/kiss.js` has no `test/unit/kiss.test.js`), exercising each in isolation (mostly pure functions, or a module with its dependencies passed in via DI). It also covers `scripts/` — the dev tooling the branch ritual runs (`base-branch`, `gates`, `check-staged-format`, `bench`, `sync-plugin-versions`) and the type emitter (`emit-types`) are outside the engine, so nothing else exercises it. Those tests target the pure decision core each script exports; the I/O wrapper below it stays thin and untested.
- `test/integration/` — cross-module behavior driven through the public `Kiss` API: lifecycle (`generate`/`complete`), dedupe, config resolution, watch mode, ESM/CJS interop, and a broader "characterization" suite. This is where `lib/kiss.js` itself is covered — end-to-end through its public API rather than in a dedicated unit file.
- `test/helpers/site.js` — `makeSite(files)` creates an isolated temp-dir site (under `os.tmpdir()`) and returns `{ root, src, build, folders, read, exists, touch, cleanup }`; `waitFor(predicate, { timeout, interval })` polls until a predicate is true (used for watch-mode assertions) or throws after `timeout`. Paths are returned with forward slashes because the engine compares and slices paths as posix throughout (`utils.posixPath`).
- A test that spawns a child process of its own — `test/unit/pipeline.test.js` runs `node -e` commands through `createPipeline` — uses `process.execPath`, quoted, rather than a bare `node`, and must `close()` the pipeline in `afterEach`: a watch process left running keeps the worker (and the temp folder) alive.
- `test/helpers/kiss.js` — re-exports `Kiss`/`utils` from `lib/kiss.js` and `ENTRY` (`path.resolve('lib/kiss.js')`), so integration tests import one thing instead of reaching into `lib/` directly.
- `test/fixtures/consumer/` — a plain-JS site (`site.js`, `// @ts-check`) plus a deliberately broken one (`bad.js`), each with its own tsconfig mapping `kiss-ssg` to the repo's `types/kiss.d.ts`. `test/unit/types.test.js` runs `tsc --noEmit` over both through `child_process`: `site.js` must be clean, `bad.js` must report exactly three named errors. Not a unit test of any module — it is the published type surface checked from the outside, the way a consumer meets it.
- `test/aikb.test.js` — **not** the unit test for `lib/aikb.js` (that is `test/unit/aikb.test.js`, with `test/integration/aikb.test.js` beside it); this one is the repo's docs-sync test, named for the `AIKB/` folder it guards. It is covered by this doc's own CLAUDE.md table row: fails if a `lib/` module has no `AIKB/` doc, a doc isn't listed in `CLAUDE.md`'s lookup table, a doc has no matching module, or a doc drops one of the five required headings. It also holds the two shipped-docs parity checks: every non-underscore `Kiss.prototype` method is named in `llms.txt`, and the config-defaults block in both `llms.txt` and `README.md` evaluates to exactly `resolveConfig({})` — so a new default cannot land in `config.js` alone.
- `test/unit/plugin-manifests.test.js` — the Claude Code plugin's own sync test: `.claude-plugin/marketplace.json` and `plugins/kiss-ssg/.claude-plugin/plugin.json` must parse, both must carry `package.json`'s version, the marketplace's `source` must resolve to the plugin folder, and every skill's frontmatter `name` must match its folder. It also walks each `SKILL.md` for inline-code paths starting `node_modules/kiss-ssg/` and fails if one does not exist in the repo or is not inside the `files` whitelist — the skills point at the shipped docs instead of restating them, so a path that does not ship sends the agent nowhere.

## Commands

```bash
npm test                        # vitest run — full suite, single pass
npx vitest run <file>            # a single test file
npm run test:watch              # vitest, watch mode
npm run test:coverage           # vitest run --coverage
npm run lint                    # eslint . (flat config, eslint.config.js)
npm run types                   # regenerate types/ from the JSDoc in lib/
```

## Conventions

- Pass `logger: silentLogger` (from `lib/logger.js`) into `new Kiss(...)` in any test that doesn't specifically assert on log output — keeps `npm test` output clean.
- Dev-mode / watcher tests mock the dev server rather than binding a real port for every test: `vi.mock('../../lib/dev-server.js', () => ({ startDevServer: () => ({ ready: Promise.resolve(), close: async () => {} }) }))` before importing `Kiss`. The mock must include `ready` — the `Kiss` constructor does `this._devServer.ready.catch(...)`, and a mock without it throws a `TypeError` that the surrounding `try/catch` swallows into the (silent) logger, so the dev-mode test would pass for the wrong reason.
- Any test that calls `.watch()` (directly or via `{ dev: true }`) must `await kiss.close()` in `afterEach` — otherwise chokidar's open watchers keep the process/worker alive and can hang the test run.
- `fs.utimesSync` rounds to whole milliseconds, so a test that pins a file's mtime back and then asserts `statSync().mtimeMs` against the `Date` it passed can be 0.001ms off. Assert the difference is under 1ms, not equality (`test/unit/kiss-page.test.js`, the content-keyed cache test).
- `watch({ entry: null })` is the standard way to disable the entry-script watcher in tests (see `lib/watcher.js` — there's no real "entry script" when `Kiss` is constructed from a test helper).
- `test/integration/esm.test.js` verifies `require('kiss-ssg')` still works from CommonJS by spawning a real `node` process on a generated `.cjs` file (via `execFile`) — this can't be tested in-process because Vitest itself runs under ESM.
- `test/integration/check.test.js` runs the real `bin/kiss-ssg.js` as a child process against a throwaway site under the OS temp dir — the only way to assert on an exit code and on stdout carrying nothing but the JSON report. The fixture sites it writes import the engine by absolute `file://` URL (a temp dir cannot resolve `kiss-ssg` from `node_modules`), and each one asserts that the build folder is still absent, or still holds its sentinel file, afterwards. Its second `describe` reads the same report through the API instead — `kiss.report()`, `err.report`, and the staged-path mapping after a promoted and after a discarded atomic build — since `lib/kiss.js` is covered here rather than in a unit file.
- `test/integration/bench-watch.test.js` is the one exception to "the I/O wrapper below the decision core stays untested": `scripts/bench.mjs`'s `--dev` watch reading spawns a real dev-mode site, drives it over a websocket and edits its source files, and none of that can be asserted from a pure function. It generates a three-file site under the OS temp dir, links this repo into its `node_modules` with a **junction** (`fs.symlinkSync(…, 'junction')` — no elevation on Windows, and it is what lets `resolveKissFrom` prove which engine was measured), picks both ports with `net.createServer().listen(0)` because the engine's defaults collide with any dev server the operator left open, and afterwards asserts the three touched files are byte-identical and the livereload port binds again — the proof that no child was left running. 60s timeout, like the other child-process suites; it runs in about three seconds.
- A skill's helper script under `.claude/skills/*/scripts/` gets a `test/unit/` test when it carries logic of its own: `test/unit/corpse-collector.test.js` exercises the scanner's AIKB-staleness check on a temporary git repository (`git init`, commits driven by `execFileSync` with an explicit `cwd`, never a shell string), which is why `scan.mjs` keeps its scan body under `main()` and exports the check.
- `test/integration/examples.test.js` builds every example under `examples/` (1–11) as a child process and asserts its exit code, its page count, and each example's distinctive behaviour (example 8's controlled failure, example 9's deduped `lookup` warning and dedupe recipe, example 10's pipeline-generated stylesheet). Every example writes into the one shared repo-root `public/`, so its tests stay in one plain (non-`concurrent`) `describe` — Vitest's default declaration order is the only sequencing this needs — and each test clears its own example's output folder immediately before building, so a page count can never be a leftover from a previous run. Skips (rather than fails) if `examples/` is absent. Example 9 is the exception to "every example writes into `public/`": `examples/9-migrated-from-v1/AIKB/` is committed source, recorded by `npx kiss-ssg aikb`, so one test runs the published bin from `examples/` and asserts the four generated files come back byte-identical to the committed ones. That is the guard on the property the whole feature rests on: recording an unchanged site twice must leave `git status` clean. Example 8 is the counterpart — it fails on purpose, so it can never be recorded, and its test asserts no `AIKB/` appears beside it.

## Gotchas

- `npm run lint`'s `@eslint/js` (v10) requires Node ≥22.13, even though the package's own runtime floor (`package.json`'s `engines.node`) is 22.12 — on Node 22.12.x exactly, `npm test` passes but `npm run lint` may refuse to run.
- **`types/` is generated — never hand-edit it.** `test/unit/types.test.js` re-emits it and byte-compares, so a JSDoc change in `lib/` fails the suite until `npm run types` has been run and the result committed. The failure names the file and the command.
- The examples (`npm run eg1` … `eg10`) and `node docs` build and exit by default, so they are safe to run bare — except example 8, which exits 1 by design. It is the `--dev` flag that starts a server and **never exits on its own** — `node docs --dev`, or `npm run eg1 -- --dev` (examples 1–6, 8, 9, 10; example 7 takes a season slug instead). Use `timeout 10 node <script> --dev` in Git Bash (or equivalent) to smoke-run that path and let the timeout kill the process.
- `docs/` is emptied by `docs.js` on every run (`cleanBuild: true`, the default) — nothing hand-written can live there. Specs and implementation plans belong in `planning/` (`planning/specs/`, `planning/plans/`), never under `docs/`.
- **Watch-mode assertions wait on the rebuild, not on one file.** A replay's orphan sweep removes an output and its dev-mode `.json` sibling one `await` apart, so `waitFor(() => !exists('x.html'))` returns while the sweep is still running. A test that then asserts on the sibling is racing that interleaving — it fails under load (roughly 1 in 100 exposures with the suite run 5-up on 4 cores) and, worse, can pass for the wrong reason when it asserts a file is _kept_. Wait on the file to see the rebuild has started, then drain the queue (`while (kiss._rebuildInFlight) await kiss._rebuildInFlight` — `rebuildSettled()` in `watch.test.js`) before asserting anything else. Likewise, wait on a new page's _content_, not its existence: `fs.outputFile` creates the file before writing it.
- The CJS interop test (`test/integration/esm.test.js`) spawns a real `node` binary on a `.cjs` file via `execFile` — a slow or misconfigured `node` on `PATH` shows up as a test timeout there, not an assertion failure.
