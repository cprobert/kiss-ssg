# rebuild.js

## Responsibility

The watch session, from a file event to a reloaded browser: what each watcher event means
(`_handleChange()`), the one serial queue every rebuild goes through (`_requestReplay()`,
`_requestRebuild()`, `_runRebuildQueue()`), the two kinds of rebuild — a whole-site replay from
the logged registrations (`_replay()`) and a scoped re-render of the pages an edit can reach
(`_rebuild()`) — and the one live reload per settled rebuild (`_reload()`, `_builtAssetPath()`).
It also holds the body of `watch()`, which wires `lib/watcher.js`'s callbacks to all of that.
`lib/watcher.js` is the file watching itself and knows nothing of the stack.

Every function takes the `Kiss` instance and reads its state at call time. The state stays on
`Kiss` — `_rebuildInFlight`, `_pendingReplay`, `_pendingTargets`, `_pendingAssets`, `_closing`,
`_watcher`, `_helpersReady`, `_unswept`, `_replaying`, and everything a replay resets — and each
private method on `Kiss` is a one-line delegator to the function here. **This is the module the
late-binding rule exists for**: tests spy on or replace `_reload`, `_rebuild`, `_replay`,
`_requestReplay`, `_requestRebuild` and `registerPartials` on the instance, call
`_handleChange`, `_runRebuildQueue` and `_rebuild` directly, and overwrite `_pendingReplay`,
`_helpersReady` and `_watcher` mid-test. So every call here goes through the instance —
`kiss._replay()`, `kiss.registerPartials()`, `kiss.generate()`, never the function behind it —
and the closures handed to `createWatcher` call `kiss._handleChange(…)` at event time.

## Public interface

Each is the body of the `Kiss` method named beside it:

- `replaySession(kiss)` — `_replay()`.
- `requestReplay(kiss)` — `_requestReplay()`; `requestRebuild(kiss, entries)` —
  `_requestRebuild()`; `runRebuildQueue(kiss)` — `_runRebuildQueue()`.
- `rebuildEntries(kiss, entries)` — `_rebuild()`.
- `handleChange(kiss, event, changedPath)` — `_handleChange()`.
- `startWatching(kiss, entry)` — the body of the public `watch()`, which keeps its documentation,
  its `entry = process.argv[1]` default and its `return this` on `Kiss`.
- `builtAssetPath(kiss, changed)` — `_builtAssetPath()`; `reload(kiss, changed = '/')` —
  `_reload()`.

## Non-obvious behavior

- Non-dev `watch()` with `cleanBuild: 'atomic'` is unsupported: a failed build latches disposal, and later replays can write staging without promoting it. Use a separate one-shot atomic build for publication. This existing limitation is documented, not repaired by the source-protection branch.
- Replay invalidates the settled link-check cache after orphan removal and asset restoration: removed pages must no longer resolve, and restored copies can bring in newly added files. The rebuild queue's preliminary scan is quiet; the final scan logs its verdict and refreshes the report. Dev mode and `links.check: false` still skip link checking. The launch-readiness audit follows the scan here exactly: `_audit` is reset and `_runAudit()` re-run beside it, because the orphan sweep and the restoration change what the folder walk finds.
- Asset watcher events join `_pendingAssets` in the rebuild queue. Each batch waits for initial rendering, copies/reconciles assets, then performs its replay or scoped render. With hashing enabled, all pages re-render only when the manifest's CSS/JS URL revision changes; image/font edits and identical emitted URLs keep the fast path. One changed Sass output gets a stylesheet refresh; multiple outputs get a full refresh. Reload follows completion, and `close()` drains the active batch. The shared output registry protects generated files at write and cleanup time, including custom auxiliary filenames, releases removed page ownership, and follows atomic promotion.
- `_replay()` starts by `await Promise.allSettled([...this._promises, ...this._generating])` — it must not reset those arrays while work is still running. A page chain still resolving (a slow URL model, an initial build that was never awaited) would otherwise land in the _new_ `_stack` and make the replay's own page lose the `buildTo` dedupe, leaving the previous build's output in place. `allSettled`, not `all`: a rejected in-flight promise must not abort the rebuild. Replays never overlap each other (the rebuild queue serialises them), so this only ever waits on non-replay work.
- **`_replay()` re-runs `scan()` when `_scanRequested` is set**, so a page file created while watching joins the site instead of waiting for a restart. The order inside `_replay()` is load-bearing: drop vanished scanned registrations → re-scan → replay the rest. Dropping first is what stops a just-deleted view being re-added by its own stale registration. The re-scan runs while `_replaying` is still `false`, so `page()` records what it finds as a new scanned registration that every later replay replays like any other — but it also _queues_ those pages there and then, which is why the replay loop iterates a snapshot of `_registrations` taken before the re-scan. Replaying the post-scan list would queue each new page a second time and lose it to the `buildTo` dedupe.
- `_replay()` drops any `scan()`-created registration whose `.hbs` view no longer exists on disk (logged once as `Removed page: <view>`) before re-registering, so a deleted page file is not re-queued, its `buildTo` is absent from the new stack, and the orphan sweep below removes its output and the `.json` sibling. Only scanned registrations are dropped: `scan()` derives the page list _from_ the file tree, so the file going away is the caller's own instruction, whereas a page registered by name is not — a missing view there stays a build failure rather than a silent disappearance, which is what would hide a typo. Scan-created registrations are tracked in a `WeakSet` (`_scanned`) keyed by the registration object rather than by a key on it, because `_registrations` entries are spread straight back into `page()` on replay and any own key would reach the render context and the dev-mode `.json` sibling; `scan()` sets `_scanning` around its `page()` calls the same way `_replay()` sets `_replaying`.
- **A renamed asset is invisible to the orphan sweep, on purpose.** The sweep works from `_stack` `buildTo` paths (page outputs); assets have no stack entry. Stale hashed files are removed by `lib/assets.js` from the manifest's own record of the name it replaced, not here.
- **Under a hashing policy an asset edit re-renders the pages.** `watch()`'s `assetsChanged` normally just re-copies and names the built file for a live-reload stylesheet swap. With `config.assets.hash`, and only for a file the policy actually renames (`isHashable`, i.e. the built `.css`/`.js`), the copy has changed the filename, so every page is linking one that no longer exists: the handler instead asks the rebuild queue for a scoped re-render of `_stack` (the same scoped path an edited partial takes, but every entry: a renamed asset can be linked from any page) and lets the queue's `.finally()` do the one reload, after every page has been rewritten. An edited image or `robots.txt` keeps its name, so it keeps the cheaper targeted reload. `_builtAssetPath` also resolves through the manifest, so the path it hands live reload is the file that is actually on disk.
- `_replay()` (watch rebuilds only) discards `_stack`, `_promises` and `_generating` (and `_failures`, and resets `_assetQueue`), re-registers partials, then re-runs `page()` for every entry in `_registrations` with `_replaying = true`, and finally `generate()` + `complete()`. Because the whole pipeline re-runs, models are re-read from disk (and URL models are _re-fetched_ — a watch rebuild costs a network round trip per remote model, unless `config.fetch.cache` is set to a directory, in which case the cached body is read instead and no request is made: see `AIKB/fetch-policy.md`) and controllers re-run; `_replaying` also propagates as `fresh` into `applyController`, which busts Node's module caches so an edited controller file reloads (see `AIKB/controller-resolver.md`). The build dir is _not_ cleaned by a replay (that would blow away assets and leave the site briefly empty for the dev server); instead the replay snapshots the previous stack's `buildTo` paths up front and, in a `finally` around `complete()`, removes any that the new stack no longer contains — plus the same-named `.json` dev debug sibling. So a page whose slug changed, or one that vanished from a shrinking `.pages()` fan-out, no longer leaves stale output behind. The removal runs in a `finally` so a failed rebuild still cleans up — but only one that failed **after** it re-queued the site. The `try` now opens right after `previous` is captured and wraps the whole re-registration half (`registerPartials()`, the drop-vanished-registrations filter, the re-scan, the `page()` loop) as well as `complete()`, and a `requeued` flag flips once the `page()` loop has run. Two reasons. (1) A throw in that half used to skip the `finally` altogether, so `previous` was lost and every stale output stayed on disk for the life of the process — no later replay could see it, because each one snapshots `previous` from a `_stack` that no longer mentions those files, and in dev mode the server went on serving a page that had been deleted. (2) Simply widening the `try` is not enough on its own: with `requeued` still false the new stack is empty because the replay _failed_, not because the site shrank, so an unguarded sweep would delete the entire build. So a replay that throws before re-queuing sweeps nothing and parks `previous` on `_unswept`, which the next replay folds back into its own `previous` (deduped) and sweeps then; the last good build stays on disk in the meantime and the failure is reported as `Error rebuilding site` as before. Once the pages are re-queued the old contract holds unchanged: every page that should exist has a `buildTo` in the stack (`_preparePage` runs before the render), so `previous` minus the stack is genuinely stale even when the rebuild then fails while rendering. **The sweep is only atomic at the rebuild's edge, not per page**: it removes the output and then its `.json` sibling one `await` later, and works through `previous` one entry at a time, so between those awaits the build dir is legitimately half-swept. The completion signal is the rebuild queue settling (`_rebuildInFlight`), never an individual file disappearing — anything that reacts to one removal and then reads another (a test, a deploy step) is reading a state the engine never promised. That is what made `test/integration/watch.test.js`'s deleted-scanned-view test load-sensitive: it waited on `gone.html` and then asserted on `gone.json`.
- A replay re-runs `llms()` on the same rule and right after the sitemap, from `_llmsRequest` — an entry's title, description or URL can all change with a model or controller edit, so a stale `llms.txt` is exactly as wrong as a stale `sitemap.xml` was.
- A replay re-runs `feed()` too, from `_feedRequest`, immediately after the `llms()` re-issue and on the same rule. A feed item's title, description, date and URL all come from the same options a model or controller edit rewrites, so the three registry-derived files (`sitemap.xml`, `llms.txt`, the feed) are re-issued as one block and can never be a rebuild apart. `_feedRequest` is the one of the three fields `_replay()` does **not** reset — it is the standing request, not the result; `_feedPath` is reset beside `_llmsPath`.
- A replay re-runs `sitemap()` when one was ever requested: `sitemap()` records `_sitemapRequest = { options, callback }` (idempotent — the replay's own call re-records the same request), and `_replay()` re-issues it right after `generate()` so `complete()` drains it and `sitemap.xml` matches the new stack. v1 (and v2 before this) left `sitemap.xml` stale after a slug change in watch mode. Like the `generate` callback, the `sitemap` callback re-fires on every watch rebuild — once per replay, with that rebuild's `urls`, not just on the original call.
- Watcher rebuilds are fire-and-forget from the watcher's point of view — nothing awaits what `_handleChange` returns — but they are still _tracked_: `_rebuild(entries)` pushes each `page.generate().catch(() => {})` onto `_generating` (caught there because `KissPage.generate()` now rethrows, and it has already logged; a scoped rebuild must not turn into an unhandled rejection or a `complete()` failure), so a replay's `allSettled` waits for it and `complete()` drains it. `_generating` accumulates one entry per re-rendered page until the next replay resets the array.
- **All rebuild work goes through one serial queue** (`_runRebuildQueue()`): one in-flight slot and one pending slot, where the pending slot is a set of scoped targets (stack entries to re-render) plus a "replay" bit. `_requestReplay()` sets the bit and clears the set — a replay rebuilds everything, so it supersedes every scoped rebuild — and returns the in-flight promise, so N rapid watcher events (save-all, a formatter, a branch switch) produce at most one in-flight run plus one follow-up and the last replay reads the newest files. `_requestRebuild(entries)` adds to the set, or is a no-op while the bit is set. Two rebuilds must never overlap, for two distinct reasons: `_replay()` resets `_stack` synchronously, so two replays interleaved would let the older one's still-pending chains fill the new stack and the newer pages — the ones carrying the newest edit — would be rejected by `_preparePage`'s `buildTo` dedupe with a `Page already processed` error, leaving stale output; and scoped work in flight when a replay starts re-renders from a stack the replay is about to discard. Two scoped rebuilds racing each other are the same hazard in miniature, which is why the queue covers both kinds rather than only replays. The follow-up run is _not_ chained into the returned promise (the `.finally()` callback returns `undefined`), so awaiting `_requestReplay()` waits only for the run that was in flight. Errors from either kind of run are caught and logged as `Error rebuilding site`.
- **Live reload is issued from here, once per settled build**, because nothing watches the build folder any more (review finding F-E4 — see `AIKB/dev-server.md` for what was removed and why). `_reload(changed = '/')` is the single call site of the dev server's `refresh`; it is a no-op when there is no dev server, and it swallows anything the call throws, because a live-reload socket that has gone away must never fail the rebuild that triggered it. There are exactly three places it fires:

  | When                                                               | Where                                                   | Path sent                  |
  | ------------------------------------------------------------------ | ------------------------------------------------------- | -------------------------- |
  | the first build settles                                            | the constructor's dev block, after `_settle()`          | `'/'` (reload the page)    |
  | a rebuild settles — replay or scoped, one reload for the whole run | `_runRebuildQueue()`'s `.finally()`                     | `'/'`                      |
  | an assets copy the watcher asked for finishes                      | `watch()`'s `assetsChanged`, chained onto `_assetQueue` | `_builtAssetPath(changed)` |

  The rebuild reload sits in the queue's `.finally()`, which is **after** a replay's orphan sweep, so the browser can never fetch a page that is still being written or one the sweep is about to remove. The initial one exists because a browser left open across a restart would otherwise sit on the previous build's output until the next edit. `_builtAssetPath(changed)` maps an edited asset to where it lands in the build folder (with `.scss`/`.sass` → `.css`, since that is what sass wrote): naming the built file is what lets livereload swap a stylesheet in place instead of reloading the page, which is why the assets watcher forwards the changed path at all. It returns `'/'` when there is no assets or build folder — nothing was copied, so there is nothing to name.

- **The watch dispatch lives here, not in the watcher** (`_handleChange(event, path)`), because deciding needs the stack, the partials registration and the rebuild queue — all of which are `Kiss` state. The watcher forwards every event under `src` and this is the whole table: **Every folder test in it resolves both sides**, including the page test, which was a raw `changed.startsWith(pagesDir + '/')` — a comparison of two path SPELLINGS. `folders` derives the six folders from `src`, so they normally share a form and it worked; but either can be given explicitly, and a site naming `src` relatively and `pages` absolutely made that test false for every page edit. The consequence was the safe direction and therefore invisible — the view matched no stack entry and the edit fell through to the replay fallback — so a scoped re-render of one page silently became a whole-site rebuild, which is the difference the benchmark work exists to protect. The view name is now `path.relative(pages, changed)` rather than a slice by string length, for the same reason: two spellings can be the same place.

  | Event                                                     | Action                                                                                                                                            |
  | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `add` / `addDir` (after the watcher's own `ready`)        | `_requestReplay()`                                                                                                                                |
  | `unlink` under `folders.pages`                            | `_requestReplay()`                                                                                                                                |
  | `change` under `folders.partials` / `folders.layouts`     | `registerPartials()` + `_requestRebuild(_graph.dependentsOf(name))`                                                                               |
  | `change` of a page view matching stack entries            | `_requestRebuild(matches)`                                                                                                                        |
  | anything else (model, controller, unknown file, no match) | `_requestReplay()`, plus a restart notice for a `.js`/`.mjs`/`.cjs` file under none of `folders.models`, `folders.controllers`, `folders.helpers` |

  A replay is the default and the fallback: only the two scoped rows are narrower than one, and each is provably so.

- **A replay cannot pick up every file it rebuilds for, and says so.** Models are re-read from disk and controllers re-imported on a cache-busted URL, so an edit to either reaches the build — that is why the last row's notice excludes them. Everything else the build script imported is already in the ESM cache, and the replay runs from `_registrations` rather than by re-running the script, so a helper module's edit cannot reach the build at all. Announcing only `Rebuilding site:` therefore presented a change that was never applied as one that was: the site rebuilt, the browser reloaded, and the old helper output was served. The notice is the whole fix — re-registering helpers is the build script's job, not `Kiss`'s, and `Kiss` has no handle on it. **It is scoped to JavaScript modules on purpose**: `import` is what holds a cached copy, so only a `.js`/`.mjs`/`.cjs` file can be stuck. A data file under `src` (`.json`, `.md`, `.csv`) is read at render time — the pattern the docs recommend for helper data — and a replay re-renders every page against whatever is on disk, so the edit does land. Measured: a helper reading `src/data/business.json` with `readJsonSync` at render time picked the edit up while the first version of this notice was still claiming it had not, which is the same lie in reverse.
- **A path-matching regression in this dispatch is invisible in the output, and that is worth knowing before trusting a green build as evidence.** An event whose path matches no folder falls through to `replay()`, which re-reads every model, re-imports every controller and re-renders every page — so it produces exactly the bytes a correct scoped dispatch would, by the expensive route. Measured: mutating the `src` watcher to emit absolute paths (the mismatch that made the helpers entry unreachable) left an output-only watch test green. `test/integration/watch.test.js`'s defaults test therefore asserts the **dispatch** — `Rebuilding:` is scoped, `Rebuilding site:` is a replay — and it was confirmed red under that mutation. An assertion about output cannot tell the two apart, which also means a site can lose the whole scoped fast path to a config typo and only ever feel it as slowness.
- **The partial/layout fast path is safe.** An edited partial or layout cannot change `_registrations`, `_stack`, any page's resolved options, its `buildTo`, or the sitemap — the only thing a replay would do differently is _which_ pages it re-renders. So the stack is unchanged by construction, orphan cleanup, the `buildTo` dedupe and `_failures` are untouched, and what is skipped is exactly the expensive half of a replay: every model re-read from disk, every controller re-imported with a cache bust, every URL model re-fetched over the network (or read from `config.fetch.cache`). `test/integration/replay-equivalence.test.js` is the standing proof: the same edit sequence applied through the real dispatch and through forced replays must leave byte-identical build directories.
- **A partial or layout `change` re-renders the pages that rendered it.** `_handleChange` re-registers the partials, maps the path to a name with `partialNameFor`, and asks `_graph.dependentsOf(name)` (`AIKB/dependency-graph.md`): the matching stack entries go to `_requestRebuild`, through the same serial queue as every other rebuild. `null` — a partial no page has recorded, because nothing has rendered it yet or only a failed page would have — re-renders every entry and logs a notice naming the file, so an untraced edge shows up as a fixable gap rather than silent slowness. `[]` re-renders nothing, which is right: no page used it. A partial edit that arrives while a rebuild is in flight is still upgraded to a replay (below). Measured before the graph existed (diploma-msc, 654 pages): a partial save re-rendered everything in 1247ms; a page render is ≈1.9ms, so a partial N pages use now costs ≈2N ms plus registration.
- **A partial edit arriving while a rebuild is in flight is upgraded to a replay** (the `_rebuildInFlight` check inside the fast-path branch of `_handleChange`). Whether the run already in flight read the file before or after the edit landed is a race nobody can reason about — the render is synchronous but the registration that fed it may not be — so the pessimistic answer is the only one that can be justified. It costs one full rebuild in the rare overlapping-save case and removes a class of "the dev server is showing the old partial" bug.
- **`_rebuild(entries)` skips any target `_stack` no longer holds.** A scoped target queued before a replay names a page from the stack that replay discarded; re-rendering it would write from options nothing holds any more, and its `buildTo` may since have been swept as an orphan. The skip is silent — it is the expected outcome of "a replay supersedes scoped work", not a fault.
- The replay orphan sweep restores each asset copy whose producer survives a released page claim, once per copy. Restoration and report refresh run in the replay's finally path even when another page failed; they also run without an asset event. Changed hashed URLs re-render pages before the single refresh. The rebuild queue has no separate refused-path retry. Copy-before-render still provides current mappings; keeping old page ownership until the sweep protects outputs if replay fails before registration completes.
- Replay retires old page producers before rendering, while preserving their on-disk ownership for the orphan sweep. The sweep checks current kind and never removes another writer's output. Page registrations capture their working directory, retain it through replay, and use absolute `page.outputPath` for ownership, deduplication and cleanup. The report retains `buildTo`'s configured spelling.

## Known knowns

The watch session's accepted fringe: misbehaviour that only `--dev` shows and that **Ctrl-C and a fresh `--dev` clears**. The one-shot build is the contract; this register is what kiss knowingly does not chase, under the rule in `CLAUDE.md` ("The dev watcher is best-effort"). An entry graduates to a fix only when it stops meeting that bar — the one-shot build or `kiss-ssg check` shows it too, a restart does not clear it, it reaches a source file or anything outside the build folder, or the operator asks.

Each entry: **symptom** · **trigger** · **what clears it** · **how to re-check**. Add one in a line or two when a watch quirk turns up, and move on.

- **A page renders empty for a moment.** · An editor's truncate-then-write save that leaves the file empty for longer than the watcher's 200ms grace (`AIKB/watcher.md`). · The next save, or a restart. · Read the `isEmptyFileEvent` branch in `lib/watcher.js`: while it is still a fixed 200ms `setTimeout` rather than a check of the editor's write, this entry is current.
- **An edit is rebuilt but not applied: a `.page()` added to the build script, or a module the helpers entry imports.** · Both are held by the ESM cache, which a replay cannot invalidate (`AIKB/upstream.md`, "ESM has no cache-invalidation API"). kiss prints a restart notice rather than claiming the change landed. · A restart. · Add a `.page()` call to `examples/11-blog/router.js` during `npm run eg11 -- --dev` and look for the restart notice.
