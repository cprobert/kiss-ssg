# kiss-page.js

## Responsibility

One page's render logic: resolving its title/slug/path/extension, compiling and rendering its Handlebars template, minifying the HTML, and writing the output file (plus a debug `.json` sibling in dev mode).

## Public interface

- `class KissPage`
  - `new KissPage(view, { hbs, logger, graph } = {})` — `view` is a `.hbs` path (relative to `pagesDir`) or an inline template string. `graph` is an optional `DependencyGraph` (`./dependency-graph.js`); without one the render is unchanged.
  - `set path(path)` — sanitizes via `sanitizePath` (`./utils.js`); falsy values are ignored (default `''` kept).
  - `set slug(slug)` / `get slug()` — setter normalizes via `toSlug` (`./utils.js`); falsy values are ignored (default `'index'` kept).
  - `set ext(extension)` — strips a leading `.`, then slugifies via `toSlug` (`./utils.js`), like `path` and `slug`; falsy values are ignored (default `'html'` kept).
  - `set extLess(val)` / `set isDev(dev)` / `set debug(dev)` — each unconditionally coerces with `!!val` and assigns (`this._extLess = !!val`, etc.) — unlike `path`/`slug`/`ext`, these do **not** ignore falsy values; e.g. `page.debug = false` overwrites the existing value rather than being skipped.
  - `buildDir` / `pagesDir` / `livereloadPort` — plain fields `Kiss._preparePage` assigns from the resolved config (`folders.build`, `folders.pages`, `livereloadPort`); `livereloadPort` falls back to `DEFAULT_CONFIG.livereloadPort`.
  - `get buildTo()` — `${buildDir}/${pageURL()}`, the absolute-ish output path and the dedupe key `Kiss._preparePage` checks.
  - `pageURL()` — the page's URL/relative-path, honoring `extLess` (writes `slug/index.ext` instead of `slug.ext`, except for `slug === 'index'`).
  - `prepare()` — merges default options (`title`, `path`, `slug`, `generate: true`) under any already set on `this.options`; returns `this`.
  - `hash` — sha1 (hex) of the bytes `generate()` last wrote, or `null` if it has not written any. `BuildPage.hash` is this value (`AIKB/build-report.md`).
  - `async generate()` — compiles the template, renders with `this.options`, injects the livereload script in dev, minifies in production (dev skips minification entirely), asserts the resolved `buildTo` is inside the resolved `buildDir`, writes the file (records its `hash`) and, in dev, the debug `.json`; returns `this.buildTo`. Logs _and rethrows_ render/minify/escape/output-write errors.
- `loadMinifier()` — the one shared `Promise` for the `html-minifier-terser` import, resolving to its `minify`; every render awaits it.
- `preloadMinifier()` — starts that load without awaiting it, swallowing a failure that `loadMinifier()` will re-surface at the render that needs it. Called by the `Kiss` constructor for non-dev builds.

## Depends on

`fs-extra`, `node:path`, `node:crypto` (`createHash`, for the output `hash`), `html-minifier-terser` (dynamic `import()`, never at module load); `./utils.js` (`toSlug`, `toTitleCase`, `sanitizePath`), `./logger.js` (fallback logger only), `./config.js` (`DEFAULT_CONFIG.livereloadPort`, the fallback for a `KissPage` built outside `Kiss`). The dependency graph arrives as `deps.graph` (`AIKB/dependency-graph.md`) and is referenced only by a type-only `import('./dependency-graph.js')` in the JSDoc — there is no runtime import of that module here.

## Depended on by

`lib/kiss.js` (`_preparePage` constructs and stacks a `KissPage`).

## Non-obvious behavior

- **The render carries the page's identity in Handlebars' data frame**: `template(this.options, { data: { kissPage: this.buildTo } })`. Handlebars copies the frame into every nested partial invocation and handlebars-layouts passes `{ data }` through `extend`/`embed`, so a recording partial (`AIKB/partials.md`) reads `options.data.kissPage` and attributes itself to the right page whatever the render order — there is no "current page" variable and no assumption that pages render one at a time. Before rendering, the page calls `graph.clearPage(buildTo)` so its edge set is exactly what this render reached. `graph` is optional (`deps.graph`); without it the render is byte-identical to before — the extra `data` only adds a key to a frame Handlebars creates anyway.
- In dev mode the `.json` sibling gains `partials`: the names this page recorded, from `graph.usesOf(buildTo)` — the per-page view of `dependency-graph.json`.
- `_title` is computed from the _default_ slug (`'index'`) in the constructor, before any page-specific slug is set — so a page without an explicit title or model title falls back to `'Index'`, not a title derived from its own slug. This is a preserved v1 quirk, not a bug to fix.
- `buildTo` is the value `Kiss._preparePage` uses to detect duplicate pages (same output path) — a duplicate is a build failure there, not a skip.
- **Every part of `buildTo` is sanitised, `ext` included.** `ext` used to strip only the _first_ `.` (`replace('.', '')`) and never slugify, so unlike `path` (`sanitizePath`) and `slug` (`toSlug`) it carried `/` and `..` straight into the output path: `ext: './../../../escaped/pwned.html'` wrote three levels above the build folder, and the value is reachable from model data through the documented "controller derives the page's options" pattern (review finding C1). It now goes through `toSlug(extension.replace(/^\./, ''))` — `'.xml'` → `'xml'`, `'../x'` → `'x'`.
- **`generate()` refuses to write outside the build folder**: immediately before `fs.outputFile` it compares `path.resolve(buildTo)` against `path.resolve(buildDir)` and throws `Refusing to write outside the build folder: <buildTo>` otherwise. Belt-and-braces behind the sanitised setters — nothing reachable through them should trip it — and it throws inside `generate()`'s try, so it is logged and collected like any other render failure rather than being a silent write.
- **`hash` names the output, not the inputs.** It is the sha1 of `minifiedHtml` — the exact string handed to `fs.outputFile` — taken immediately _after_ the write resolves, so it can only exist for bytes that reached the disk. Hashing the render inputs (the template text plus the options) would have been cheaper to reason about and wrong in both directions: a template refactor that produces identical HTML would read as a change, and a minifier upgrade that changes every byte would read as none. It is set to `null` at the top of `generate()`, before anything is rendered, rather than in the catch — every path out of that `try` rethrows, so one clear-before is the only place that can promise "no hash unless _these_ bytes are on disk". A page with `generate: false` never enters the branch, so its hash stays `null` from construction. The consumer is `diffReports` in `lib/check.js`, which is why `null` has to mean "nothing to compare" and not "empty output": it counts a `null` on either side as changed.
- `fs.outputFile`/`fs.outputJson` writes are `await`ed — `generate()` does not resolve until the file (and, in dev, the debug JSON) is actually on disk.
- **The injected livereload `<script>` resolves its host at runtime, in the browser.** It is a short inline script that builds `http://<location.hostname || 'localhost'>:<livereloadPort>/livereload.js?snipver=1` and appends a `<script>` element via `document.createElement` + `document.body.appendChild`. Two reasons for the shape: the URL used to hardcode `localhost`, so with `devHost: '0.0.0.0'` a page opened from another device asked _that device's_ localhost and live reload silently did nothing; and the element is appended rather than written with `document.write` (livereload's own README snippet), which browsers warn about for injected scripts. `?snipver=1` is livereload's protocol marker and must stay. The script survives verbatim because dev mode skips `minifyJS`.
- The injected livereload `<script>` points at `livereloadPort`, a plain field `Kiss._preparePage` sets from `config.livereloadPort` (the same value `startDevServer` binds). It is a field rather than a render option deliberately: page options reach the template context and the dev-mode `.json` sibling, and the port is engine plumbing, not page data. The port used to be hardcoded, so a second site's pages polled the first site's livereload server (review finding D-01).
- Dev mode (`isDev`) injects the livereload `<script>` tag immediately before `</body>` and writes a sibling `.json` file (same path with only its _trailing_ extension swapped, via `/\.[^.]+$/` — a plain `replace(ext, 'json')` would also hit an earlier occurrence, e.g. a folder named `html`) containing the fully-resolved `options` — useful for inspecting what a page rendered with.
- `generate()` logs an error and then **rethrows** it, so `Kiss.generate()` can collect the failure and `Kiss.complete()` can reject with it (v1 logged and resolved, so a site could "build" with a page missing). Four failure paths rethrow: a render throw (e.g. `Missing helper`), a minify throw, the outside-the-build-folder assertion, and a failed write of the _output_ file (its inner `catch` logs `Error creating <buildTo>` and rethrows, so the error is logged twice — once specific, once by the outer `Error processing view <view>` handler). The dev-mode debug `.json` sibling is the exception: it is a debug artifact, so a failure to write it stays log-only and the page still counts as built.
- A view that ends with `.hbs` is a **filename** and must be read from `pagesDir`; anything else is an inline template string. When the read fails, `_getTemplate` throws `Error reading view: <path>` (with the fs error as `cause`), so the failure reaches `Kiss.generate()`'s catch, lands in `_failures` and makes `complete()` reject. It used to log the error and fall through with `viewText` still set to the view filename, which compiled the _filename_ as the page body — a deleted or misspelled view "built successfully" with `about.hbs` as its content (review finding B3).
- A template that fails to _compile_ is still log-only: `_getTemplate` returns `null` and `generate()` takes the "Skipping page generation" branch instead of throwing — so an unparseable template is a skipped page, not a build failure.
- **`html-minifier-terser` is loaded on demand, and a production build starts loading it from the `Kiss` constructor.** It costs ~155ms (it pulls in terser and a CSS parser), and `lib/kiss.js` imports this module eagerly for the `KissPage` class, so as a static import the cost landed on every process that touched Kiss — including ones that render nothing. Loading it at the first render instead put that 155ms on the critical path, serial with the work: measured same-machine, the `build` phase of a 50-page production build went **up ~44%** while end-to-end still fell, because import had dropped further. So `Kiss` calls `preloadMinifier()` from its constructor whenever `config.dev` is false, so the load can overlap whatever asynchronous work sits between construction and the first render. **What that buys depends on how much such work there is.** Most of the 155ms is CPU (evaluating terser), and a dynamic `import()` only progresses while the main thread is awaiting something, so it hides behind model resolution and the asset copy, not behind the synchronous constructor. Measured same-machine, 9 runs: at 50 pages the `build` phase is unchanged (`scan` +2.7%, `fanout` +7.2%, `styled` +0.5% — inside or at the noise floor, because 50 model reads are ~5ms of cover for a 155ms load); at 500 pages it falls (`scan` -5.1%, `fanout` -10.8%), where 500 model or view reads are enough to hide most of it. The 50-page cost of deferring the minifier is therefore _not_ repaid by preloading; it is inherent to loading a 155ms module in a process that has nothing else to do yet. Dev never minifies and never loads it. `loadMinifier()` caches the _promise_, not the resolved function: every page's render starts concurrently, and caching the result had each early caller issue its own `import()` before the first resolved — deduped by Node, so harmless, but one shared promise is the honest shape. A preload failure is swallowed and resurfaces from `loadMinifier()` at the render that needs it, against a page.
- **Compiled templates are cached per Handlebars environment, in a module-level `WeakMap` keyed on the env.** `_getTemplate` runs on every render and used to `readFileSync` and `hbs.compile` each time. A `scan` build hides that — one page, one view — but a fan-out does not: `.pages({ view: 'item.hbs', model: 'items' })` renders N pages from one template and compiled it N times. Handlebars is 44% of a 500-page build in the CPU profile, and it is the compiler, not the renderer. Measured on a real site's views (diploma-msc's four `catalogs/*.hbs`, 3.56ms each to compile, shared by 111 course pages): 395ms of compilation becomes 14ms. On the fixture's much smaller fan-out view, the build drops ~8%.
- **The cache hangs off the environment, not the module, because `hbs.compile` closes over the environment it was called on** — its helpers and partials resolve against that instance. Two Kiss instances in one process have two environments, and a template compiled on one must never be served to the other. A `WeakMap` also lets the cache die with the env rather than pinning every template a process ever compiled. `test/unit/kiss-page.test.js` pins this with two environments registering different `shout` helpers against the same view path; swapping the WeakMap for a shared Map fails it.
- **A cached template is validated by content, not mtime.** The view is read on every render and compiled only when its text differs from the text last compiled: the read costs ~0.03ms, the compile milliseconds, and the compile is the whole saving. The first version keyed on mtime, which depended on the filesystem's timestamp granularity — exFAT and some network and WSL2 mounts round to a second or two, so two saves inside one tick after a render would have served the stale template until the next save, a failure that only ever shows under `watch`. Comparing the text has no such dependence, needs no `stat`, and also sees through a save that changed nothing (a formatter no-op, a `touch`), which the mtime check recompiled. `test/unit/kiss-page.test.js` pins both: a content change with the mtime pinned back to its old value recompiles; a same-content rewrite with a newer mtime does not.
- **Only a successful compile is cached.** Caching a failed one would hide the error log from every later render of the same broken view; a broken template should complain once per attempt, not once ever.
- **Dev skips minification entirely rather than running it with every option off.** It used to call the minifier with `collapseWhitespace`, `minifyCSS` and `minifyJS` all `false`, leaving only comment and empty-attribute removal — which still paid for the parse, and (since the minifier is imported at first render) still paid ~155ms to load the package. A dev build never ships, so that pass costs more than it is worth; keeping comments and whitespace is arguably better for reading dev output. Measured over 9 runs: `watch@50` build **-32.7%**, `watch@500` build **-11.3%**. The saving is mostly the fixed import, which is why it is proportionally larger on the smaller site. It does **not** improve the scoped re-render (~37ms, unchanged): by then the package is loaded and per-page minification is a fraction of a millisecond. Production is untouched — the example suite still builds byte-identical to `main`.
- **Why the Sass compile still emits `compressed` in production, even though the minifier runs `minifyCSS` over the same bytes.** This looked like pure double work — on diploma-msc's real stylesheets the two paths land within 0.16% of each other (`catalog.scss` 21904b vs 21939b; `about-us.scss` +0.02%; `faculty.scss` +0.00%), so dropping the Sass side would have saved ~11ms a page for nothing. It was tried and reverted: Sass's `compressed` style converts percentage-form colours to hex (`rgb(80.4%,41.2%,21.6%)` → `#cd6937`) and clean-css does not, so a stylesheet built on `color.adjust` and friends grows instead. The benchmark's own `styled` fixture is exactly that shape and came out **19% larger** over 200 pages. The three real stylesheets contain zero percentage-form colours, which is why they showed nothing. A library default has to hold for stylesheets nobody has sampled, so the redundancy stays.
