# scorm-bridge.js

## Responsibility

The bridge between a page and a SCORM 1.2 LMS such as Moodle (`planning/plans/2026-10-24-learning-packages.md`, section B and amendment 2). In a SCORM package each member page is a SCO; the LMS puts an `API` object on a frame above it, and the page must start a session, report what happened and finish. The bridge does that, and gives the page's own script a small API, `window.kissScorm`, to record answers.

It is one inline `<script>`, not a file: the `{{scormBridge}}` helper renders it, so the same page works on the web, in an IMS content package and in a SCORM package, byte for byte. With no LMS above it, every call does nothing.

## Public interface

- `scormBridgeScript({ manual = false })` → `string`: `<script>(<the bridge>)(window,<manual>)</script>`. The same bytes on every call. The `scormBridge` helper (`AIKB/handlebars-helpers.md`) is its only caller in kiss.
- In the browser, `window.kissScorm`:
  - `available`: `true` while a session with an LMS is open.
  - `interaction({ id, type = 'choice', response, correct, result })`: one `cmi.interactions.n` entry at `n = cmi.interactions._count`: `id` first (SCORM 1.2 requires it of a new entry), then `type`, `student_response`, `correct_responses.n.pattern` (one per correct answer), `result` (`true` or `'correct'` is `correct`, anything else `wrong`) and `time` (CMITime, `HH:MM:SS`); then a commit. A `choice` answer is a letter: an option index (`0` is `a`) or a letter given; a `response` array is several, comma-separated (`c,a`). `correct` is a **pattern**, encoded apart from the response (`keys`): an array is a set every choice of which is required, `{a,c}` in SCORM 1.2's CMIFeedback, where a bare `a,c` means something else; `{ anyOf: [...] }` lists alternatives, each its own `correct_responses.n`, each a letter or a set. Before the Codex adversarial review of 2026-10-25 both went through one encoder, so a multi-select key was recorded as `a,c`. A non-`choice` type takes `{ anyOf }` the same way, each value as a string.
  - `score(fraction)`: `min` 0, `max` 100, `raw` the fraction as a whole percentage, clamped to 0–1; then a commit. `min` and `max` are optional in SCORM 1.2: an LMS without them refuses those two writes (401, not kept for a retry), still gets `raw`, and the bridge stays on (code review, 2026-10-25).
  - `status(value)`: sets `cmi.core.lesson_status` to `passed`, `completed`, `failed`, `incomplete` or `browsed`; any other value is ignored.
  - `resumed`: `{ location, state }` from `cmi.core.lesson_location` and `cmi.suspend_data` when the LMS launched the SCO with `cmi.core.entry` `resume`; `null` otherwise, and off an LMS — and `null` on the waiting placeholder until it hands over. A field the LMS failed to return is `null` (unknown), never `''` (read back empty): the drop rule at handover protects anything not confirmed empty (fourth Codex adversarial review of `ready()`, 2026-10-25: a failed read became `''` and a queued `bookmark('')` overwrote the saved place). Whether the learner is resuming is a read as well: when `cmi.core.entry` cannot be read, `resumed` is `{ location: null, state: null }` rather than `null`, so the page restores nothing and both fields are protected (fifth round: a failed entry read let queued defaults overwrite both). A queued `bookmark()`/`save()` is replayed with the bridge's own second argument, `queued`: its caller was told `true` when it queued, so a refusal at replay is kept in `unsent` and written again before the next commit, like any write the page never saw refused, rather than lost (same round). Pages never pass it; the embedded proxy and a waiting placeholder pass it on.
  - `ready(fn)`: calls `fn(kissScorm)` once the bridge has decided and returns a promise of the same object. The live bridge (an LMS or none) calls back at once; the embedded page's proxy when its owner is ready, with the embedded page's own `kissScorm`; the waiting placeholder at handover, after its queue — and its handover completes only when the bridge it hands to is itself ready (`next.ready(() => finish(next))`), so an embedded page whose bridge decided first, as a proxy to an owner still waiting, calls back once, with what is resumed (Codex adversarial review, 2026-10-25: it called back at once with nothing), and the placeholder keeps queueing meanwhile, so nothing is reordered. It also stays `window.kissScorm` until then (`finish` publishes the decided bridge): published early, a script running between two handovers called the new proxy, whose calls reached the owner's queue ahead of the ones still in this placeholder, and wrote them in reverse (third Codex adversarial review of `ready()`, 2026-10-25). Requested by a consumer (2026-10-25): a page that read `resumed` once at start, under a parent still loading, restored nothing, and its first `bookmark('')` was replayed over the saved place. A callback that throws does not stop the others; the first error is rethrown after them all.
  - `bookmark(location)` / `save(state)`: write `cmi.core.lesson_location` (at most 255 characters) / `cmi.suspend_data` (printable ASCII, at most 4,096 bytes), returning whether they did. A value past the limit is refused, never truncated. The first successful one sets `cmi.core.exit` to `suspend`, so the next launch is a resume. A session that was itself a resume sets `suspend` at the start, in any mode but `review`: without it, a learner who comes back and leaves without saving again exits normally, and the LMS starts them afresh next time with what they left unreadable (code review, 2026-10-25). Neither commits on the call: each successful one schedules a commit 2.5 s later (`commitSoon`) on the window's own `setTimeout`. The first uncommitted write starts the timer and later ones ride on it, so a burst of view changes commits once, and a learner who keeps moving is never more than 2.5 s uncommitted, which a strict trailing debounce would not promise. Any other commit (an interaction, a score, a status, the load-time completion, a checkpoint) cancels the timer, since it carried the writes. What is still unsaved is known exactly: `unsaved`, every value written since the last commit or finish the LMS **accepted**. A commit that fails leaves them there and is retried on the same timer, at most five times in a row, so persisting never waits for the learner's next action or the exit (Codex adversarial review, 2026-10-25: a failed commit cleared the flag and nothing retried). **On Moodle a retry cannot recover a commit lost in transit**: its API moves each element's baseline before sending, so the retry sends nothing and reports success, and `unsaved` is cleared with the values not on the server. Recorded, not worked around (`AIKB/upstream.md`, the operator's decision). A value a restarted session refused to take back (`unsent`) stays unsaved through a commit that succeeds, is written again before the next commit, and keeps the retry going (second Codex adversarial review, 2026-10-25: it was cleared with the rest, and lost); a timer that fires after `LMSFinish`, with the bridge off, or in review mode commits nothing, and review mode never schedules one. Requested from a consumer's Moodle test (2026-10-25): Moodle commits with synchronous XHR, which a browser may block while the page is dismissed, so a place written moments before leaving and left to the `pagehide` commit was lost on relaunch. A window without timers keeps the hidden and `pagehide` checkpoints only. A write the LMS refuses returns `false` and does not turn the bridge off.
  - `mode`: `cmi.core.lesson_mode` (`normal` when the LMS gives none), `null` off an LMS. In `review` every write is a no-op; only in `normal` is a page completed on load.
  - `log`: the last 50 events, `{ call, element, ok }` per LMS call, with `code`, `message` (`LMSGetErrorString`) and `diagnostic` (`LMSGetDiagnostic`) on a failure, read straight after it; and `{ event }` for the bridge's decisions. **Never a value**, written or read: learner data, answers, bookmarks and state stay out of it.

## What it does

1. **Once per window.** If `window.kissScorm` exists, it returns: including the helper twice is harmless.
2. **It waits for a parent still loading.** At handover, if the decided bridge finds the learner resuming, the `bookmark()` and `save()` calls queued meanwhile are dropped and logged (`… dropped: the learner is resuming`): they were written blind to the place the learner left and would overwrite it; answers, the score and the status are still sent. Only a resumed field the LMS did not confirm empty is protected: a queued `bookmark` is dropped unless the resumed location read back `''`, a queued `save` unless the resumed state did (same review: an empty resume lost the learner's new progress). A page that waits on `ready()` never queues one. It walks up `parent` (at most 20 frames, in `try`/`catch`). A same-origin parent whose document is still loading may yet run its own bridge (placed after an iframe in its `<body>`), so the bridge waits for each such parent's `DOMContentLoaded` before it decides, with a placeholder `kissScorm` that queues the page's calls (`available` is false meanwhile). Then it runs again, and sends the queued calls. The placeholder stays a working object afterwards: a page that kept it (`const scorm = window.kissScorm`) has every later call and property (`available`, `resumed`, `mode`, `log`) forwarded to the bridge that replaced it. Before the Codex review of 2026-10-25 it kept queueing into a queue nobody drained again, and that page's score and status were lost. Without the wait, whichever bridge ran first owned the session: a child that ran before its parent started it, the parent's `LMSInitialize` failed and turned the parent off, and the child's unload finished the session (found by a Codex adversarial review, 2026-10-24). A bridge in `<head>` runs before the page's iframes are parsed, so the usual case waits for nothing.
3. **Embedded pages proxy.** If a same-origin ancestor has `kissScorm`, this copy forwards every call to it and never touches the LMS: only the outermost kiss page of a SCO owns the session. It looks the ancestor's `kissScorm` up at each call, because an ancestor still waiting replaces its placeholder when it decides.
4. **Finds the API** up `parent`, then up `opener`, at most 20 frames each (10 until 2026-10-25; 20 is the depth the SCORM 1.2 best-practice report the operator supplied uses); a frame of another origin is skipped, never thrown on.
5. **Starts the session** with `LMSInitialize('')`, then reads `cmi.core.lesson_mode`, and `cmi.core.entry` with the bookmark and state when it is `resume`. Only in `normal` mode, it reads `cmi.core.lesson_status`: unless `manual`, it sets `completed` only from `not attempted`, `browsed` or `incomplete` (never downgrading `passed` or `failed`); with `manual`, it sets `incomplete` only from `not attempted`, since an LMS (Moodle among them) may record a status the SCO never set as completed at `LMSFinish`, and a learner who leaves early would count as done (Codex review, 2026-10-25). Then it commits at once.
6. **On `pagehide`**: sets `cmi.core.session_time` (CMITimespan, the time the page was live) and commits; it calls `LMSFinish` only when `event.persisted` is false. A persisted `pagehide` stops the session clock and a persisted `pageshow` restarts it, so an hour in the back/forward cache is not an hour of session time (Codex adversarial review, 2026-10-25: it was). A page frozen in the back/forward cache keeps its session, because Moodle's API refuses every call after `LMSFinish`. It registers no `unload` or `beforeunload`, which would keep a page out of that cache.
7. **On `visibilitychange` to `hidden`**: sets `cmi.core.session_time` and commits, never finishes. A phone that switches apps, or a browser that discards a background tab, may never fire `pagehide`; this is the checkpoint that saves the learner's answers anyway.

## Depends on

Nothing: the bridge runs in the browser, on `window` alone.

## Depended on by

`lib/handlebars-helpers.js` (`scormBridge`). `test/unit/scorm-bridge.test.js` runs the script in Node's `vm` against a scripted SCORM 1.2 `API` and stub frames, as rendered and as minified.

## Non-obvious behavior

- **The bridge is a real function, inlined by its source.** `scormBridgeScript()` uses `Function.prototype.toString`, so the bridge is linted, type-checked and formatted like the rest of `lib/`, and must use nothing from the module's scope. A production build minifies it with the page; the tests run both the rendered and the terser-minified script.
- **Every call is guarded.** After each call it reads `LMSGetLastError()`. On 301 (not initialised: the LMS ended the session underneath the page) it calls `LMSInitialize('')` once, **writes back every `unsaved` value** in the order first written (logged as `restored n of m values`), and retries once. Moodle's `LMSInitialize` rebuilds its data model from what was persisted, so a bookmark written before the session ended and committed by a timer after it was lost while the bridge reported nothing wrong (Codex adversarial review, 2026-10-25). Codex also offered never restarting from a background commit; restoring keeps amendment (4)'s restart and makes it safe for every caller, the timer among them. `unsaved` is cleared only by an accepted `LMSCommit` or `LMSFinish`. Only a session that stays lost (301 after the retry) or a call that throws turns the bridge off for the rest of the page's life. **Any other error fails that call alone**, logged with its code: the session is still open, so the next write and the next checkpoint's commit try again, and `LMSFinish` still runs on `pagehide`. Turning off on any error was the rule until the Codex adversarial review of 2026-10-25 showed one refused commit (101) losing every score, status and the finish after it. `call()` returns the error `code` for the callers that decide by it. Nothing ever throws into the page.
- **A refused write is kept, unless the page was told.** `set()` keeps any write the LMS refuses, other than as not implemented (401), in `unsent` and `unsaved`, so the next commit writes it back, under the bounded retry: the load-time completion, a `status`, a `score` and the `cmi.core.exit` suspend. The sixth Codex adversarial review (2026-10-25) found a refused suspend left a bookmark that the LMS would not offer back; the load-time completion, a status and a score were the same class, swept with it. The exception is `bookmark()`/`save()`'s own value (`set(…, told)`): the page is given `false` and decides, so the bridge never writes it behind the page's back. `suspend()` writes the exit once per page; a refusal of it is kept like any other.
- **An answer's time survives every hop.** The placeholder queues it with the time it was given, and the embedded page's forward passes that time on (`interaction(answer, at ?? clock())`): before the sixth round, an answer that waited for a loading parent was stamped with the time the parent finished loading.
- **An answer never takes an unrestored answer's index.** An answer's index is the LMS's `cmi.interactions._count`, which a refused write-back of an earlier answer's `id` leaves short; the next answer would take that index and overwrite it, inheriting its correct patterns besides (third Codex adversarial review, 2026-10-25). So `held()` (an interaction `id` in `unsent`) is checked _after_ the count is read, since reading it may itself restart the session. While it holds, the answer is `deferred`, and every later answer queues behind it. What is queued is the answer **encoded at submission** (`encode`: the entry's fields as strings, with the time it was given), never the page's object: a page that reuses one answer object and changes it before the queue drains would otherwise have its later answer recorded twice and the earlier one lost (fourth Codex adversarial review, 2026-10-25). The placeholder's queue, while a parent loads, is the other place an answer waits: it keeps a `snapshot` of the answer and the time it was given, and a bookmark or state as its string (fifth round: it kept the object). `record()` says what happened: `'done'` once the entry's `id` is in, `'held'` behind an unrestored id, `'retry'` when the LMS refused the count or the `id` this time, `'off'` on 401. A held or retried answer stays first in the queue; a field refused after its `id` landed is kept at its index in `unsent`, so the commit that follows writes it back (fifth round: a transient refusal discarded the answer); each commit writes the unsent values back first, then records the deferred answers in order, and the bounded retry keeps going while any wait. Answers still waiting when the retries run out are logged as not recorded.
- **Interactions fail soft, and only 401 stops them.** A 401 on `cmi.interactions._count` or a field (not implemented: Moodle's answer where interactions are unsupported) switches interactions off and the rest of the bridge keeps working. Any other refusal is retried, never dropped: a refused field is kept at its index and written back before the next commit; a refused count or `id` (without the `id` the entry does not exist) keeps the whole answer queued, in order, under the bounded retry. A field an LMS refuses for good (405, say) costs at most the five retries.
- **Ids are cleaned, not clipped.** An interaction id must be a CMIIdentifier. An id that is already `[A-Za-z0-9_.-]{1,255}` is kept; any other is cleaned to those characters, cut to 246, and given `-` and an 8-digit FNV-1a hash of the original, so two ids never become the same.
- **The session time counts the time the page was live** (`spent` plus the current stretch since `since`), set again at each `pagehide`. Moodle adds `session_time` to the total only at `LMSFinish`, so setting it more than once does not count time twice.
