# site-helpers.js

## Responsibility

Loads the **site's own** Handlebars helpers from `config.folders.helpers` and registers them on the `Kiss` instance, so a build script never writes `registerHelpers(kiss)` itself. Distinct from `handlebars-helpers.js`, which registers the helpers kiss ships.

## Public interface

- `helpersEntry(folder)` → the absolute path of the folder's `index.js` / `index.mjs` / `index.cjs`, or `null`. `null` is the ordinary case for a site with no custom helpers and must stay silent.
- `loadSiteHelpers(folder, { kiss, logger, fresh, previous, required })` → `{ loaded, entry, registered?, error? }`. Imports the entry, calls its `registerHelpers` export (or its default) with the instance, and **resolves** rather than throwing — a helpers folder that will not load is a build failure for the caller to record, not an exception through `new Kiss()`.

## Depends on

`fs-extra`, `node:path`, `node:module`'s `createRequire`, `node:url`'s `pathToFileURL`. Nothing in `lib/`.

## Depended on by

`lib/kiss.js` only — the constructor starts `_loadHelpers()`, `generate()` awaits it, and the helpers watcher calls it again with `fresh: true`.

## Non-obvious behavior

- **This module can only exist because the ordering constraint kiss documented for years was false.** `llms.txt` said the `registerHelpers(kiss)` call "must stay immediately after `new Kiss()`: partials are compiled at construction, and a helper registered later is not there when they render." Measured: a helper registered after construction _and_ after `.page()` renders correctly, in pages and inside partials. Handlebars resolves a helper from the registry at **render** time, not at compile time. That is what makes asynchronous loading safe from a synchronous constructor: the import is started in the constructor and awaited by `generate()`, which is always before the first render.
- **`generate()` awaits `_helpersReady` alongside `_promises`, and throws its result away.** `Promise.all([this._helpersReady, ...this._promises]).then(([, ...data]) => …)`. The discard is load-bearing: `data` is the documented array whose entry 0 is the construction-time asset copy, and renumbering it would silently break every site using `getModelByID`. Same reasoning that keeps `config.assets.pipeline` off `_promises` (`AIKB/kiss.md`).
- **`helpersEntry` returns a posix path**, like every other path kiss hands out. `path.resolve` gives native separators, and this one is compared against a watcher event (`Kiss.helpersChanged`) and lands in `_failures[].buildTo`: on Windows a native separator is a comparison that never matches and a failure nobody can grep for. The unit test pinning it is green on Linux whatever the implementation does — Windows CI is the leg that can see it, which is the standing caveat on any "gates green" claimed from a Linux checkout.
- **How the folder was chosen decides how hard a missing registrar bites** (`required`). `Kiss` reads `config.folders.helpers` from the config **as supplied**, before `resolveConfig` fills the default in — afterwards the two are indistinguishable and they mean opposite things. Named by the author → an entry exporting no registrar is a build failure, as it always was: they pointed kiss here. Defaulted → kiss guessed, so it is a `warn` naming the file and the fix (`folders.helpers` to the right folder, or `null`) and the build continues without site helpers. This is the upgrade hazard the default created: a project that had a root `helpers/` of unrelated utilities long before this feature existed lost its whole build to a folder nobody pointed kiss at. Only that one branch moves — an import that throws, or a registrar that throws, is a failure either way, because a folder that _is_ ours and broken loses every helper on a green build.
- **`folders.helpers` is not derived from `src` and is not in `foldersToEnsure`.** It defaults to `./helpers`, beside the build script, for the same reason `aikb` does: it is code the author writes, not content derived from `src`. Keeping it out of `src` also keeps it out of the `src` watcher, whose dispatch has no branch that could serve it — a helper module there is none of the six things a `src` event can be, so it fell through to a replay that ran the cached module and changed nothing.
- **A reload busts both module caches**, the same idiom as `controller-resolver.js`: `require.cache` by filename for CommonJS, a `?v=<mtimeMs>` query for ESM. Re-registering a helper of the same name is how Handlebars replaces one, so an **edited** helper needs no teardown.
- **A removed helper does need one**, and that is what `previous`/`registered` are for. `registered` is what the site's registrar registered on that load, as `{ name, prior }` **pairs** rather than bare names, measured across the `register(kiss)` call by comparing the registered **function** in `kiss.handlebars.helpers`, not by the name being new — so a built-in is never counted as the site's, and neither is a helper the registrar left alone. Identity rather than novelty because a site upgrading from before this feature still has its own `registerHelpers(kiss)` call in the router: the same registrar runs twice, by hand and then by kiss, so every name is already in the registry by the time kiss's load runs. Measured on the real loader, "names that were not there before" returned an empty list on that shape — which left the teardown with nothing to tear down, on exactly the sites most likely to need it. `registerHelper('x', () => …)` builds a fresh closure per call, so the entry differs even when the name does not; a registrar passing the same module-level function reference twice is not detected, which is no worse than not comparing at all. Hand that list back as `previous` on the next reload and each one is **undone** after the module imports and before the registrar runs — restored to its `prior` if it had one, unregistered if it did not — so whatever the new source does not re-register stays gone.
- **What the registrar registers is observed, not inferred from a diff.** `loadSiteHelpers` wraps `kiss.handlebars.registerHelper` for the duration of the `register(kiss)` call (restored in a `finally`, so nothing else ever sees the wrapper) and records every name it is given, in both the `(name, fn)` and object forms. A diff of the registry across the call cannot see a registrar that re-registers the **identical function reference** — a site that hoists its helpers to module scope and runs the registrar twice — so nothing was owned and the teardown had nothing to undo, on exactly the upgrading sites that do run it twice.
- **It also says when the registrar has already been run by hand.** Every site written before `folders.helpers` existed still calls `registerHelpers(kiss)` from its router, because the old docs said to, and nothing told the author it is now redundant. A name the registrar registers that something had _already_ put there is that signal, and it is a `notice` on the first load only (a reload restores priors first, so it would fire every time). A kiss built-in the registrar deliberately overrides is excluded — `Kiss` snapshots `_builtinHelperNames` after registering its own helpers and before the site's registrar can run, which is what makes the two distinguishable at all.
- **The rule is "undo what this load did", not "delete the name", and the difference is load-bearing.** Recording only names meant a kiss built-in the registrar had _overridden_ was counted as the site's and then deleted when the site stopped overriding it: `{{markdown}}` went `BUILTIN` → `SITE` → **empty**, silently, because an argument-less mustache is a missing property to Handlebars rather than a missing helper. A site that overrode `markdown` and later stopped would have lost Markdown rendering on every page with no error anywhere — worse than the bug the ownership rule was introduced to fix. The same rule settles the double-registration case: on a site whose router also calls the registrar by hand, teardown reverts the name to the **router's** registration, because that one is genuinely still in effect and was never kiss's to remove. The double registration is the thing to fix there, and the migrate skill names it. The ordering is the whole design — clearing before the import would empty a running site's registry on a module that fails to import, and clearing after the registrar would undo the load itself. A registrar that throws part-way undoes the **whole attempt** — anything it newly registered is removed and anything it overwrote is put back, not just the old names restored — because a failed load reports no `registered` list, so a helper the failed registrar added would be owned by nobody and never removed by a later success or a delete. The teardown also runs on the **no-registrar** path, which used to return above it: `registered: []` goes back to the caller, so "the build continues without site helpers" is now true rather than a sentence printed over a registry that still holds them.
- **`isHelpersEntry(folder, file)` is what a watch event is classified with, not `helpersEntry()`.** Both sides are resolved before comparing, and that is the whole point: `resolveConfig` leaves `./helpers` **relative**, so chokidar watches a relative path and emits relative events, while `helpersEntry` returns an absolute one. Compared with separator normalisation alone, an edit to the entry looked like an edit to a sibling — restart notice, no reload, no rebuild — in the **default** configuration, on the branch whose purpose is to stop a dev rebuild lying about what it picked up. No test caught it because every test in the suite named the folder absolutely (`grep -rn "'./helpers'" test/` returned nothing): the tested path and the shipped path were different paths. It also asks whether a file _could_ be an entry rather than whether it is the one precedence picks today, which is what a delete needs — with `index.js` and `index.mjs` both present, deleting `index.js` leaves `helpersEntry` pointing at `index.mjs`, so the file that just vanished would otherwise be classified as a sibling and the fallback would never load.
- **`isActiveHelpersEntry` is the narrower question a _change_ is classified with**, and the split from `isHelpersEntry` is deliberate. A reload busts the **selected** entry's URL and nothing else, so an edit to `index.mjs` while `index.js` is selected must not take the reload path — it would rebuild against the stale module and skip the notice that names the problem. A **deleted** candidate is the exception, and the reason the broader question exists at all: removing `index.js` changes which file is the entry, to `index.mjs` or to none, so it reloads even though it is not the selection when the question is asked.
- **The bust reaches the entry and nothing else, and that is stated rather than papered over.** `index.js`'s own `import './format.js'` resolves to the un-busted URL and comes back from the ESM cache, so re-running the registrar would register the **old** helper while every page re-rendered and the browser reloaded — the dev rebuild trap, inside the feature built to remove it. ESM has no cache-invalidation API, so `Kiss`'s `helpersChanged` has three outcomes. An **entry** reloads and re-renders. A **JavaScript sibling** gets the restart notice and **no rebuild**: no re-render, no live reload, no claim that the edit landed. **Anything else** — `labels.json` beside the helpers, say — is re-rendered without a reload, because a helper reads a data file at render time and a rebuild genuinely does pick it up; asking for a restart there is the same lie in reverse, and it is the lie `_handleChange` already had to be corrected for once.
- **The watcher for this folder lives in `watcher.js` and only exists when the folder does** (`existsSync`), so a site with no helpers opens no extra file handle. On a change to the **entry**, `Kiss` reloads fresh and re-renders every stack entry — helpers only affect rendering, so this is a replay minus its expensive half (no model re-read, no controller re-import, no URL model re-fetch).
- **A load failure is recorded as `<site helpers>` on `_failures`**, so `complete()` rejects rather than shipping a site whose templates silently lost their helpers. An entry that exports something other than a function is the same kind of failure, named explicitly, because the alternative is every `{{helper}}` rendering as nothing on a green build.
