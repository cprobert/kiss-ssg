Controllers return; they do not mutate

A controller that changed options.model in place was fine in v1 and is usually fine in v2 — until the model is a plain object and the site is running under .watch(). Then it drifts, one edit at a time.

Why the model kind matters

A .json file, a models folder or an http(s):// model is re-resolved on every build, so an in-place change is thrown away with it. A plain object model is replayed from a shallow snapshot of the original .page() call — the same object, every rebuild.

What that looks like

A controller doing model.pours.push(…) adds one more row on every save. The dev server looks fine at first and drifts further from a fresh build with each edit, which is the worst kind of bug to be told about second-hand.

This page's controller

It numbers the pours and counts them by building a new object: { ...model, pours: model.pours.map(…), count }. Nothing it was handed is touched, so the tenth rebuild renders exactly what the first one did.

How this example works

The same rule covers options.config: every page renders with its own shallow copy, so a controller may override config for its own page, but nested objects such as folders are shared and must be left alone. Return new values and the distinction never has to be remembered.
