Recipe · the exit code

Await complete(), and catch it

This is the migration that costs the most if it is missed, because nothing about it is visible: the build still ends, the script still exits, and the deploy still runs.

The v1 idiom

A chain that ends at generate(), or a callback-style complete(function () { … }) with no .catch. v1 logged a page's failure and resolved anyway, so a script shaped like that exited 0 on a build with pages missing from it.

What v2 does

complete() rejects with an AggregateError, and err.failures lists every failed page as { view, buildTo, error }. Unhandled, that is now an unhandled rejection rather than a silent success.

The catch has to do the work too

A failed build never runs complete()'s own callback. Anything that lived there — a sitemap, an index, a deploy step — has to run again in the catch, or it quietly stops happening on exactly the builds you most want to know about.

The shape this script uses

const finish = (outcome) =>
  console.log(`post-build step ran after a ${outcome} build`)

await kiss
  .complete(() => finish('successful'))
  .catch((err) => {
    reportBuildFailure(err)
    finish('failed')
  })

reportBuildFailure lives in examples/_shared/site.js: it prints each failure and sets process.exitCode = 1. Example 8 is the same shape with a feed that really does fail.

How this example works

Run this example and the console prints post-build step ran after a successful build. Run example 8 and the same line reads failed, after the failure report — that is the whole recipe: one function, called from both branches, so the exit code is the only difference.
