Recipe · Handlebars

One Handlebars environment per instance

v2 creates the environment with Handlebars.create(), so the global handlebars module knows nothing about this site's helpers or partials.

The v1 idiom

A project helper that did require('handlebars').partials[name]. Under v2 that object is empty: the helper returns an empty string, the page renders, the build is green, and the block is simply missing from the output.

The v2 form

Register on kiss.handlebars and read the partials off the same environment. This site registers a renderPartial helper that way; the card beside this one is that helper rendering a partial by name.

kiss.handlebars.registerHelper('renderPartial', function (name, context, options) {
  const partial = kiss.handlebars.partials[name]
  if (!partial) return ''
  const template =
    typeof partial === 'function' ? partial : kiss.handlebars.compile(partial)
  // Pass the helper's own data frame through — that frame is how the page is
  // recorded as using the partial, so a save re-renders just this page.
  return new kiss.handlebars.SafeString(template(context, { data: options?.data }))
})

Handlebars' own {{> partial}} needs no helper at all. This one exists for the v1 case it replaces: a partial chosen at run time and rendered against a context the template does not have. Pass options.data through as the recipe does: without it the partial still renders, but under watch() this page is not re-rendered when that partial changes.

How this example works

The same rule covers helpers you register yourself, the six kiss ships, and every partial under folders.partials and folders.layouts. If code outside the instance needs one of them, hand it kiss.handlebars rather than importing the module — that is the whole of the migration.
