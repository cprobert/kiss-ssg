# Plan — 2026-09-10: Site memory — a build-generated AIKB, a build-to-build diff, and a `kiss-memory` plugin

Status: in progress. Session file: `planning/sessions/2026-09-10-site-memory.md`.

## The problem this solves

A developer returns to a kiss site after years, or a second developer joins one. Nothing tells them what the site is, how it is built, what changed lately or why the odd parts are odd. Context windows that held that knowledge are gone. The engine knows most of the structural half at build time (which pages render which partials, which model and controller sit behind each page, which URLs are fetched, which pipeline steps run) and throws it away when the build finishes.

## What this branch ships

Three independent pieces, one contract. The engine writes the half of a site's knowledge base a machine can write; a `check` diff makes "did this change exactly what I meant" checkable; a second plugin ships the site-shaped open/pulse/close loop and a "catch me up" briefing that reads all of it back.

### A. `kiss.aikb()` — the build writes the site's map (`lib/aikb.js`)

**Public API.** `kiss.aikb(options?, callback?)` returns `this`, sits beside `.sitemap()` and `.llms()`, and is replayed by a whole-site watch rebuild the way `_llmsRequest` is. `options` is reserved (accepted, none defined yet). `callback(map)` receives the map object once written.

**Folder.** `config.folders.aikb`, default `./AIKB`. It is a source-side folder, meant to be committed, so it is not derived from `folders.src` and is **not** in `foldersToEnsure` — it exists only once `.aikb()` has run.

**Timing.** The dependency graph is filled by rendering, not by model resolution, so the write cannot happen on `_promises` like `.llms()`. It happens once per settled build, in the same place the report is assembled (`Kiss._finishBuild`), so every page has rendered and the graph is complete.

**Check mode.** `KISS_CHECK` publishes nothing, and the AIKB folder is a publish. Under check mode the map is computed and the note rules are evaluated, but **nothing is written**; the report carries the verdict with `written: false`.

**Files written (build mode), all byte-stable across identical builds — no timestamps, sorted keys and rows:**

| File                   | Regenerated?                              | Contents                                                                                                                                                                                                                                                                                                                                          |
| ---------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AIKB/README.md`       | written once if absent, never overwritten | what the folder is; which files are generated and must not be edited; how to write a note (the template below); which subjects need one                                                                                                                                                                                                           |
| `AIKB/site-map.md`     | every build                               | the human form of the map: Site (siteUrl, build folder, source folders), Pages table (Output, View, Model, Controller, Partials & layouts), Partials (name, pages that rendered it), Models (source, pages), Controllers (file, pages), Asset pipeline (steps). First line says it is generated by kiss-ssg from the build and must not be edited |
| `AIKB/site-map.json`   | every build                               | the same data as JSON: `{ site, pages[], partials{}, models[], controllers[], pipeline[] }`, every list sorted                                                                                                                                                                                                                                    |
| `AIKB/last-build.json` | every build                               | the `BuildReport` of this build with `duration` omitted (so git does not churn on timing). This is what `check --against AIKB/last-build.json` compares the working tree against                                                                                                                                                                  |
| `AIKB/notes/**/*.md`   | never by the engine                       | authored notes on subjects that carry judgement (below)                                                                                                                                                                                                                                                                                           |

**Map sources.** A page row comes from its stack entry and the registration it came from: `view`, `buildTo` reported against the real build folder (use the same path mapping the report uses), model source classified as `file:<name>` / `folder:<name>` / `url:<url>` / `inline` / `none` from the _registration_ (the stack's `options.model` has been replaced by data), controller as `file:<name>` / `inline` / `none`, partials and layouts from `graph.usesOf(buildTo)`. Partials come from `graph.toJSON()`. Pipeline steps from `config.assets.pipeline` (name, or first word of `run`). A `.pages()` fan-out contributes one row per item, as the report does.

**Subjects and notes.** A subject is a thing with judgement in it: a controller **file**, a **URL** model, a **pipeline step**. Inline controllers and inline models have no file to attach a note to and are not subjects (documented limit). Plain pages, partials and JSON models are never subjects — a note saying "renders the about page" is noise.

Note paths, derived from the subject id so the rule is mechanical:

- controller `stockist.js` → `AIKB/notes/controllers/stockist.md`
- URL model `https://api.example.com/v2/events?x=1` → `AIKB/notes/models/api.example.com-v2-events.md` (host + path, slugged; query dropped)
- pipeline step `tailwind` → `AIKB/notes/pipeline/tailwind.md`

Two rules, evaluated every build (check mode included):

- **missing** — a subject in the map with no note file.
- **dead** — a note file under `AIKB/notes/` whose subject is not in the map.

Note template (guidance in `AIKB/README.md`, not enforced this branch): `## What it does`, `## Why it is this way`, `## Gotchas`.

**Report.** `BuildReport` gains one appended key: `aikb: null | { folder: string, written: boolean, notes: { missing: string[], dead: string[] } }` — `null` when `.aikb()` was not called. `formatReport` adds one line per missing and dead note. **The exit code of `kiss-ssg check` is unaffected** by note findings this branch; a strict flag is a non-goal.

**Example.** `examples/8-data-fed-site.js` calls `.aikb()` with `folders.aikb: './8-data-fed-site/AIKB'`; the generated folder is committed (it is the exemplar), with a note for `stockist.js` so the example shows the rule satisfied. `test/integration/examples.test.js` keeps passing (the map must be stable across the two runs it does).

**Docs.** `AIKB/aikb.md` (template headings), the CLAUDE.md lookup-table row, `llms.txt` § API and the report shape, `README.md`, `types/` regenerated.

### B. Page hashes and `kiss-ssg check --against <report>` (`lib/kiss-page.js`, `lib/build-report.js`, `lib/check.js`, `bin/kiss-ssg.js`)

**Hash.** `KissPage.generate()` records a sha1 (hex) of the bytes it writes; `BuildPage` gains `hash: string|null` (`null` when the page was not generated or failed). Appended key on the page entry, report key order otherwise unchanged.

**Diff.** `diffReports(before, after)` in `lib/check.js`, pure: pages matched by `buildTo`; returns `{ buildDir, added: string[], removed: string[], changed: string[], unchanged: number }`, lists sorted. Reports are paired by `buildDir` (one script may build several sites); a report in `after` with no partner in `before` diffs as all-added. `before` may be JSON Lines (a `KISS_REPORT` file), a JSON array (what `check` prints) or a single report object (`AIKB/last-build.json`) — one reader, `readReportsFile(text)`, accepts all three. A page whose `hash` is `null` on either side counts as changed.

**Bin.** `check --against <file>` is an option before the script, like `--summary`. Missing or unreadable file: usage error, exit 1. JSON mode prints `{ "reports": [...], "diff": [...] }` when `--against` is given (documented: the shape changes only under the flag). Summary mode prints the report line(s) then, per report, `  + <path>` for added, `  - <path>` for removed, `  ~ <path>` for changed, and `  = N unchanged`. The diff never affects the exit code.

**Docs.** `AIKB/build-report.md`, `AIKB/check.md`, `AIKB/kiss-page.md`, `HELP` text, `llms.txt` § check, `types/`.

**Skills**, all `kiss-` prefixed, each pointing at `node_modules/kiss-ssg/llms.txt` for the API rather than restating it:

## Amendment — 2026-09-11: the ceremony is the only writer

**Why.** With `.aikb()` any real build rewrote `AIKB/last-build.json`, so the baseline the diff compares against moved on every build a developer ran to look at the site, and dev builds churned the page hashes. The diff answered "since my last build", not "since I opened this piece of work". The operator's requirement: the knowledge base is written once per closed piece of work and read at open, nothing else triggers it, and it only ever describes a build that worked.

**What changes.**

1. **`Kiss.aikb()` is removed**, with `_aikbRequest`, `AikbOptions`, the callback and the replay hook. `folders.aikb` stays as the folder's location.
2. **`kiss-ssg aikb <script>` is the writer.** The bin runs the site's build script exactly as `check` does (staged and discarded, `KISS_CHECK=1`, `KISS_REPORT`), and additionally sets `KISS_AIKB=1`. It accepts `--summary`, `--against <file>` and `--help` with the same parsing as `check`. It **refuses to record a failed build**: the engine writes nothing when any failure was recorded, and the summary says so. Exit code as `check`'s.
3. **The engine's rule**, in `_finishBuild()`, with the env read the way `KISS_CHECK` is (`''`, `'0'`, `'false'` mean off):
   - `folder = config.folders.aikb`. If `null` → `aikb: null`.
   - `record = KISS_AIKB is on`. `optedIn = record || <folder>/site-map.json exists` (a file only a record ever writes, so a site that has recorded once is opted in and a folder that merely exists is not — this repo's own `AIKB/` holds module notes and must not trip the docs-site build).
   - Not opted in → `aikb: null`, nothing built.
   - Opted in → build the map and evaluate the notes. `write = record && !config.dev && failures.length === 0`. Under `write`, `README.md` (once), `site-map.md`, `site-map.json`, then `last-build.json` after the report exists. `aikb: { folder, written, notes }` on the report either way.
4. **`check` diffs by default.** When `--against` is not given and a report's `aikb.folder` has a `last-build.json`, `check` diffs against it (read after the run, which under `check` has not touched the file). Pure helper in `lib/check.js` (`defaultBaseline(reports)` or similar). The `aikb` command diffs only when `--against` is given explicitly, because it has just overwritten that file.
5. **The exemplar moves from example 8 to example 9.** Example 8 fails on purpose and can no longer be recorded. Example 9 passes, has the controller file `shelf-item.js` used by two registrations and an inline controller. `examples/9-migrated-from-v1.js` gets `folders.aikb: './9-migrated-from-v1/AIKB'`; the folder is recorded with `node ../bin/kiss-ssg.js aikb 9-migrated-from-v1.js` from `examples/` and committed with one authored note `notes/controllers/shelf-item.md`. Example 8's `AIKB/` folder and `.aikb()` call are deleted; its `folders.aikb` is removed. The examples test asserts example 9's record is byte-stable and example 8 writes no folder.
6. **The report key, the folder layout, the note rules, `formatReport`'s note lines and `hash` are unchanged.**
7. **Skills.** `kiss-catch-up` runs a plain `check --summary` (the default diff appears when a record exists). `kiss-open` reads; if the site has no `AIKB/site-map.json` it records once (`npx kiss-ssg aikb <script>`) and commits it as the state at open. `kiss-pulse` runs a plain check. `kiss-close`: check `ok: true`, criteria against the default diff, notes complete, then `npx kiss-ssg aikb <script>`, commit the folder — the only moment the baseline moves. No skill mentions `.aikb()`.
8. **Docs.** `llms.txt` (method removed; § check gains the `aikb` command, `KISS_AIKB`, the default baseline), `README.md` (the `.aikb()` section becomes "Recording the knowledge base" beside "Checking a build"), `AIKB/aikb.md`, `AIKB/kiss.md`, `AIKB/check.md`, `AIKB/build-report.md`, `AIKB/config.md`, CLAUDE.md's table row and command list, `types/` regenerated, the plugin READMEs.

**Delegation.** D (engine + bin + tests + AIKB docs + llms.txt + CLAUDE.md + examples) and E (both plugins' skills and READMEs) run concurrently; Fable edits README.md, reviews, runs the gates and commits.

## Amendment — 2026-09-11 (2): consistency lints and consolidation

**Why.** The knowledge base has three parts that rot differently. The map cannot rot. Notes rot quietly in two mechanical ways: the subject changes and the note does not; the note names a file that no longer exists. Session logs grow without bound and are read back only three at a time, so old lessons become write-only. The operator wants the tools for this shipped now, so that client sites do not need a later engine upgrade to clean up.

**F — engine lints (mechanical, no judgement, free on every check).**

1. **Subjects carry a hash.** `site-map.json` gains `subjects: [{ kind, id, note, hash }]`, sorted like `noteSubjects`. `note` is the path `notePathFor` derives (relative to the AIKB folder, e.g. `notes/controllers/stockist.md`). `hash` is sha1 hex of: the controller file's bytes (read from `folders.controllers/<id>`; `null` if unreadable), the pipeline step's `run` string, or `null` for a URL model (its id is the whole subject). `site-map.md` gains a `## Subjects` table (Kind, Subject, Note, Hash first 12 chars).
2. **Notes may be stamped.** A note's optional frontmatter line `subject-hash: <sha1>` records the subject hash the note was last written against. The engine never writes it; the close skill does, copying it from `site-map.json`. A note with no stamp is not stale (it is simply unstamped).
3. **Two new findings** in `evaluateNotes`, appended to `notes`: `stale: string[]` — a present note whose stamp differs from the subject's current hash (URL models never go stale); `dangling: string[]` — entries `"<note path>: <token>"` for every backticked token in a present note that looks like a file reference (contains `/` or ends in `.hbs .js .mjs .cjs .json .html .md .css .scss .txt .xml`; no spaces, `<`, `>`, `*`, `{`, `}` or `$`) and resolves to nothing: not a file on disk relative to the cwd, not a page `view`, `buildTo`, partial name, model source name, controller id or folder in the map, and not a path under the AIKB folder itself. `formatReport` adds `note stale:` and `note dangling:` lines. Exit code unaffected. `BuildAikb.notes` typedef updated.
4. **The generated `AIKB/README.md`** (written once) documents the stamp, the four findings and `site.md` (below). Example 9's `README.md` is deleted and re-recorded so the shipped exemplar shows the current template; its `shelf-item.md` note is stamped with the real hash; `test/integration/examples.test.js` asserts `notes` has all four lists empty.
5. **`AIKB/site.md`** is an authored, evergreen page the engine never writes and never checks beyond dangling references (it is scanned like a note for `dangling` if present). Its shape is the skill's business, but the generated README names it and its sections: What this site is and who for · How it is deployed · Conventions · Standing gotchas · Retired feedback.

**G — skills.**

6. **`kiss-consolidate`** (new, `plugins/kiss-memory`). Runs a plain check first. Reads every `planning/sessions/*.md` whose frontmatter lacks `consolidated:`, plus `AIKB/site.md` (creating it from the template if absent), the notes and the check's findings. Then: folds durable lessons from the sessions' Feedback, Amendments and Verdicts into `site.md`; a Feedback item that has recurred across sessions becomes a line under Conventions or Standing gotchas and is listed under Retired feedback with the session dates, so `kiss-open` stops surfacing it; fixes `stale` notes (re-read the subject, update the note, restamp), `dangling` references and `dead` notes; writes `missing` notes only when the subject can be understood from the code, otherwise lists them for the human; flags contradictions between notes, `site.md` and the map for the human — never resolves a contradiction silently; stamps each session it read `consolidated: <date>`; commits with one message. Never records the knowledge base (the baseline is the close's). Triggered by `kiss-open` when a Feedback item recurs in three or more sessions or five or more sessions are unconsolidated, by `kiss-close` as a recommendation in its final report under the same rule, or by hand.
7. **`kiss-close`** stamps every note it writes or updates with `subject-hash` from `site-map.json`; treats `note stale:` like `note missing:` (a hard stop until fixed); fixes `note dangling:`. **`kiss-open`**'s read-back counts recurrences, recommends `kiss-consolidate` under the rule above, and surfaces session files still `status: open` on other branches as abandoned work. **`kiss-catch-up`** reads `AIKB/site.md` first when present (recollection, curated) and reports the four findings. **`kiss-pulse`** reads the two new lines. `kiss-check` and both plugin READMEs name the new findings.

**Non-goals.** No enforcement of `site.md` structure by the engine; no automatic stamping by the engine; no exit-code change for any finding.
