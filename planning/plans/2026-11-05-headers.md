# Security headers: kiss writes them beside the cache headers

**Date:** 2026-11-05. **Session:** `planning/sessions/2026-11-05-kiss-security-and-headers.md`. **Status:** the design the engine work builds against; amend in place with dated sections. **Evidence:** `planning/specs/2026-10-30-privacy-and-security-research.md` (the verified findings only).

## The problem

A static site can send security headers only through its host's config, and the most valuable one, a strict Content-Security-Policy, cannot be kept right by hand: MDN and web.dev both say a statically served page should use **hashes** of its inline scripts, not nonces, and every edit to an inline script changes its hash. The build knows every inline script it wrote; a person does not. So the engine should write the policy.

kiss already writes host header files: `lib/cache-headers.js` appends a marked block of `Cache-Control` rules to `_headers` (Netlify, Cloudflare Pages) and writes `cache-headers.firebase.json`, chosen by `config.host` or `cacheHeaders.format`. Its note records why it appends rather than overwrites: **sites keep their security headers in `src/assets/_headers`**. Security headers are a second kiss block in the same files, not a second writer for them.

## The design

1. **Opt-in, not default.** Security headers change what a browser allows, and one of them breaks a kiss feature: `X-Frame-Options: DENY` / `frame-ancestors 'none'` stops Moodle showing a learning package, which it does in an iframe. A convention with a default (`CLAUDE.md`) here would be a default that breaks working sites, so the feature is a config key a site turns on: `securityHeaders: { … }`, off when absent.
2. **The baseline it writes**, each traceable to a verified finding: `Strict-Transport-Security: max-age=63072000; includeSubDomains` (OWASP's value **without `preload`**, which OWASP says to check the requirements for first, and which cannot be undone quickly — a site adds it itself); `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `Cross-Origin-Opener-Policy: same-origin`; `Permissions-Policy` turning off `geolocation`, `camera` and `microphone`; framing denied (`frame-ancestors 'none'` and `X-Frame-Options: DENY`) **unless** the site builds learning packages or sets `framing: 'allow'`. **Never** `X-XSS-Protection` (OWASP: do not set it).
3. **The CSP**, in web.dev's strict form for static pages: `script-src 'sha256-…' 'strict-dynamic'; object-src 'none'; base-uri 'none'`, with one hash per distinct inline `<script>` body the build wrote. It restricts scripts and plugins only, so inline styles keep working (`kiss-performance`'s `inline-style-blocked-by-csp` check is about `style-src`, which this policy does not set).
4. **Report-only first.** MDN advises testing with `Content-Security-Policy-Report-Only` before enforcing. `csp: 'report-only'` is the default when `securityHeaders` is on; `csp: 'enforce'` sends the real header; `csp: false` sends none. No reporting endpoint is written: a static site has none to receive reports, so the browser's console is the report.
5. **One policy for the site, not one per page.** The hashes are the union over every page. A per-page policy is stricter but writes one rule per page into `_headers`; the union is one rule, and a script hashed for one page is still a script the site itself wrote. Reconsider if a site needs it.
6. **The site's own headers win.** Before writing, kiss reads the site's existing `_headers` (as `lib/css-audit.js` already does for its CSP); a header the site already sets for the same path is not written again, and kiss says which ones it skipped. Two `Content-Security-Policy` headers would be enforced together, so writing a second one would be wrong, not just redundant.
7. **Encodings:** the `_headers` block (Netlify, Cloudflare Pages) beside the cache block, between its own markers; `security-headers.firebase.json` as a fragment to merge, like `cache-headers.firebase.json`, never `firebase.json` itself; `security-headers.json`, the portable list, always. Vercel is listed as uncovered, as it is for cache headers. GitHub Pages cannot set headers: out of scope here; `kiss-security` covers the `<meta>` CSP fallback.
8. **Inline event handlers** (`onclick="…"`) and `javascript:` URLs cannot be allowed by a hash without `'unsafe-hashes'`. The build reports each page that has one, as a finding, rather than weakening the policy.

## Where it lives

A new module, `lib/security-headers.js`, pure functions plus one writer, the shape of `lib/cache-headers.js`, called from `lib/build-finish.js` next to `writeHostCacheHeaders`, using the same format resolution (`config.host`). Its result goes on `report().securityHeaders`. `GUIDE.md` gains a section; `llms.txt` one index line; `types/` regenerated; `AIKB/security-headers.md`; `kiss-security` uses it.

## Decisions for the operator

- **Opt-in** (recommended) or on by default?
- **One site-wide policy** (recommended) or per page?
- **HSTS without `preload`** (recommended): a site adds `preload` itself after checking the requirements.

## Not yet verified (the research's unverified claims)

The exact `_headers`, `firebase.json` and `vercel.json` syntax for headers, and Subresource Integrity's limits, were extracted but not verified when this was written. kiss already writes `_headers` and a Firebase fragment for cache headers in a form that works, so the encodings follow that code, not the unverified claims.

## Amendment, 2026-11-05: a light baseline, by the operator's choice

The operator's concern: "the security vulnerability footprint of a static site is reasonably low. We have to create a balance not to make the security so tight that it becomes unmanageable or too hard to update and use in day to day usage." Weighed header by header, the day-to-day cost sits almost entirely in a strict CSP (every widget an owner adds later is blocked until the policy changes), and next in framing (it breaks Moodle showing a learning package, and any site that embeds this one) and COOP (it can break pop-up payment and sign-in windows). The rest are set once and never touched.

**Decided:**

- **Opt-in** (`securityHeaders`), off when absent.
- **The light baseline only:** `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin` (the cheat sheet's value; the Secure Headers list's `no-referrer` is stricter and breaks referral reporting, so it is the site's to choose); `Permissions-Policy: geolocation=(), camera=(), microphone=()`; `Strict-Transport-Security: max-age=63072000; includeSubDomains`, **without `preload`** (finding 2: add it only once every subdomain serves HTTPS). Never `X-XSS-Protection` (finding 1).
- **Not written by the engine:** a CSP, framing headers and COOP. `kiss-security` explains each as an optional step a site takes when it has a reason, with its cost — including the hash-based CSP (finding 6) and its report-only rollout (finding 7).
- Design points 3, 4, 5 and 8 above (the CSP, report-only, its scope, inline handlers) are therefore withdrawn; points 6 (the site's own headers win) and 7 (the encodings, beside the cache headers) stand.
- **Firebase:** the fragment carries HSTS, but Firebase overwrites it on `*.web.app` (finding 3); the skill and the build's note say so.
- **2026-11-06, Claude, on re-reading finding 2 while writing `kiss-security`:** HSTS is `max-age=63072000` alone, without `includeSubDomains` as well as `preload`. The finding says to add both only once every subdomain serves HTTPS; sent by default, `includeSubDomains` would lock visitors out of any `mail.` or `old.` subdomain still on plain HTTP for two years — the "too tight" the operator warned against. The skill says when to add them.
