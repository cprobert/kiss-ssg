# Roadmap to 3.0

Written 2026-11-10 from [the architecture review](../reviews/2026-11-09-architecture-review.md)
and the operator's answers to seven questions the same day. It sequences improvements to kiss. It
adds one feature, partial transforms, which was already agreed, and then freezes.

Version numbers below are proposals. The operator decides each one.

## What 3.0 is

A small core that renders pages and gives a verdict, with everything else registered through one
extension contract, run by a command line that owns the process. The agents that build kiss and
the agents that build sites with it each load only what the task in front of them needs.

By the project's own rule a major is a new generation. This qualifies: the core, the build
script's contract and the instruction system all change shape.

## Decisions already made

| Question                           | Answer (operator, 2026-11-10)                                                                         |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Who 3.0 is for                     | The operator's fleet only                                                                             |
| Break or removal                   | Removal. 2.x minors move features behind the boundary with no site change; 3.0 takes them out of core |
| Batteries included or small        | Both: a small `@kiss-ssg/core`, and `kiss-ssg` kept as the preset that bundles the usual extensions   |
| Feature freeze                     | Partial transforms first, then freeze                                                                 |
| How much the build script may move | As much as needed                                                                                     |
| Process and documentation in scope | Yes, as a full track: kiss is built by AI for AI, with the operator overseeing                        |
| Horizon                            | As long as it takes                                                                                   |
| Compatibility with other tools     | Import paths and familiar names, not runtime compatibility                                            |

## Principles for the sequence

1. **Every phase ends with the fleet check.** `node scripts/fleet-check.mjs` on each real site,
   byte for byte, before and after. A phase that is meant to change output says which bytes.
2. **The verdict survives everything.** Nothing an extension does may be invisible to the build
   report.
3. **Earn the contract.** Three built-in features move behind the internal boundary before the
   contract is written down as public. The contract is then described from what those three
   needed, not designed ahead of them.
4. **Mechanism over prose.** A rule that has recurred becomes a gate, a hook or a command, and
   its paragraph is deleted.
5. **Budgets are gates.** "Improve, do not add" holds only if adding fails a check.

## Budgets

| `{any}` annotations in core                      | 95     | 20 or fewer                         |

## The engine track

### Phase 0. Clear the ground (2.14.x patches)

Small, independent, and each one removes a reason to distrust a later phase.

- Fix the staging sweep that removes a live build's folder (review item 1).
- Settle whether asset hashing breaks JavaScript that imports other files. Build the case; fix
  or document the boundary.
- Harden fetched data: redirects with custom headers, response size, wildcard aliases from
  records, sitemap escaping (review item 8).
- Add two gates: install the packed tarball and build with it; build 2,000 pages inside a time
  budget (review item 6).
- Publish from CI with provenance; pin actions by commit; restrict the CI token (review item 7).
- Find out why `node docs` rewrites pages unrelated to a change.
- Record the budgets above as a gate that reports, without failing yet.
- Record a fleet-check baseline for every site.

**Exit:** every open item in `TODO.md` is fixed, disproved or an issue, and the file is deleted.

### Phase 1. Partial transforms, then the freeze (2.15)

- Ship partial transforms as specified in
  [the design](../specs/2026-10-24-partial-transforms-design.md). Build its table keyed by
  extension as the first registry in the engine, in the shape Phase 4 will generalise.
- As a separate release, replace remarkable with markdown-it. Remarkable has not been updated
  since 2022; markdown-it is what Eleventy uses and has a plugin ecosystem. This changes output
  bytes, so it gets its own fleet check and its own upgrade note.
- Declare the freeze. The budget gate starts failing on growth.

**Exit:** both released, fleet migrated, freeze recorded in `CLAUDE.md` as one sentence.

### Phase 2. The command line owns the process (2.16)

Eleventy, Astro and Hugo all run the build from their own command. kiss asks each site to do it.

- `kiss-ssg build`, `kiss-ssg dev` and `kiss-ssg check` run the site's `router.js`. The command
  sets the exit code, prints failures, and restarts on an edit to the script.
- `router.js` stays as the page table. It no longer needs `reportBuildFailure`, the `--dev`
  argument parsing or the final `.catch`.
- `node router.js` keeps working through 2.x. It becomes loud by default: a build that exits
  without `complete()` warns and sets a failing exit code.
- The command passes its mode to the engine directly. `KISS_CHECK`, `KISS_AIKB` and
  `KISS_REPORT` remain as aliases until 3.0.
- Improve the three error messages the clean-room test found weak: suggest the nearest page id,
  report a failed page once instead of once per page linking to it, and name the build path
  instead of the staging path.

**Exit:** the starter and all fourteen examples have no failure boilerplate; a clean-room agent
builds the bakery brief without writing any.

### Phase 3. A boundary inside the orchestrator (2.17, internal)

No site changes. This is the largest piece of work and the one everything after depends on.

- One typed build-state object replaces the 86 private fields. The satellite modules take the
  parts they need, not the instance.
- The lifecycle becomes named stages in a fixed order: configure, register, load, render,
  finalise, verify, publish. The settle sequence in `complete()` becomes an ordered list of named
  steps, each declaring what it reads and writes.
- Construction stops doing I/O. Starting a build is an explicit call the command makes.
- One pass over each written page produces its references and audit facts, used by the link
  scan, the audit and the packager.
- Tests move from private fields to the build state and the report.

**Exit:** the private-field, `{any}` and test-reach budgets are met; fleet check identical; bench
within budget.

### Phase 4. Built-in features become extensions, still in the box (2.18 to 2.2x)

The word is **extension**, because "plugin" already means a Claude Code plugin in this repository
(`plugins/kiss-ssg`). An extension declares, and may do nothing it has not declared:

- its name and its config keys, with validation
- helpers, partial transforms and settle steps it registers
- the files it writes, claimed through the output registry
- audit checks it contributes
- its section of the build report
- its lines for the site's agent index, and its skills (see the agent track)

Order, easiest first, one release each:

1. **Learning packages.** The most isolated; proves steps and outputs.
2. **CSS purge and image encoding.** Proves steps that rewrite pages, and lets core drop `sharp`.
3. **Consent and embeds.** The hardest: helpers, steps, audit checks, a browser client and a
   report section. If the contract holds here it holds.

After those three, write the contract down, then move the rest: audit checks as contributions,
and redirects, cache headers and security headers as host adapters, the shape Astro uses.

Model schemas belong here too. A page may name a schema for its model, checked through the same
validation interface extensions use for config, so a bad record fails with the file and the
field. No schema library becomes a dependency; the interface accepts any that implements the
Standard Schema shape.

**Exit:** `lib/kiss.js` imports no feature module; every feature is reachable only through the
contract; fleet check identical at each release.

### Phase 5. Split the packages (3.0.0 prereleases)

One repository, npm workspaces.

| Package                           | Holds                                                                             |
| --------------------------------- | --------------------------------------------------------------------------------- |
| `@kiss-ssg/core`                  | Config, pages, rendering, assets, the report, links, the command line             |
| `@kiss-ssg/consent`               | Consent manager and embeds                                                        |
| `@kiss-ssg/learning-packages`     | IMS and SCORM packaging, the SCORM bridge                                         |
| `@kiss-ssg/images`                | Responsive images and the encode cache                                            |
| `@kiss-ssg/audit`                 | Launch-readiness checks, CSS audit, Lighthouse runs                               |
| A package for the working rituals | `session`, `base` and `issue`, beside the `kiss-memory` skills that call them     |
| `kiss-ssg`                        | The preset: core plus the extensions most sites use, so a site still asks nothing |

**Exit:** each package passes the gates alone; the preset builds every example and every fleet
site identically to the last 2.x release.

### Phase 6. 3.0

Remove what 2.x deprecated: callbacks on `generate`, `sitemap`, `llms`, `feed` and `robots`; the
environment-variable channel; `getModelByID`; construction side effects; `kiss.remarkable`.

One migration, run by `npx kiss-ssg@latest upgrade` and the `kiss-site-migrate` skill, one site
at a time, each ending in a fleet check.

**Exit:** all five sites on 3.0; budgets met; a clean-room build and a clean-room first change
both score at least as well as on 2.14.0.

## The agent track

Runs alongside the engine track. Three audiences, three sets of work.

### The agents that build kiss

- **Cut `CLAUDE.md` to rules** (with Phase 0). One sentence per rule and a link to its history.
  The history moves to `planning/history/`, which nothing loads by default.
- **Turn recurring rules into mechanisms** (continuous). The shell-edit hook is the model. Fix
  its false positive on capturing an exit code first.
- **Split each `AIKB` doc** (with Phase 3, module by module as it is touched) into invariants,
  which stay and ship, and history, which moves and does not ship.
- **A comment states the invariant in a line.** The story stays in git. Applied to each file as
  Phase 3 and 4 rewrite it, not as a sweep.
- **A one-page architecture map**, kept true by a test against the import graph.
- **Replace the sentence-ban table** with checks that run a doc's snippets against the engine.
- **A release train.** Proposed fortnightly, so the fleet is checked against a baseline that
  holds still.

### The agents that build sites

- **The index is assembled, not written.** Core carries a short index. Each extension carries
  its own lines. `kiss-ssg init` and `kiss-ssg aikb` compose the file a site imports from the
  extensions that site has installed. This ends the 16,000-character squeeze structurally: a
  site with no consent manager loads no consent text.
- **Skills travel with their extension**, and `GUIDE.md` splits the same way.
- **Fix the doc defects the clean rooms found:** the `isActive` examples that hand-write hrefs,
  the missing single-file fan-out example, the two stale counts in `kiss-site-new`.
- **An import path from Eleventy and Hugo content** in `kiss-site-import`: Markdown with front
  matter and data files become views and models. A skill plus a converter, not a runtime mode.

### The operator overseeing both

- **A budgets report** printed by the gates: nine numbers, the direction each moved.
- **A clean-room score at every phase exit.** The same two briefs as the review, run with
  `scripts/arms.mjs`, recording attempts to green and where the agent guessed.
- **A review from a different model family at every phase exit**, with the threat model and stop
  condition written first. Same-family agreement is not confirmation.
- **One diff read by the operator per phase**, chosen as the largest.

## What this roadmap leaves out, on purpose

- Alternative template engines (already declined).
- Incremental one-shot builds. At 2.3 ms a page there is no problem to solve.
- Server rendering, islands, or any client framework.
- Running Eleventy plugins, Hugo templates or Astro components.
- Readiness for outside contributors.

## Risks

| Risk                                                 | Guard                                                                        |
| ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| The contract is fixed before it is understood        | Three features move first; consent is one of them                            |
| Phase 3 stalls, and features creep back in around it | The freeze is a gate, not an intention                                       |
| An extraction changes output without anyone noticing | Fleet check at every release, byte for byte                                  |
| Two sources of truth while docs are being split      | Each doc moves whole, in the same commit as its module                       |
| The preset hides that core is small                  | Examples 1 to 6 build on core alone                                          |
| Peer practice cited here is from memory              | Check Eleventy's, Astro's and Hugo's current docs before Phase 2 and Phase 4 |

## Decisions still needed

1. The name "extension", or another word that is not "plugin".
2. The release cadence. Fortnightly is proposed.
3. Whether markdown-it comes in Phase 1 as proposed, or waits for 3.0 so the fleet takes one
   output change instead of two.
4. Where the working-ritual commands live: a new package, or inside the `kiss-memory` plugin.
5. The budget targets.
