# Session Reflection — 2026-09-09: Cut kiss-ssg 2.0.0 stable, drop the beta tag

_A Claude Code session is supervised collaboration: Claude generates, the human directs and judges. The session's quality is set by how actively the human supervised it. This reflection reads that supervision, as CPD for both._

**What we shipped:** `chore/2.0.0-release` (`727cf18`, `376e635`) — package.json/plugin
manifests bumped to `2.0.0`, a CHANGELOG entry, gates green. Upstream of the branch, in
the same session: `learna-kiss`'s `kiss-v2` branch (2 commits) and `student-handbooks`'s
`kiss-v2` branch (2 commits, one a real bug fix), plus a fresh re-verification of
`diploma-msc`'s existing `kiss-v2` branch and an as-found check of `a1k9training`'s
in-progress v2 rewrite — the evidence this release decision rests on.

## Reflect — what the session was

Two requests, one arc. The first ("confirm all our internal KISS sites are compatible…
C:\Code\kiss\\*") named the destination but not the method — no site list, no depth, no
"how would you know it's compatible". The second, this branch, was the opposite:
`/branch-open`'s interview pinned objective, ten success criteria, impact surface and
non-goals before a single file changed. **Planned once framed, but the framing itself
was left to Claude** for the harder, riskier half of the work — the four-site audit that
everything else depends on.

That audit turned emergent partway through. `learna-kiss` and `a1k9training` went
exactly as expected (build, diff, done). `student-handbooks` did not: a clean single-item
rebuild threw `The partial undefined could not be found` under v2, and the obvious
theory — a nested dynamic-partial pattern v2's `tracingPartial` wrapper mishandles — was
wrong. Proving that took a real chain: an isolated 2-level repro under v2 (passed), a
3-level repro matching the site's exact nesting (still passed), then pulling
`kiss-ssg@1.4.4`'s actual tarball source to find `_prepareMultiplePages` reusing one
`options` object across its whole `.pages()` loop — a v1 state-leak bug, not a v2
regression. The session didn't stop at "found a plausible cause"; it kept building
smaller reproductions until the mechanism was provable, then confirmed the leak's
real-world effect by diffing v1's actual output for two University of Buckingham pages
against what the (correct) partner data said should be there.

## Evaluate — how the human supervised the AI

**Verification & ownership** is where this session earned its rating, and split cleanly
in two. During the audit, none of it was delegated to trust: every "compatible" claim
was backed by an actual build, a byte-diff or text-stripped comparison against a v1
baseline, and — for `student-handbooks` — a from-source repro before the fix was
written. Nobody was asked to take "should work now" on faith. But the _supervision_ side
of that verification was thin: the operator never re-ran a build, opened a diff, or
looked at the fixed `learna-login.hbs` output themselves before the next request moved
straight to "cut the stable release" — the same "operator didn't look at the one
artefact they asked about" pattern the prior `2026-09-08-incremental-rebuild.md`
retrospective flagged for `dependency-graph.json`. It recurred here for the moodleAccess
fix, on four repos this time, not one.

**Pushback & steering** showed up exactly once, and it mattered: the four-site "yes,
compatible" report did not end the session — three `AskUserQuestion` prompts (release
tagging, ritual scope, who runs `npm publish`) held the actual publish action open for
an explicit decision rather than inferring one from "I think we're ready." That is the
right instinct for an irreversible, public action, and it is the moment this session's
supervision was most active — even though it came from Claude surfacing the fork rather
than the operator initiating it.

**Harness leverage** has a real miss worth naming: four independent site audits ran
serially in the main thread — full build logs, multi-KB diffs, and a from-scratch
`kiss-ssg@1.4.4` tarball extraction all landed in context that a `fork` per site would
have kept out of it, since none of that raw output was needed again once each site's
verdict was reported. `student-handbooks`'s debugging chain especially — a dozen-plus
tool calls building and discarding minimal repros — is exactly the "will I need this
output again" case the fork guidance names. The release ritual itself was the opposite:
`/branch-open` → `/secrets-scan` → `/docs-sweep` → `/corpse-collector` →
`/test-coverage-check --gate` → gates → `/retrospective`, run in the documented order,
each one actually read rather than rubber-stamped (the corpse-collector's 16 candidates
were individually checked against source and all classified as false positives, not
waved through as "probably fine").

**Iteration discipline** was strong precisely where it needed to be: the
`student-handbooks` investigation is a textbook example of not stopping at the first
plausible-sounding explanation. Two repros were built and passed before the real cause
(v1's shared-object leak, found by reading actual v1 source, not remembered) was
confirmed. A weaker session stops at "the failing pattern involves nested dynamic
partials" and ships a fix that happens to work without knowing why.

**Where the human intended to supervise versus where they actually did:** the operator
set the bar ("if you can confirm…") and then trusted the confirmation completely,
including the consequential unilateral calls inside it — discarding `a1k9training`'s
stray `package-lock.json` diff, resetting `kiss-ssg`'s own `bin/kiss-ssg.js` after a
gate failure traced to a post-reboot artifact, and rewriting 21 template call sites
across a live production site's partials. Each was reversible and each was reported, but
none was checked before the branch that ships them was opened.

**Competency level: Active supervisor.** The three-question pause before publish, and
the insistence (via the `/branch-close` ritual itself, which the operator explicitly
chose the "full" variant of) on running the complete checklist rather than the minimal
one, are real steering. What keeps this from **Agentic engineering lead** is the same
gap as last time: the verification that actually happened was thorough and rigorous, but
all of it was Claude's own, and the operator's role was choosing when to trust it rather
than checking it themselves.

  clarity cost with no compensating benefit, since nothing about `learna-kiss`'s build
  log informed the read on `a1k9training`.
- **Both — a bug found while verifying compatibility is still a live-site change.** The
  `student-handbooks` fix touches production Handlebars partials for a real client site.
  It was the right fix and it was explained, but "found a bug while checking v2
  compatibility" and "ship a correctness fix to a client's site" are two different
  requests bundled into one, and the second one didn't get its own confirmation step the
  way the npm publish did.
- **Process — the `2026-09-08` retrospective's open item recurred.** That reflection's
  top feedback item was "operator, look at the artefact you asked for" regarding
  `dependency-graph.json`; this session shipped a fix to four repos without the operator
  opening any of them. Naming it twice is the point of writing these down — the third
  occurrence should read as a pattern, not a coincidence.
